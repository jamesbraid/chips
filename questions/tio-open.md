# TIO open questions

Open points about the TIO that SGI's Linux Altix platform code (linux-5.3) does not settle. Each entry: question, routes tried, next route.

## ITTE use

[missing source] The flush path picks ITTE entry 0 whenever the node offset has bit 33 or above set, and entries 1 to 7 only when those bits are clear and bits 32:30 are nonzero. The address header says a TIO node offset always has its top bit set, which would make entry 0 the only one a real address reaches. Either the offset is narrower than the header's top bit implies on this path, or entries 1 to 7 map windows whose offsets have the top bit clear. Routes tried: `addrs.h`, `tio.h`, `pcibr_dma.c`. Partly answered 2026-11-22: the SHub 2 PROM (10.54) writes zero to all eight entries when it builds the TIO object and never writes a valid one, and no kernel path writes them; the entries stay invalid ([PROM access](../devices/tio/prom-access.md#itte-established-for-the-prom-unknown-for-hardware-use)). Still unknown: the offset width that makes entries 1 to 7 reachable, and what hardware does for a PIO that hits an invalid entry. Next: a TIO register specification.

## TIO interrupt delivery

[missing source] The kernel says bridges behind a TIO do not target SHub 2 interrupt registers, and a TIOCE rev A workaround stores a word to a TIO address taken from the interrupt's Crosstalk address. The register or message path that turns such a store into an interrupt vector on a CPU is not described. Routes tried: the files above and `tioce_provider.c`. Partly answered 2026-11-22 for the TIO's own error interrupt ([PROM access](../devices/tio/prom-access.md#interrupt-delivery-established-access-inferred-meaning)): the SHub 2 PROM writes the TIO's `0x90000480` with vector `0x36` shifted to bit 52 and a 16-bit processor id, `0x90000300` with the target NASID and `0x90000500` with `0xd`, and can forward a message by hand to a SHub register at offset `0x1000_0380`. Still unknown: the crosstalk address a TIOCP, TIOCA or TIOCE writes to raise a device interrupt (the SAL runtime's allocation functions were not followed) and the SHub register at `0x1000_0380`. Next: the SAL runtime's `SN_SAL_IOIF_INTERRUPT` provider functions and the TIO register specification.

## TIO local-block register map

[missing source] Only the identification word and the three ICE registers are named. The local block, link layer, error registers and the system controller UART (the PROM reading puts it at `0x9003_8000`, inferred) have no source. Partly answered 2026-11-22: offsets the SHub 2 PROM uses in the local block and the ICE and network-port ranges, with roles mostly inferred, are in [PROM access](../devices/tio/prom-access.md#local-block-map-established-offsets-inferred-roles). The system controller UART location and the register names remain unknown. Next: the TIO register specification, or the error decoder's name-to-offset pairing (`0xff4179c0` and neighbours in 10.54).

## TIO_NODE_ID upper bits

[settled 2026-11-22] The function at `0xff4ae920` in 10.40 is the TIO class's node-number method (slot `0x108` of the TIO method table; `0xff4af670` in 10.54), called once from the routing-table install (10.40 `0xff46effc`, 10.54 `0xff46f58c`). It read-modify-writes `0x90060e80`: 14 bits at 45:32 take the node's NASID and six bits at 53:48 take a power of two; bits 47:46 and the identification fields are kept (established from the 10.54 listing: masks, `dep.z` widths and the offset; the 10.40 call site was found by the same call search). So the register is a read-write node-number register on a TIO (the caller is a TIO method, so the earlier doubt that the node is a TIO is resolved), the Linux widget-format reading covers bits 31:1 only, and `registers.toml` now carries the two fields. The SHub 2 PROM names the same two fields `NODE_ID` and `NODES_PER_BIT` on its own node register. Still unknown: the derivation of the six-bit value (decompiler only) and its hardware meaning. Details: [PROM access](../devices/tio/prom-access.md#order-of-events-established-unless-marked).
