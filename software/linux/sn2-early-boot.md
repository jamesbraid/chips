# SN2 early boot: what the 2.6.5-7.244 Altix kernel needs from firmware

From the kernel entry point through `start_kernel`, `setup_arch`, `sn_setup` and `sn_cpu_init`: every table, memory-map type, SAL call, PAL call and SHub register the SLES 9 SP3 SN2 kernel touches before the platform is up, checked against what the [PROM](../firmware/snprom/README.md) and the [SAL runtime page](../sal/sn2-runtime.md) provide. Stage 6 of the [Altix 350 boot path](../../platforms/sn2/boot-path.md#6-linux-early-boot-on-sn2); the loader that precedes it is [ELILO on IA-64](../boot/elilo-ia64.md).

## Sources and grades

- **The kernel:** `ia64-boot/sn2-kernel/2.6.5-7.244-sn2/` (`vmlinuz-2.6.5-7.244-sn2`, `System.map-2.6.5-7.244-sn2`, `config-2.6.5-7.244-sn2`; SLES 9 SP3 `kernel-sn2`). `vmlinuz` is a gzip of an IA-64 ELF64 `ET_EXEC` with symbols. Read in Ghidra with the IA-64 processor module (`--ghidra-export` inflates it), 42 functions decompiled and 26 more for the ACPI and EFI helpers, plus an `ia64-linux-gnu-objdump` listing of the whole text segment used for the call-site scan of every SAL and PAL id. The decompiler output is navigation; each claim below was checked in the listing or in a constant the decompiler shows unchanged. Addresses are kernel virtual (`0xa000000100...`) or ELF file facts.
- **Linux source** (public, by version): v2.6.5 (`arch/ia64/kernel/{head.S,setup.c,efi.c,sal.c,acpi.c}`, `include/asm-ia64/system.h`, `include/asm-ia64/pgtable.h`) and v2.6.14 (`arch/ia64/sn/kernel/{setup,io_init,irq}.c`, `include/asm-ia64/sn/{sn_sal,sn_feature_sets}.h`), from the Library `linux-history` root. **A finding that changes how to read the old notes:** the SN platform code in this kernel is not the SN code of mainline v2.6.5 (which still builds a hardware-graph and reads klconfig directly for I/O). It matches mainline's later SN code in structure and SAL use (a version after v2.6.12 and before the `SET_CPU_NUMBER` and ACPI/PCI-segment OS-feature additions; **v2.6.14 as the exact match is inferred, the review could not pin the tag**), plus SHub 2 branches, so the later SN source names the SN functions and v2.6.5 names the generic ia64 ones. Evidence: the symbols `sn_prom_feature_available`, `hubdev_init_node`, `cnodeid_get_geoid`, `sn_pci_controller_fixup` exist, `sn_cpu_init` calls `GET_SN_INFO` with a SHub-2 flag, and no v2.6.5-only SN symbol (`init_hcl`, `sgi_master_io_infr_init`) is present. **Established** from `System.map` and the decompiled bodies; three functions re-checked in the review against the newest copy of the file in the Library (`sn_cpu_init`'s `GET_SN_INFO` handling and cpu-0 simulator check, `sn_setup`'s `SAL_FREQ_BASE` type 2 fallback of 33,333,333 Hz, `sn_pcdp_setup` against `sn_scan_pcdp`) agree in shape. The kernel also has `sn_pcdp_setup`, an SGI function with no mainline equivalent (mainline later has `sn_scan_pcdp`).
- **Chips pages** cross-checked: [sn2-runtime](../sal/sn2-runtime.md), [SAL calls](../sal/README.md), [klconfig](../../platforms/sn2/klconfig.md), [efi.md](../firmware/snprom/efi.md), [SHub registers](../../devices/shub/registers.md).

## The kernel entry state

Established from the ELF header, `_start` in the listing at `0xa000000100008320` (physical `0x4008320`), and v2.6.5 `head.S`:

- **Image:** entry point physical `0x4008320`; `PT_LOAD` segments at physical `0x4000000` (virtual `0xa000000100000000`, 7.1 MB), `0x4720000` and `0x4730000` (data and bss), ending at `0x4d34d60`. `_start` finds its own physical base with `mov r3 = ip` and clears the low 26 bits (`KERNEL_TR_PAGE_SHIFT` = 64 MiB), so it works at any 64 MiB aligned physical address, with `ip` physical when it starts; `0x4000000` is only the link-time `p_paddr`, and ELILO's `relocatable` option moves it by a multiple of 256 MiB. The loader uses `p_paddr` as the address ([ELILO](../boot/elilo-ia64.md#loading-the-kernel-entry-point-and-physical-load-address)).
- **What `_start` does with the machine:** `rsm psr.i | psr.ic` first (the listing shows `rsm 0x6000`), sets region registers 5, 6 and 7, pins one 64 MiB instruction and data translation register entry at `KERNEL_START` (`0xa000000100000000`), then `rfi`s into virtual mode. It then maps the boot task's stack, loads the RSE, and on the boot processor executes `dep r28 = -1, r28, 61, 3` and stores `r28` into `ia64_boot_param`: the loader's pointer is **physical** and the kernel turns it into a region-7 (identity-mapped, cached) address by setting the top three bits. Nothing else from the loader is read: `r28` only.
- **Therefore the entry contract is:** physical-mode execution at `0x4008320` with `r28` = physical address of a readable `struct ia64_boot_param` in write-back memory. Grade **established**.
- The first boot-processor call out of `_start` is `start_kernel`; non-boot processors take `start_secondary` (SMP) instead. Neither needs firmware before `setup_arch`.

## Order: `start_kernel` to `sn_cpu_init`

`start_kernel` calls `setup_arch` (generic ia64, `0xa00000010068e560`). The listing and decompiler give this order (**established**); everything outside it is untouched until later initcalls.

## EFI: what `efi_init` and the memory map need

All **established** from `efi_init` (`0xa00000010068c240`), `efi_enter_virtual_mode`, `efi_map_pal_code` and v2.6.5 `efi.c`.

- **Boot parameter block:** only the fields up to `initrd_size` (`0x50` bytes) are read; the block, the memory map and the command line are reserved and so must stay readable ([ELILO](../boot/elilo-ia64.md#the-structure-elilo-builds)).
- **System table:** `ia64_boot_param->efi_systab`, read as a region-7 address. The signature must be `IBI SYST` (a mismatch is a `panic`, as is a null system-table pointer); a header revision (`+8`) with a major number other than 1 only warns, and the header revision is what is printed. The firmware vendor string pointer at `+0x18` (UCS-2, up to 100 characters copied) is printed; **a non-null vendor pointer must be readable**. `RuntimeServices` at `+0x58` (kept, used for `GetTime` and `SetVirtualAddressMap`), `NumberOfTableEntries` at `+0x68`, `ConfigurationTable` at `+0x70` (24-byte entries, 16-byte GUID then pointer).
- **Configuration tables the kernel looks for** (matched by GUID in a loop; absent ones are simply left null): MPS, ACPI 1.0, **ACPI 2.0**, SMBIOS, **SAL system table**, HCDP. Of these the SN2 boot needs the SAL system table and the ACPI 2.0 RSDP; `acpi_find_rsdp` returns only the ACPI 2.0 pointer and prints "ACPI v1.0 r0.71 tables no longer supported" for a machine that has only the 1.0 one.
- **Memory-map types and attributes used:**
  - *Available RAM:* descriptors with attribute **write-back (bit 3)** and type `EfiLoaderCode`, `EfiLoaderData`, `EfiBootServicesCode`, `EfiBootServicesData` or `EfiConventionalMemory` (v2.6.5 `is_available_memory`). Everything else is not given to the allocator. After trimming to 16 MiB granules (16 KiB page config), partial granules are dropped with a notice. The kernel image, the boot-parameter block, the map buffer and the initrd sit in loader types, so the kernel reserves them explicitly and nothing else relies on the distinction.
  - *Runtime descriptors:* any descriptor with attribute bit 63 gets a `virt_addr` (`efi_enter_virtual_mode`): region 7 (`0xe...`) if write-back, otherwise region 6 (`0xc...`) if uncached, write-combining or write-through; then `RuntimeServices->SetVirtualAddressMap(map_size, desc_size, version, map)` is called through a physical-mode wrapper. On failure the kernel prints "unable to switch EFI to virtual mode" and **continues** with physical-mode wrappers.
  - *PAL code:* `efi_get_pal_addr` takes the first `EfiPalCode` (type 13) descriptor; a second one only prints "Too many EFI Pal Code memory ranges" and is not used. A descriptor longer than 16 MiB is a `panic`. `efi_map_pal_code` installs an instruction translation register for it (the mapping the later virtual-mode PAL calls need); with none the kernel prints a warning and installs nothing. A PAL range inside the kernel's own 64 MiB mapping needs no register.
  - *I/O port space:* the first descriptor of type 12 with `EFI_MEMORY_UC` (bit 0) set; the test in `efi_get_iobase` looks at that bit only, so the runtime bit (63) is not required, although the PROM's `0x8000000000000001` satisfies it. `ia64_iobase` is its physical address OR'd with region 6. Without it the kernel prints "No I/O port range found" and uses `ar.k0` (what the firmware left there; zero if untouched).
  - *Legacy VGA hole:* `efi_mem_type(0xa0000)` is compared with `EfiConventionalMemory`; anything else selects the VGA console driver (the later `sn_setup` check then disables it unless PCDP named a VGA device).
- **Runtime services used by the kernel before userspace:** `SetVirtualAddressMap` (above), `GetTime` (once, in `time_init`: a failure leaves the wall clock at 1970), and later the EFI variable and reset routines through the kernel's wrappers. [efi.md](../firmware/snprom/efi.md) lists the PROM's runtime services as reachable through SAL (`0x0a`, `0x0b`, `0x08`).
- **HCDP/PCDP:** `efi.hcdp` is optional. `sn_pcdp_setup` requires table revision 3 or later; it walks the device list after the UART entries (each `0x2d` bytes from `+0x28`) for a primary-console VGA device and records its I/O and memory bases; with none, `sn_setup` prints "SGI: Disabling VGA console". The PROM installs a revision-3 table ([efi.md](../firmware/snprom/efi.md#3-configuration-tables-and-where-sn2-specific-data-lives)).

## The SAL system table

`ia64_sal_init` and `early_sn_setup` (**established**):

- Signature `SST_` (a mismatch only prints). Header `0x60` bytes: SAL revision (u16) at `+8`, entry count (u16) at `+0x0a`, SAL_B version at `+0x16` (used as the version), OEM id at `+0x18`, product id at `+0x38`. A revision/version pair of `0x4929`/`0x4929` is rewritten to SAL 2.08. Entries start at `+0x60`.
- Entry type 0, the entry point: `+8` PAL_PROC, `+0x10` SAL_PROC, `+0x18` SAL global pointer. All three are converted to region-7 addresses (`ia64_sal` becomes a two-word descriptor `{SAL_PROC, gp}`). Both `early_sn_setup` (which walks only until it finds this entry, from the EFI table) and `ia64_sal_init` use it; **without it the early console is dead and the kernel prints "failed to find SAL entry point"**.
- Type 2, platform features: byte at `+1`: bit 0 bus lock, bit 1 IRQ redirection (turns on the kernel's redirect), bit 2 IPI redirection, bit 3 ITC drift.
- Type 4, PTC domain info: pointer kept. Type 5, AP wakeup: byte `+1` must be 0 (external interrupt), vector at `+8`; any other value prints "AP wakeup mechanism unsupported".
- Types 1 and 3 (memory descriptor, translation registers) are skipped by length (entry sizes 48, 32, 16, 32, 16, 16 for types 0-5).
- SAL is called through `ia64_sal(id, a1..a7)` with all of the kernel's scratch FP registers saved around it (`ia64_save_scratch_fpregs`), under a spinlock `sal_lock` for the calls the kernel marks non-reentrant, in **virtual mode with translation on** (`psr.dt/it/rt` set, region-7 identity addresses), interrupts possibly enabled. So the SAL runtime must answer in virtual mode ([sn2-runtime](../sal/sn2-runtime.md#how-a-call-reaches-its-routine)); `PAL_PROC` is called the same way with the `ia64_pal_call_*` wrappers.

## ACPI

ACPI is **used**, not absent: `CONFIG_ACPI_BOOT=y`, `ACPI_NUMA=y`. What the kernel needs from tables (**established** from `acpi_table_init`, `acpi_numa_init`, `acpi_boot_init`, `acpi_numa_memory_affinity_init`, `acpi_numa_processor_affinity_init`, `acpi_parse_madt`, and the `sn_setup` loop below):

| Table | Used for | If missing |
|---|---|---|
| RSDP 2.0 (via `efi.acpi20`) and XSDT | root of everything | warning, then nothing below parses |
| **SRAT** (type 14 in the kernel's table enum) | processor affinity entries (proximity domain byte at `+2`, APIC id `+3`, EID `+8`; no enable flag is tested) and **memory affinity entries** (proximity domain byte at `+2`, base `+8`, length `+0x10`, flags `+0x1c` bit 0 = enabled; disabled entries are skipped) fill `node_memblk` and `node_cpuid`. **At least one processor entry is required:** `acpi_numa_arch_fixup` builds the proximity-to-node maps and `numnodes` only when `srat_num_cpus` is non-zero; with none it marks node 0 online and leaves memory ranges unmapped. Nodes are numbered in ascending proximity domain over every domain any entry names | `find_memory` prints "node info missing!" and sets `numnodes` to 1; `sn_setup` then finds no memory range, computes NASID `-1` and calls `GET_KLCONFIG_ADDR(-1)`; the kernel stops with a `BUG` only if that call returns r9 = 0 (**established** from `find_memory` and `sn_setup`) |
| **SLIT** (type 12) | NUMA distances | warning only |
| **MADT** (type 1) | local APIC address (stored as `ipi_base_addr` in region 6 when non-zero; SN sends IPIs through the SHub, so it is not used for them: inferred), **LSAPIC entries (type 7)** give the CPU ids; IOSAPIC, interrupt source overrides, platform interrupt sources and NMI entries are parsed if present | "Can't find MADT" and the kernel assumes one CPU: it uses the id in `cr.lid` |
| FADT (type 7) | power and legacy flags | "Can't find FADT", boot continues |

The XSDT OEM id "SGI" is **not** used by this kernel (a fixed `sn2` build, no OEM-id lookup). The DSDT and the `SGIHUB` namespace of the v5.3 ACPI I/O path are not used either: this kernel does not set the OS ACPI or PCI-segment features, and its I/O path is the direct SAL one (`0x55` to `0x58`, below). The contents of the PROM's ACPI tables are **unknown** in chips; this is the table of what they must contain ([questions](../../questions/sn2-sal-open.md)).

### Differences from v5.3

- No `SET_CPU_NUMBER` call (chips lists it first; v5.3 only).
- `SET_OS_FEATURE_SET` twice (ids 0, 1: MCA slave to OS INIT slave, log single-bit errors), not four times; so no ACPI or PCI-segment OS feature is announced and the PROM is **not** asked to rebuild its DSDT.
- `GET_PROM_FEATURE_SET` **is** called (chips records that mainline v2.6.12 does not call it; this kernel's SN code is newer in this respect).
- I/O is discovered by the direct calls `0x55` to `0x58`, never by `IOIF_INIT` and the ACPI `SGIHUB` namespace.
- The node-table build is embedded in `sn_setup`, driven by `numnodes` from the SRAT; the klconfig scan loads the word at `+20` of the SAL result, the byte at `+5` of each board (`0x11` or `0x12`: `KLTYPE_SNIA`, `KLTYPE_TIO`), the halfword at `+48` (its NASID) and the word at `+0` (next board), as [klconfig](../../platforms/sn2/klconfig.md) already records.
- v5.3 has no `sn_pcdp_setup`; mainline later has the equivalent `sn_scan_pcdp`.
- SHub 2 code paths exist in this kernel (`GET_SN_INFO` SHub-2 flag, `pio_write_status` tables for slices 0 to 3), so an Altix 4700 PROM is a possible peer; the Altix 350 uses the SHub 1 branches.

## How `sn_setup` finds the nodes

(**established**, `sn_setup` listing.) For each node `n` counted by `acpi_numa_arch_fixup` (`nid_to_pxm_map`), it looks up the memory range whose proximity domain matches (no match gives `0xffffffff`, i.e. NASID `-1`) and computes `NASID = (range_start >> nasid_shift) & nasid_mask`, using the shift and mask from `GET_SN_INFO` (38 and `0x7ff`: **the SRAT memory ranges must be NASID-addressed**, `nasid << 38`). It stores the pair in `sn_cnodeid_to_nasid` and `physical_node_map`. Then, unless it is running on the simulator (`sn_prom_type` 2), for every node it calls `GET_KLCONFIG_ADDR(nasid)` and walks that node's `lboard` list for boards of type `0x11` or `0x12`, adding the NASID in each such board to the node tables if not yet known (this is how headless and I/O-only hubs get a compact node number). Only then does it allocate the per-node data, run `hubdev_init_node` and call `sn_cpu_init` again.

## Where a model that implements only what chips documents today fails

Assume the minimum of [sn2-runtime](../sal/sn2-runtime.md#what-a-synthetic-sal-for-one-node-must-do) and [efi.md section 6](../firmware/snprom/efi.md#6-what-an-emulated-machine-must-provide-for-efi-to-reach-the-boot-manager-prompt), plus an unreviewed ELILO. In boot order:

1. **ELILO load:** the PROM's map has nothing free at `0x4000000` in either address form, so ELILO needs `relocatable` in `elilo.conf` and then loads the kernel at the first 256 MiB boundary inside conventional memory ([the lone-node map](../firmware/snprom/efi-boot.md#efi-memory-map-on-a-lone-node)). The model keeps the PROM's map.
2. **ACPI tables:** the PROM's own tables, which meet everything below, are in [os-handoff-tables.md](../firmware/snprom/os-handoff-tables.md). The kernel needs an ACPI 2.0 RSDP in the EFI configuration table, an XSDT, an **SRAT with at least one processor affinity entry (without one `numnodes` is never derived) and one enabled memory affinity range per proximity domain, each NASID-addressed** (`nasid << 38`), a MADT with LSAPIC entries and ideally a FADT. Without an SRAT, or with memory ranges but no processor entries, `sn_setup` derives NASID -1 and stops with a `BUG` unless the SAL answers `GET_KLCONFIG_ADDR(-1)` with a non-zero r9. Without a MADT the kernel survives with one CPU.
3. **EFI memory map content:** chips' EFI page requires one conventional region; the kernel additionally needs write-back attributes on all RAM, one `EfiPalCode` descriptor, at most 16 MiB (larger is a `panic`; the PAL lookup does not test attributes), a type-12 port-space descriptor with the UC bit set (`0x8000000000000001` is accepted; or a non-garbage `ar.k0`), runtime attribute bits on the runtime descriptors, and the legacy `0xa0000` range typed so the VGA decision is intended.
4. **EFI runtime services:** `SetVirtualAddressMap` must exist (failure is tolerated, but a crash or a hang is not), `GetTime` should return a plausible time, and the firmware-vendor pointer in the system table must be null or readable. The PROM's runtime services are in [os-handoff-tables.md](../firmware/snprom/os-handoff-tables.md).
5. **SAL system table:** exactly the layout above, with the type-0 entry first at `+0x60` and an AP-wakeup entry (type 5) only with byte 0 equal to zero; the platform-features entry (type 2) changes kernel behaviour. The PROM's complete table is in [os-handoff-tables.md](../firmware/snprom/os-handoff-tables.md).
6. **SAL runtime in virtual mode:** every call is made with translation on through region-7 addresses; chips documents the runtime component for virtual-mode entry, but a model that answers SAL only in physical mode (as SAL_B does) would fault.
7. **Calls missing from chips' minimum list:** `GET_MASTER_NASID` (`0x02000004`, hwperf init), `PRINT_ERROR` (`0x12`), `LOG_CE` (`0x06`), `GET_FIT_COMPT` (`0x1b`), `HUB_ERROR_INTERRUPT`, `IOIF_ERROR_INTERRUPT`, the I/O slot enable/disable calls, `PHYSICAL_ID_INFO` (`0x01000013`) and the PCI config calls (`0x01000010`, `0x01000011`) are all made after `sn_cpu_init` and tolerate `-1`; the early set is covered. Chips marks `SET_CPU_NUMBER`, `GET_PROM_FEATURE_SET` and `SET_OS_FEATURE_SET` as v5.3 only (and says v2.6.12 calls none of the three). This kernel calls the last two but not `SET_CPU_NUMBER`; answering set 1 with -2 and OS features 0 and 1 with -1, as chips records, is right for them.
8. **Klconfig and the I/O hand-off:** `GET_KLCONFIG_ADDR` must return a non-null region-7-reachable address whose header word at `+20` leads to an `lboard` of type `0x11` carrying the node's NASID at `+48`. The PROM-side content for a 350 is now in [klconfig](../../platforms/sn2/klconfig.md#what-a-one-node-altix-350-with-an-io10-gets-summary) (node board `0x11`, midplane `0x42`, per-bus I/O boards; the heap address is bounded, not exact). The kernel's later `0x55` to `0x58` calls need the `hubdev_info`, `pcibus_bussoft`, `pcidev_info` and flush-list layouts in [sn2-runtime](../sal/sn2-runtime.md#the-structures-behind-0x55-to-0x58); a model must also return v0 = 1 from `0x56` for a missing bus. Open: BAR PIO addresses, `bs_legacy_*`, `bs_base` and `bs_xid` values, and the 350's I/O board type letter. (`pcidev_info` is 0x60 bytes; the flush entries are 0xa0-byte `sn_flush_device_war`.)
9. **Time and interrupts:** the RTC at `0x1_101c_0000` must count at the `SAL_FREQ_BASE` type-2 rate; the timer interrupt vector `0xef` comes from the processor's own interval timer (no SHub register), and `PAL_FREQ_RATIOS` must be coherent with `SAL_FREQ_BASE` type 0.
10. **Console:** the early console writes with `CONSOLE_PUTB`; the kernel prints nothing visible if the SAL console routes nowhere. The PROM routes it through `candidate_dev[block B +0x88]` to the system-controller objects, which buffer the text and send it as framed L1 messages (flushed after each PUTB) over the junk-bus UART; a real 350 selects `sysctl_rt_dev`, index 1 ([sn2-runtime](../sal/sn2-runtime.md#console-0x02000021-to-0x0200002c)). A model without an L1 can answer `PUTB` itself with status 0 and the count; the kernel uses only the count.

## I/O discovery in SN2 kernels

The Debian 7.11 kernel (Linux 3.2.78) is read call by call, with structure offsets, on [SN2 I/O discovery in the 3.2 kernel](sn2-io-discovery-3.2.md).

Which path an SN2 kernel takes to find its PCI buses, what gates each, and what the SAL 5.04 PROM of snprom 10.54 (`shub1snprom.bin`) hands over. Kernel facts are from the linux-sn2 tree at the v7.0-rc1 and v7.3-rc3 tags (the discovery path is the same in both, and `io_common.c` and `setup.c` differ only in DMA-related code; the v7.0 GPU tag was not available). PROM facts are from the SAL_B handlers read in Ghidra. Grades follow the page header.

**The gate (established, kernel source).** `sn_io_early_init` (an `arch_initcall` in `io_common.c`) copies the DSDT's OEM revision into `sn_acpi_rev`. `SN_ACPI_BASE_SUPPORT()` is `sn_acpi_rev >= 0x20101`.
- True: `sn_io_acpi_init` (`io_acpi_init.c`). It calls `acpi_get_devices` for `SGIHUB` and `SGITIO`, which copies each hub's `hubdev_info` out of a vendor-typed `_CRS` resource, then calls `SN_SAL_IOIF_INIT` (0x5f) once and panics unless status and v0 are both 0. The kernel makes no `0x55`, `0x56` or `0x57` call on this path. Bus and device records (`pcibus_bussoft`, `pcidev_info`, `sn_irq_info`) also come from vendor `_CRS` resources, matched by `_SEG`, `_BBN` and `_ADR`. The PCI root bridges come from the generic ACPI scan of the namespace.
- False: `sn_io_init` (`io_init.c`), the direct walk with `0x55`, `0x56`, `0x57`. This is the 2.6.5 path (that kernel has no ACPI I/O code), so the SAL walk and its PROM handlers above are what the primary distro target uses.
- `sn_ioif_inited` is set late (`fs_initcall`) and only gates interrupt redirection and the DMA flush code; it does not gate discovery. The PROM feature words and the OS feature calls do not gate it either. The kernel ignores the status of `SET_OS_FEATURE_SET`, so the -1 the PROM returns for features 0 and 1 is harmless.

**What the PROM does today (established).**
- `GET_PROM_FEATURE_SET` (`0xffb60170`): set 0 returns 0xf (PAL cache flush safe, per-device flush list, hotplug, CPU disable); set 1 returns -2. It does not depend on the OS feature calls.
- `SET_OS_FEATURE_SET` (`0xffb5fc90`): only 2 and 3 are implemented; 0 and 1 return -1. Feature 3 runs the segment-enable routine (`0xffb20230`), which re-initialises the hubs and buses and rebuilds the ACPI tables. Feature 2 sets bit 2 of block B `+0xc8` and issues the internal call `0x5c`, unless the POD variable `NoACPIIO` is set to non-zero.
- The ACPI builder (`0xffb58ca0`) generates the DSDT (the AML for one hub device per node and one bus device per bus on it) and one SSDT per function-0 PCI device, and appends the SSDTs to a new XSDT, whose address it writes into the RSDP. The header writer's OEM revision argument is `0x101` only when bit 2 is set and the DSDT is longer than the 36-byte header; a header-only DSDT stays at `0x20001`. **So 0x20101 is the sign that a DSDT with a body exists, which settles the earlier unknown about which condition selects it.** The decoder is the tail of `0xffb58ca0`; the strings it prints ("generating DSDT", "ACPI 2.0 dsdt at", "generating SSDTs") are in the image.
- `IOIF_INIT` (`0x5f`, case in `0xffb1e660`): runs the hub late-init loop (`0xffb29390`) and the bus late-init loop (`0xffb2c370`), returns r8 = r9 = 0. Needs nothing from the OS feature calls.
- Order that matters: the kernel's order is 0, 1, 3, 2. The DSDT body is therefore built at feature 3 and only re-stamped at feature 2.

**Where an ACPI-path boot loses its PCI buses (inferred from the kernel source, plus one emulator observation; not settled).** An emulator run of the 7.0 kernel against this PROM made the calls above in that order and then called `0x5f` once; the guest then logged `AE_NO_ACPI_TABLES` while loading the namespace, and had no PCI devices. The tables themselves were present in `/sys/firmware/acpi/tables` (APIC, DSDT, FACP, FACS, SLIT, SRAT, two SSDTs). The cause reads as a kernel interaction, not missing PROM content:
1. `setup_arch` calls `acpi_table_init()` before `sn_setup`; `sn_setup` calls it again after the OS feature calls, to pick up the rebuilt tables.
2. The second call memsets the static table array but leaves `current_table_count` alone, so the first pass's six entries (MADT, SRAT, SLIT, FADT, the stub DSDT and the FACS) become zeroed holes and the second pass's tables, including the DSDT, land after them. `acpi_gbl_dsdt_index` points at the new slot.
3. `acpi_early_init` reallocates the root table list; `acpi_tb_resize_root_table_list` copies only entries with a non-zero address, so the holes disappear and every table moves down, but the DSDT, FADT and FACS indexes are not updated.
4. `acpi_tb_load_namespace` then reads `tables[dsdt_index]`, which no longer holds the DSDT, and returns `AE_NO_ACPI_TABLES`. With an empty namespace `acpi_get_devices` finds no `SGIHUB`, the ACPI scan finds no root bridge, and no device-level SAL call follows.

Unverified: that this sequence is what the run did, and why the same sequence would work on a real Altix. The next subsection traces it with line numbers and says what would settle both.

**Fix options (not applied).** In the kernel, reset the table list before the second `acpi_table_init()` (or skip the first pass on SN2). Presenting the final DSDT and SSDTs before the first pass does not help: the second pass still appends after the holes, so the index is off by the first pass's count whatever the tables hold.

### Second table pass and the DSDT

Kernel side read in the linux-sn2 tree at the v7.3-rc3 tag; the v5.15 and v6.19 branches carry the same code in the same functions (checked for `acpi_gbl_dsdt_index`, the compaction loop and the namespace-load test). PROM side read in the `shub1snprom.bin` 10.54 image (SAL 5.04). Guest facts are from an emulated boot: RSDP, XSDT (pass 1: 4 entries, length 0x44; pass 2: 6 entries, length 0x54), FADT revision 3 length 0xf4 with 32-bit `DSDT` and `FIRMWARE_CTRL` zero and the `X_` fields set, `X_DSDT` unchanged between passes (stub with OEM revision 0x20001, then the full table with 0x20101, length 0x370), two SSDTs of 0x95 bytes. Decompiler output was used for navigation; call sites were cross-checked in a plain listing. The header re-stamp rules below were read from the decompiled bodies only.

**1. What the second pass does to the root table list (established from source; that this run followed it is inferred until the values below are observed).**
1. Pass 1: `setup_arch` (`arch/ia64/kernel/setup.c:585`) calls `acpi_table_init` -> `acpi_locate_initial_tables` (`drivers/acpi/tables.c:710`) -> `acpi_initialize_tables` (`acpica/tbxface.c:68`). Early validation is off by default (`tables.c:719`), so installs do no checksum or duplicate check. `acpi_tb_parse_root_table` (`tbutils.c:216`) installs MADT, SRAT, SLIT, FADT at indexes 0 to 3; `acpi_tb_parse_fadt` (`tbfadt.c:316`) installs the DSDT stub at 4 and the FACS (from `X_FIRMWARE_CTRL`) at 5. `acpi_gbl_dsdt_index` = 4, count = 6.
2. Pass 2: `sn_setup` (`arch/ia64/sn/kernel/setup.c:389`) calls it again. `acpi_initialize_tables` memsets the whole static array (`tbxface.c:88`) but nothing resets `current_table_count` (only `acpi_tb_terminate`, `tbdata.c:725`, and the resize, `tbdata.c:640`, write it). Indexes 0 to 5 are now zeroed holes. `acpi_tb_get_next_table_descriptor` (`tbdata.c:676`) appends at 6: MADT 6, SRAT 7, SLIT 8, FADT 9, then the FADT parse runs inside the loop (`tbutils.c:333`): DSDT 10, FACS 11; SSDTs 12, 13. `acpi_gbl_dsdt_index` = 10, `acpi_gbl_fadt_index` = 9, count = 14. The 128-slot array is not resized.
3. `acpi_early_init` (`drivers/acpi/bus.c:1291`) calls `acpi_reallocate_root_table` (`tbxface.c:133`). Validation is now on, so its loop (`tbxface.c:176-186`) checksums and duplicate-checks every unverified entry and uninstalls failures (clears the address). Then `acpi_tb_resize_root_table_list` (`tbdata.c:586`) allocates count + 4 slots and copies only descriptors with a non-zero address (`tbdata.c:625`). The six holes vanish, the eight live tables are renumbered 0 to 7 (DSDT now 4), count = 8. No code updates the DSDT, FADT or FACS indexes: the only writers are `tbfadt.c:316-330`.
4. `acpi_bus_init` (`bus.c:1373`) -> `acpi_load_tables` -> `acpi_tb_load_namespace` reads `tables[acpi_gbl_dsdt_index]` (`tbxfload.c:118`), slot 10, past the live count and zeroed. The test at `tbxfload.c:120-123` (signature is not DSDT) returns `AE_NO_ACPI_TABLES`.
5. Why nothing else notices: `sn_io_early_init` (`arch/ia64/sn/kernel/io_common.c:471`) reads the DSDT with `acpi_get_table`, which finds it by signature, not by index. So the OEM revision reads 0x20101, the ACPI I/O path is chosen, and the empty namespace then finds no `SGIHUB`.

Answers to the specific questions. A stale index: yes, the descriptor is intact, the index is off by the first pass's descriptor count (6). Duplicate detection: no. The second pass's memset clears the verified flag, so `acpi_tb_check_duplication` (`tbdata.c:428-442`) skips every pass-1 entry, and a DSDT at the same address is never compared with the stub. (The reallocate loop can still drop a pass-2 table that is byte-identical to an earlier verified one, or has a bad checksum; for the DSDT that would end in the same error, but it logs "Attempted table install failed" or "Table is already loaded".) Resize between the passes: none; the only move is step 3, and it is the cause. The FADT form is handled: `acpi_tb_convert_fadt` (`tbfadt.c:473`) calls `acpi_tb_select_address`, which returns the 32-bit value only when the 64-bit one is zero, so `X_DSDT` alone is enough, and `acpi_tb_parse_fadt` installs from `Xdsdt` (`tbfadt.c:316`) and `Xfacs`. `arch/ia64/kernel/acpi.c` has no DSDT code; it reads the FADT by signature (`acpi_boot_init`, line 671). No change to the DSDT address, length or 32-bit field avoids this: the wrong index is a function of the pass-1 count only. It is avoided only if pass 1 left no descriptors, or the kernel resets the list (zero `current_table_count` and the four indexes in the static-array branch of `acpi_initialize_tables`, or before the second call in `sn_setup`).

With `NoACPIIO` set (see [PROM variables](../firmware/snprom/efi-boot.md#prom-variables)), the DSDT is header-only in both passes, the XSDT has 4 entries and there are no SSDTs. The stale-index defect still fires, but the failed namespace load is harmless because OEM revision 0x20001 selects the direct SAL walk.

**2. The FADT form (established, PROM code).** The FADT builder (`0xffb57c40`) takes a zeroed 0xf4-byte block from the SAL-to-EFI hand-off arena (`0xffafc350`, which clears what it returns) and never stores the 32-bit `FIRMWARE_CTRL`, `DSDT` or PM and GPE block fields. It stores the 64-bit blocks, `X_FIRMWARE_CTRL`, and `X_DSDT` as its second argument (0 at hand-off). The DSDT address later reaches `X_DSDT` only through `0xffb58ca0`, as eight byte stores at FADT `+0x8c`, followed by a re-checksum. So the form is the same on any board running this image; the only input-dependent part is whether `X_DSDT` is 0 or an address. If generation fails, `0xffb58ca0` still stores a header-only DSDT there.

**3. How the DSDT address and length arise (established unless marked).**
- `0xffb58ca0` generates only when FADT `X_DSDT` is 0. The body comes from `0xffb4d590` (AML per node that has a node record, via `0xffb4c2b0`), wrapped by `0xffb5c620` in a freshly allocated block of body + 0x24 bytes with OEM revision 0x20101 and the creator-revision word set to the full length. SSDTs come from `0xffb52720`: one per function-0 device the PROM found, walking segments and buses.
- The block is then **hidden, not shrunk**. When bit 2 of the OS-feature word (block B `+0xc8`) is clear, `0xffb58ca0` rewrites the header to length 0x24 and OEM revision 0x20001 and cuts the XSDT to 0x44, keeping the real length in the creator-revision word. When the bit is set it restores both from that word and stamps 0x20101. So a stub and the DSDT it hides are one buffer, and the restamp never allocates. The same address in both passes therefore needs no coincidence unless feature 3 rebuilds in between (below).
- The first generation happens before the kernel: EFI start-up issues SAL `0x45` (start I/O, `0xffb20350`) -> `0xffb2d450` -> `0xffb585c0` (frees the old DSDT and SSDTs, zeroes `X_DSDT`, cuts the XSDT to 0x44) -> `0xffb58ca0`, with bit 2 clear. `0xffb2d450` is also reached from the first `0x55`, from `0x5b` when it runs a second time, and from feature 3.
- Feature 3 (`0xffb20230`) rebuilds only if the I/O state word at `+0x10` is 0: it sets it to 1, re-initialises, and runs `0xffb2d450` again, so the DSDT, SSDTs and XSDT are freed and **allocated fresh**; it is not a reuse of the buffer. If this ran in the guest, the unchanged `X_DSDT` means the allocator handed back the freed block (whether it ran is not observed; the I/O state word's value after EFI start-up was not read). If that word is already non-zero, feature 3 does nothing. Feature 2 sets bit 2 and issues `0x5c` (`0xffb58ca0` again, now only a restamp), unless the POD variable `NoACPIIO` is non-zero; then it logs "ACPI IO disabled" and the DSDT stays at the stub.
- Address inputs: the block size (node records, buses and devices per hub), and the hand-off arena's state: its boundary-tag allocator (`0xffac30c0`, free `0xffac2330`, size bins and coalescing) returns whatever fits after every earlier hand-off allocation and free (EFI tables, SAL table, memory descriptors, the first generation's blocks, the AML builder's growing temporary buffer, `0xffafc4b0`). The same address after free-then-allocate of an equal size is inferred, not read: the large-block path of the allocator was not decoded. A model controls the node table, the PCI topology the PROM scans and the EFI memory map, not the allocator. Real hardware with more buses, devices or earlier allocations would put the pass-2 DSDT elsewhere and with another length, and none of that matters to the failure in section 1, which does not read the address.

**Which model difference could matter (not established).** Nothing at the table level explains why hardware would boot. The defect needs only a populated pass 1, and the stock PROM presents a stub DSDT in pass 1 by design, so an SN2 kernel with this ACPICA would hit it on hardware too. Either the hardware boot used a kernel or ACPICA without it (unknown which tree that was), or hardware stayed off the ACPI I/O path. The one input that gates that path is `NoACPIIO` (feature 2 skips the reveal and the DSDT keeps OEM revision 0x20001, so `sn_io_early_init` takes the direct `0x55`-`0x58` path); whether hardware has it set is unknown. How to set it and where it is stored: [PROM variables](../firmware/snprom/efi-boot.md#prom-variables).

**Checks in the guest.**
- Early dmesg: two `ACPI: DSDT` lines, the first length 0x24 and revision 0x20001, the second 0x370 and 0x20101; "Early table checksum verification disabled"; no "Attempted table install failed" or "Table is already loaded" (those would point at the reallocate loop instead).
- After the second `acpi_table_init` returns (in `sn_setup`): `acpi_gbl_root_table_list.current_table_count` = 14, descriptors 0 to 5 all zero, `acpi_gbl_dsdt_index` = 10, `acpi_gbl_fadt_index` = 9, `acpi_gbl_xfacs_index` = 11.
- On return from `acpi_tb_resize_root_table_list` in `acpi_reallocate_root_table`: count = 8, max = 18, the DSDT descriptor at slot 4, `acpi_gbl_dsdt_index` still 10.
- A breakpoint at `acpi_tb_load_namespace` shows slot 10 zero; stopping where `tbxfload.c:121` sets the status confirms the exact branch.
- To confirm the cause and not just the symptom: zero `current_table_count` and set the four indexes to 0xFFFFFFFF before the second call, and the namespace should load. To test the `NoACPIIO` branch: set the variable non-zero in the model's variable store and look for the PROM's "ACPI IO disabled" line and OEM revision 0x20001 in the second pass.

## Review of the 350 summary, block A, I/O SAL and console (second reader)

## Review (second table pass and the DSDT, commit b5edaac)

Independent review of chips commit `b5edaac` (examined at that revision; the later `eae2bb7` edits one sentence of the same section). The reviewer wrote none of it. Method: the ACPICA, `tables.c`, `bus.c`, `setup.c` and `io_common.c` files read in the held linux-sn2 tree at tag `v7.3-rc3-epic1-sn2`, with the compaction loop and the namespace-load test also read on the `v5.15-sn2` and `v6.19-epic3-sn2` branches; the PROM (`shub1snprom.bin`, SAL 5.04, sha256 `51ccf9ad830b...`) re-read in the Ghidra IA-64 module (`--sn2-prom --sal-runtime --no-analysis` over the named addresses) and in a whole-image `ia64-linux-gnu-objdump` listing. Decompiler output was used for navigation; the claims below marked "listing" were checked there. Nothing was run.

**Confirmed.**
- The ACPICA mechanism and every step in item 1 (grade as written): the static array is memset without touching `current_table_count` (`tbxface.c:88`; only `acpi_tb_terminate` and the resize write the count, `tbdata.c:725` and `:640`), descriptors are appended at the old count (`tbdata.c:660-680`), the resize copies only entries with a non-zero address (`tbdata.c:625`), `acpi_tb_parse_fadt` is the only writer of the DSDT and FACS indexes (`tbfadt.c:316`), and `acpi_tb_load_namespace` reads `tables[acpi_gbl_dsdt_index]` and returns `AE_NO_ACPI_TABLES` on a non-DSDT signature (`tbxfload.c:118-123`). Call sites match: `setup.c:585`, `sn/kernel/setup.c:389`, `bus.c:1291` and `:1373`, `tables.c:719`, `io_common.c:471`. The counts (6, then 14, then 8, indexes 10, 9, 11) follow from those sources; they were not observed.
- FADT builder `0xffb57c40`: block of 0xf4 bytes from the hand-off arena allocator `0xffafc350` (which zeroes it); it never stores offsets `0x24` (`FIRMWARE_CTRL`) or `0x28` (`DSDT`); it stores `X_FIRMWARE_CTRL` (`+0x84`) from its first argument and `X_DSDT` (`+0x8c`) from its second; header revision 3. (Ghidra and listing.)
- DSDT restamp `0xffb58ca0`: generates only when `X_DSDT` is 0 (calls `0xffb5c810`, which calls the AML builder `0xffb4d590` and the wrapper `0xffb5c620`, then the SSDT builder `0xffb52720` via `0xffb5c940`); with bit 2 of the word at `[[0x1000040]+0xc8]` clear it rewrites the header to length 0x24 and OEM revision 0x20001, keeps the real length in the creator-revision word and cuts the XSDT to 0x44; with it set it restores both and stamps 0x20101. `0xffb585c0` frees the DSDT, zeroes `X_DSDT` (FADT `+0x8c`), frees the XSDT entries past 0x44 and cuts the XSDT to 0x44 (listing; the decompiler dropped blocks). SAL `0x45` (`0xffb20350`) -> `0xffb2d450` -> `0xffb585c0` then `0xffb58ca0` is as written.
- Feature 3 (`0xffb20230`): proceeds only when the word at `[[0x1000040]+0x40]+0x10` is 0, calls `0xffb2d110(1)` (which stores 1 there) and then `0xffb2d450(0,0,1,0)`. Feature 2 (`0xffb5fc90`): when `NoACPIIO` is zero or absent it sets bit 2 and issues SAL `0x5c`; otherwise it prints "ACPI IO disabled" and sets neither.

**Findings.**
1. **`NoACPIIO` has a second reader that the page omits.** `0xffb58ca0` itself reads `NoACPIIO` (string reference at `0xffb595d0`; the only other code reference is `0xffb5ff30` in feature 2). When it is non-zero the first generation, at SAL `0x45` before the kernel, builds no AML body and no SSDTs: it prints no "generating DSDT/SSDTs" line and stores a header-only 0x24-byte DSDT with OEM revision 0x20001, so there is no hidden 0x370-byte table and the XSDT stays at 4 entries in both kernel passes. Section 3 ("generates only when `X_DSDT` is 0 ... If generation fails, a header-only DSDT") and the "Which model difference could matter" paragraph treat `NoACPIIO` as a feature 2 switch that only withholds a reveal. Fix: add this reader to section 3, and change the `NoACPIIO` check under "Checks in the guest" to: no `generating DSDT` or `generating SSDTs` text, no SSDTs, DSDT length 0x24 and revision 0x20001 in both passes, plus the "ACPI IO disabled" line. (Grade: established from the listing reference and the decompiled control flow; the SSDT guard was read in the decompiler only.)
2. **Inferred, not stated: whether `NoACPIIO` avoids the kernel failure.** The pass-1 count (6) and the stale index do not depend on the DSDT body, so a `NoACPIIO` boot still reaches `acpi_tb_load_namespace` with the wrong index. The page's "hardware stayed off the ACPI I/O path" explains a hardware boot only if the kernel carries on after `acpi_bus_init` fails, which was not read. Fix: say so in that paragraph.
3. `tbutils.c:323` and `:332` cite a function that starts at line 216; the FADT parse call is at `:333` (one line off). Fix the line numbers.

**Verdict.** Accept the kernel trace and the PROM claims graded established, with findings 1 and 2 recorded; no grade needed downgrading. Nothing here changes the stale-index conclusion.

**Not verified.** The emulated-boot facts (lengths 0x370, 0x95, 0x44 and 0x54, the two OEM revisions); the claims that `0xffb2d450` is also reached from the first `0x55` and from `0x5b`; the boundary-tag allocator and the "same address after free" inference; the AML and SSDT builders beyond their call sites; the `v5.15`/`v6.19` `sn_setup` call (only the ACPICA files were compared there); kernel line numbers other than those named above were spot-checked, not all re-read.
