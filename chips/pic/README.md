# PIC

Mode: **no-spec** (see [docs/specs.md](../../docs/specs.md): no specification is held). Every fact below comes from the
IRIX 6.5.30 IP35 objects `pic.o` and `pcibr.o`, the IP35 CPU PROM and the IP27/IP30 kernels as cited.
Hypothesis, not evidence: PIC descends from Bridge and XBridge, so a Bridge-like layout is a guess to test, never a
fill for a gap. Census: [census/](census/census.md) (`census.tsv`, `fields.tsv`, `context.tsv`,
`census-sites.tsv`, and `shim-run.txt` from `retools/tools/chips/run_routine.py`).

## What identifies a PIC (established, `pic_attach2` in `pic.o`, read in full)

- `pic_attach2` builds the per-chip record (2752 bytes) and stores chip type 2 in the halfword at record +114
  and a count of 1024 in the halfword at +112 (the number of internal address-translation entries it clears,
  below). It stores slot numbers 0 and 3 in the bytes at +56 and +57 (four slots numbered 0 to 3) before the
  hints may change them. `pic_attach2` returns -1 when `pcibr_hints_get` returns a hints record whose word at +12 is nonzero
  (this check runs before the 2752-byte record is allocated) and returns 0 on the normal path.
- It reads the 64-bit identification register at +0x0 (`pcireg_id_get`) and forms `revision | (part << 4)` from
  bits 31:28 and 27:12. It accepts parts 0xd102 and 0xd112, each at revisions 1, 2 and 3 (the six constants
  0xd1021, 0xd1022, 0xd1023, 0xd1121, 0xd1122, 0xd1123). Any other value is not rejected: it only changes the
  revision name in the attach debug message (revisions 1, 2, 3 print `A`, `B`, `C`, anything else prints `unknown`;
  the mapping of the string pointers to those names is inferred from the strings at the offsets the code adds) and
  attach carries on (audited: every branch rejoins at the same debug call). `pic_init` registers the driver for
  part 0xd102 with manufacturer 36 only.
- The shared accessor routines in `pcibr.o` (`pcireg_*`) choose among four chips by that halfword at +114
  (0 and 1 are Bridge-family, 2 PIC, 3 a fourth chip TIOCP) and, when given a raw pointer, by the part number in
  the identification word (0xc002, 0xd002 for the Bridge family; 0xd102, 0xd112 PIC; 0xe000, 0xe010 TIOCP).
  Which of those numbers is which chip is read from the compare-and-branch structure plus `pic.o` setting type 2
  with 0xd102 and 0xd112 (established for PIC); the Bridge-family and TIOCP names are inferred.
- The window pointer of the second head is the first plus 0x800000 (inferred: the pointer-returning routine
  `pcibr_bridge_ptr_get` adds 0x800000 for its second argument on the PIC path; two heads per PIC).

### Registers whose use is established by reading the code

- `+0x0` identification (read, 64-bit): see above. Fields used: 31:28 revision, 27:12 part number, 11:1 a
  manufacturer number that the `pcireg_*` accessors in `pcibr.o` compare with 36 when given a raw pointer to a PIC,
  TIOCP-part or 0xd002 chip, and with 54 for part 0xc002 only; bit 0 not used by the code. (established for the
  fields the code isolates; the compare lives in the accessors, not in `pcibr_bridge_ptr_get`)
- `+0x20` control: written through `pcireg_control_set`, `_bit_set`, `_bit_clr`; the attach sets bit 21
  (0x200000) always, and bit 29 (0x20000000) when the identification revision is not 1 (established: the revision
  test is `(1 << revision) & 2`); it also ORs 0xc0000000 (bits 31:30) and writes the caller's value into bits 55:48
  after clearing them. The two literal-pool masks are established (audit): the object's own options section gives
  gp 0x7800, so the lowest literal displacement is literal 0; they are 0xff00ffffffffffff (clears 55:48) and
  0x9fff00ffffffffff (clears bits 62:61 and 47:40, which the first draft of this page left out). The write goes
  through `pcireg_control_set`, which on the PIC path stores the doubleword and reads it straight back. Bits 5:4 are
  returned by `pcireg_speed_get` as the bus speed field (established: the code shifts right 4 and masks 3).
  Reset value: unknown.
- `+0x28` request timeout: `pcireg_req_timeout_set(0x750)` on revision 1 of the PIC only (established).
- `+0x38` interrupt destination: `pcireg_intr_dst_target_id_get/set` use bits 51:48 as the target widget
  (established: shift 48, mask 0xf in the getter); `intr_dst_addr_get/set` the address bits. Written by
  `pcibr_setwidint` (read in full in IP27; same accessor names in IP35) with target, address and the vector
  passed on to `+0x128`.
- `+0x100` interrupt status, `+0x108` enable, `+0x110` reset (clear), `+0x118` mode, `+0x120` device,
  `+0x128` host error field, `+0x130 + 8n` per-pin host address, `+0x170` and `+0x178` (view and multiple), `+0x180 + 8n`
  force-always, `+0x1c0 + 8n` force-with-pin: roles inferred from the accessor names only (`intr_status_get`,
  `intr_enable_*`, `intr_reset_*`, `intr_mode_*`, `intr_device_*`, `intr_host_err_*`, `intr_addr_*`,
  `intr_view_get`, `intr_multiple_get`, `force_always_set`, `force_intr_set`). Per-pin host address: bits 55:48
  are the vector (established: shift 48, mask 0xff in `pcireg_intr_addr_vect_get`) and the next field is an
  address (mask 10:0 after shift 1, inferred).
- `+0x200 + 8n` device, `+0x240 + 8n` write-buffer flush, `+0x280` and `+0x288` read response buffers (index 0 even,
  1 odd, established by running `pcireg_rrb_bit_set` in the harness: index 0 touches +0x280, index 1 +0x288),
  `+0x290` status, `+0x298` clear: inferred from names. Bits 19:16 and 3:0 of both response-buffer registers are
  set by the attach for revision 1 (established: constant 0xf000f). The buffer fields are established from the allocator
  `do_pcibr_rrb_alloc` (chips/bridge/README.md, "Response buffer fields"): eight 4-bit fields per register, the register chosen by
  slot parity (`slot & 1`: +0x280 even, +0x288 odd), and for the PIC each field is bit 3 valid, bits 2:1 virtual channel (0 to 3), bit 0 the device
  pair `slot >> 1` (slots 0 to 3 only). The revision-1 constant 0xf000f therefore marks fields 0 and 4 of each register valid, on virtual channel 3,
  for device pair 1 (slots 2 and 3); why the workaround reserves exactly those is not read.
- `+0x600` to `+0x630` (seven registers): PCI-X error address, attribute, data, split-address, split-attribute,
  request-error attribute and request-error address, in that order (inferred from the accessor names
  `pcix_bus_err_addr_get` ... `pcix_req_err_addr_get`; read-only).
- `+0x10000 + 8n` internal address translation entries: 1024 entries cleared one by one in the attach
  (`pcireg_int_ate_set(i, 0)`, established).
- `+0x18000`, `+0x18800`, `+0x19000`: three banks of 256 doublewords cleared with zero in the attach
  (established: `pic_attach2` at 0x954, 0x958 and 0x95c of `pic.o`; the loop, unrolled by two, stores a doubleword
  zero at base + 8i for i below 256, in each pass in the order +0x18000, +0x18800, +0x19000). They are the only accesses to the range in any
  of the three images the census covers (`pcibr.o`, `pic.o` and the IP35 PROM, the last with no unresolved window pointer), and no
  accessor names them, so nothing the shipped software does depends on their contents. What they hold is unknown; the end state is
  "no software dependency beyond the zeroing".
- `+0x20000` configuration windows and `+0x80000` external translation RAM accessors exist in the shared code
  (`pcireg_type0_cfg_addr`, `pcireg_type1_cfg_addr`, `pcireg_ext_ate_*`); whether they apply to PIC: unknown.

## Access sequences

**Attach and initialisation (established: `pic_attach2`, `pic.o`, read in full).** In order:

1. Read the identification register and check it against the accepted values.
2. Read the one-wire register address several times (`pcireg_nic_addr`) and the mode and speed (`pcireg_mode_get`,
   `pcireg_speed_get`): mode 1 selects the PCI-X path (later: a rbar calculation and a slot loop).
3. Zero three 256-doubleword banks at `+0x18000`, `+0x18800`, `+0x19000`.
4. `pcireg_intr_reset_set(0x7f)`: write 0x7f to `+0x110`. Meaning of the seven bits: inferred (clear pending
   interrupt/error groups); the value is established.
5. `pcireg_intr_device_set(0x6db6db)`: write 0x6db6db to `+0x120`: eight 3-bit fields each holding 3
   (established arithmetic; that a field names a device for a pin: inferred).
6. Initialise the direct map (`pcibr_directmap_init`, read in full, below).
7. Read control, mask, merge in the widget number and the constants above, write control. Then for each of the
   1024 translation entries write zero.
8. Allocate an interrupt for error reporting (`xtalk_intr_alloc`, `xtalk_intr_connect`), which reaches
   `pcibr_setwidint` and writes `+0x38` and `+0x128`; read the programmed destination back
   (`intr_dst_target_id_get`, `intr_dst_addr_get`) for a debug message.
9. Read enable, OR in `0x00003eff7ffffe00` (bits 30:9, 39:32 and 45:41), and write it back with
   `pcireg_intr_enable_set`. On revision 1 (chip type 2 only) the value is first ANDed with 0xffffff7ffffffdff,
   after the OR, so bits 39 and 9 end up clear, and `pcireg_req_timeout_set(0x750)` is called before the write.
   Constants: established (audit: literal 2 and 3 of `pic.o` against gp 0x7800).
10. `pcireg_intr_mode_set(0)`, read the target-flush register (`pcireg_tflush_get`, the read is the operation: inferred).
11. On revision 1 set the response buffer bits at +0x280 and +0x288 (above); then per slot: slot info, address
    space, device init, PCI-X rbar init, device attach; last, for a device whose two identity words equal 4116
    and 423, clear the low ten bits of the timeout register `+0xc0` (`pcireg_timeout_bit_clr(0x3ff)`;
    meaning unknown).

**Direct map set-up (established: `pcibr_directmap_init`, `IP35/.../IP35boot/pcibr.o` at 0x1080, 300 bytes, read in full, with the
four `pcireg_dirmap_*` setters at 0x11bac, 0x11d48, 0x11f38 and 0x120b8).** It takes the bridge record in `a0` (its Crosstalk widget handle at
+0, vertex at +4, window pointer at +8, widget number byte at +48) and returns nothing.

1. It reads the device-administration string `PCIBUS_DMATRANS_NODE` from the vertex (`device_admin_info_get`). When present, the string is a
   hardware-graph path: `hwgraph_path_to_vertex` and `nodevertex_to_cnodeid` turn it into a compact node number; a failure prints the text
   "Invalid hwgraph node path specified:" with the device-admin name and value (`cmn_err`, level 4) and uses node 0. With no string it uses node 0.
2. It asks `xtalk_dmatrans_addr` for a direct-map address on the widget, with device 0, the address `nasid << 33` (the NASID is the halfword for
   that node in `compact_to_nasid_node`), a length of 0x4000 and no flags. Call the result `x`.
3. It stores `x >> 31` through `pcireg_dirmap_diroff_set`, the widget number through `pcireg_dirmap_wid_set`, and copies the widget byte to +88
   of the record.
4. When `x` is exactly 0x20000000 it sets the add-512-MiB bit (`pcireg_dirmap_add512_set`) and keeps 0x20000000 at +80 of the record; for any other
   value it clears that bit (`pcireg_dirmap_add512_clr`) and keeps `x & 0x80000000` at +80.

The setters take either a chip window address (an address with bits 63, 60 and 57 set, the 0x92... window; they then read the identification word and
pick the path from its part number and manufacturer field) or a bridge record (they read the chip type from the halfword at +114 of the record).
The chip type selects the register access: 0 Bridge and 1 XBridge use the 32-bit word at `+0x84`, the low half of the doubleword at `+0x80`; 2 PIC
and 3 (the part with identification 0xe000 or 0xe010) use the doubleword at `+0x80`; type -1 or a null record calls `panic`, and any other value returns without a store. For the PIC (type 2) the fields are: widget number bits 23:20 (the setter clears `0xf00000` and stores
`(w & 0xf) << 20`), offset bits 16:0 (cleared with `0xfffffffffffe0000`, then ORed with the argument masked to 17 bits), add-512-MiB bit 17
(`0x20000`). The part of type 3 has one more field, bits 25:20 (mask `0x3f00000`, overlapping the widget field), which its offset setter writes first from bits 22:17 of the argument (the argument shifted left by 3, masked). So the PIC direct-map
register is `{widget:4 at bit 20, add512 at bit 17, offset:17 at bit 0}`, and the driver puts into it the widget number, the translated address in
units of 2 GiB, and the 512 MiB add-on only for the translation that equals 0x20000000. Established: the code. Inferred: that the register at `+0x80`
is the one meant (the setters touch `+0x80` in every chip-type path) and that "2 GiB units" is the offset granularity, from the shift of 31.

**Programmed-I/O flush workaround (established: `pic_pio_flush_new`, `issue_force_interrupt`, `pio_spin_wait`).**
For chip type 2 and certain devices, the driver takes a spin lock and picks a pin from a per-chip mask (the mask
is the byte-wide word at record +2744, initially 255, and the chosen pin is removed from it; which pins are allowed
depends on the device: the mask is ANDed with 0xd0 when a byte field of the device record equals 1 and its two
identity words are 4265 and 4106, otherwise with 0xcc, or 0x88 when `get_chimera_type` returns 3 and
`pciio_info_bus_get` returns 2; the meaning of those tests is not read). It writes the pin's per-pin host address vector 237 (0xed)
(`pcireg_intr_addr_vect_set`) and, as the address (`intr_addr_addr_set`), the address of the counter at +80 of the
caller's flush record. `issue_force_interrupt` then zeroes that counter and forces the interrupt by writing the value
1 to `+0x180 + 8*pin` (`pcireg_force_always_set`, pins 0 to 7; the chip-type 0 path of that accessor panics), and
`pio_spin_wait` spins until the counter equals 493. Nothing in these routines writes 493: the interrupt service
routine is not read. Purpose: ordering PIO writes by making an interrupt arrive: inferred from the structure.

**Error interrupt service (established for the paths named: `pcibr_error_intr_handler` at 0x9bb4 and `pcibr_error_dump` at 0x891c of IP35 `pcibr.o`; the rate limiter and the callee at 0x9a4c are not decoded).**
The handler takes the bridge record in `a0`, finds it in the global list of bridge records (no match: `panic`, "is not a pcibr_soft!"), then:

1. Asks `hubii_check_widget_disabled` about the record's node and widget byte. If it says disabled, the handler schedules itself again one tick later
   (`timeout`), adds one to the word at record +2104 and returns without touching the chip.
2. Reads the interrupt status (`+0x100`, `pcireg_intr_status_get`). Only bits 63:8 count as errors; bits 7:0 (the pin interrupts) are not examined, and a status
   with none of 63:8 set returns at once. Bit 31 is dropped from the set the rest of the routine works on.
3. If status bit 11, 15, 34 or 38 is set (mask `0x4400008800`) it calls the routine at 0x9a4c (a programmed-I/O error check; not read).
4. Keeps a 12-byte record per status bit 8 to 63 at record +2276 + 12 * (bit - 8): a count it increments each time the bit is seen, a tick stamp and a count at that
   stamp. From them it works out an error rate per tick and prints "Excessive error interrupts" or "Error rate" through `cmn_err`; for a bit that
   keeps firing it collects the bit and later clears it from the enable register (`+0x108`, `pcireg_intr_enable_bit_clr`) under the spin lock at record +140, printing
   "Disabling error interrupt type". The thresholds and which revisions skip this are not decoded. Inferred purpose: stop an error storm.
5. Status bit 24 (request with an invalid address for the bridge widget) is cleared from the working set only when the bus-error register (`+0x18`)
   has bits 63:22 equal to 3 and the command-word error register (`+0x40`) under mask `0xf07f00` equals `0x402000`; the meaning of those values is not read (inferred:
   one access the handler is meant to ignore).
6. Dump: a global mask, `bridge_errors_to_dump`, starts as `0x22573fc0e800` (bits 11, 13, 14, 15, 22 to 29, 32, 33, 34, 36, 38, 41, 45). The handler first ORs `0x4400008800` into it
   when the global `pcibr_pioerr_dump` is nonzero and removes those four bits when it is zero. If any working-set bit is in the mask it prints "BRIDGE ERR_STATUS" and calls `pcibr_error_dump`.
7. Fatal set: for a PIC (record chip type 2), working-set bits 21:20 (mask `0x300000`) are fatal on revisions 1 and 2 only (the test is `(1 << revision) & 6`). For every chip type, a bit in
   `0x22133fc06000` (bits 13, 14, 22 to 29, 32, 33, 36, 41, 45) is fatal. Fatal means: print "BRIDGE ERR_STATUS", dump, `machine_error_dump`, then `panic` ("PCI Bridge Error interrupt killed the system").
   The bits with fatal status are the ones the shipped text names as parity errors, request and response packet errors and framing errors, the unexpected response, PCI-X data and address parity, PCI-X SERR, internal RAM parity and the split completion message parity error.
8. Clear: for chip types 2 and 3 it writes the status word it read, with bit 6 also set (`status | 0x40`), to the reset register `+0x110`
   (`pcireg_intr_reset_set`); types 0 and 1 write a group mask from a small routine at 0x99c8 instead. So on a PIC the handler clears by writing back the status it read.
   For a PIC revision 1 with status bit 40 (arbitration error) set it then sets bits 23:20 of the arbitration register (`+0xa0`, `pcireg_arbitration_bit_set(0xf00000)`). Last it stores zero to the word at record +2120.

## Reset expectations

Unknown for every register: no routine reads a register before writing it in the attach sequence, apart from
read-modify-write of control and enable (so it expects whatever the hardware presents, and clears or sets
listed bits). The attach itself writes: `+0x110` 0x7f, `+0x120` 0x6db6db, `+0x118` 0, the banks and entries zero.

The IP35 PROM routine at 0xc00000001fc41f38 (read in full, 0xc00000001fc41f38 to 0xc00000001fc41fb4) clears the interrupt registers before the
kernel runs, and it has two paths on the identification word. For parts 0xd102 and 0xd112 with manufacturer 36 it
stores 64-bit zero to `+0x108` and 64-bit all-ones to `+0x110` (established). Only for any other part does it use
the 32-bit stores at `+0x10c`, `+0x114` (0xffff) and `+0x12c` (true of that routine only: the bridge diagnostic below does 32-bit accesses on the PIC path). So the census rows of the PROM `sw` stores at those
three offsets belong to a Bridge-family path, not to the PIC: the scanner assigned them to the PIC because it kept the part-number
variant after the manufacturer check failed, and it missed the PIC stores because the PROM image was split after each
return. Both are fixed: a failed manufacturer check withdraws the variant and routines are cut by control flow, so the
census now has the 64-bit PIC stores under `pic` and the 32-bit stores under `probe?` (chip not named). The register table's `4,8` widths for
`+0x108`, `+0x110` and `+0x128` and the `+0x110` constant 0xffff come from those rows; the PIC value the PROM
writes to `+0x110` is all-ones, the kernel's is 0x7f.

## PROM bridge diagnostic (0xc00000001fc4ca98)

The routine that prints the "Running %s diag (Bridge base = 0x%08x)" start message and names itself
`bridge_sanity` takes the window base in `a1` and a mode word in `a0`. The census scanner now seeds it
(`prom_c00000001fc4ca98` in `tools/configs/pic.json`); before, the routine was reached through a pointer the scan
did not follow, so none of these sites were in the census. Read in full, 0xc00000001fc4ca98 to 0xc00000001fc4cfcc:

- It reads the identification word (+0x4) through a helper that accepts parts 0xc002, 0xd002, 0xd102 and 0xd112
  and prints a warning for any other. Only 0xc002 gets an extra check (control word +0xc, bit 5). The path
  below does not branch on 0xd102 or 0xd112, so a PIC that reaches it runs the same sequence as a Bridge
  (established for the code). That a PIC reaches this path (mode bit 0x40 set, low mode nibble not 2) is
  inferred from a public capture that runs the diagnostic on PIC widgets; the mode word was not traced.
- Every access is a 32-bit `lw`/`sw` at an address of the form 8n+4, the low word of the big-endian doubleword at
  8n (established: the instructions). That this is the low half of a 64-bit PIC register is inferred from the
  byte order.
- Sequence for the path with mode bit 0x40 set (established: the instructions and their order): read +0x104
  (prints a warning if nonzero); write 0xa5a5a5a5 to +0x3c and 0x5a5a5a5a to +0x34 and read each back (+0x3c
  compared whole, +0x34 under mask 0xfffff against 0xa5a5a); write 0x01000000 to +0x10c. Then for test number
  n = 0 and 7 to 19: write n to +0x12c and read it back; if equal, write 0xdeadbeef to +0x7c; poll +0x104 up to
  1000 times (a delay call between polls) until the whole word equals 0x01000000, that is bit 24 set and nothing
  else; poll the doubleword at +0x98 of a Bedrock register block for bit n; write 8 to +0x114; write n to
  the doubleword at +0x90 of that block and read +0x98 again. At the end write zero to +0x10c, +0x34 and +0x3c.
  Which Bedrock register block the +0x90 and +0x98 accesses reach, and what they mean, is inferred from the
  constants that form the address and the "did not reach" message strings the routine prints, not read from a
  source.
- The write to +0x7c is on the low word of slot +0x78, which this page lists as read-only (its only accessor is
  a getter, `linkside_err_addr_get`: inferred). The routine does not check that the write was ignored. What a
  PIC does with it is unknown.
- Register roles are unknown from this routine. The 0xa5a5/0x5a5a pattern, the bit 24 test and the +0x10c and
  +0x114 values are what the code does, not what the registers mean.
- With mode bit 0x40 clear, another path reads +0x2c, +0x24, +0x204, +0x20c, +0x214 and +0x21c (all `lw`) and
  writes +0x24 (`sw`). These are census sites; the path was not read in full (unknown meaning).

## Against the emulator's datasheet (reported after the reading above)

The datasheet lists ranges for the PIC map, not slots. IRIX touches six slots the ranges do not cover as
registers (+0x90, +0xa0, +0xb0, +0xc0, +0xc8, +0xd8) and the external translation RAM window +0x80000; the
datasheet does list +0x0 to +0x78, +0x80, +0x100 to +0x1f8, +0x200 to +0x298, +0x600 to +0x638 and the entry
arrays, and nothing here contradicts those ranges. The +0x18000 banks and the 0x20000 configuration windows agree
with its address list.
