# Visual Workstation 320 versus 540: memory, processors, PCI slots and the board-type byte

What differs between the two products, from the owner's guides (Silicon Graphics 320, 007-3701-001; Silicon Graphics 540,
007-3882-001) and the NT HAL's board-generation tables ([nt-hal.md](../../software/visws/nt-hal.md)). Grades as on the
[platform page](README.md): a statement of a published guide is established as that guide's text; a mapping built from
the guides and the HAL tables together is inferred.

## Memory

| | 320 | 540 |
|---|---|---|
| DIMM slot groups | two, A and B, six DIMMs each (guide p. 24) | four, A to D, six DIMMs each (guide p. 28) |
| Capacity per group | 128, 256 or 512 MB (single-sided, double-sided, double-sided stacked) | the same three sizes |
| Maximum | 1 GB | 2 GB |
| Rules | group A first, then B | group A always populated, groups filled in order, groups may differ in capacity; minimum 128 MB |

Established as guide text. The HAL never decodes banks: it reads the loader's memory descriptors and touches only the memory
block's ECC and error registers ([nt-hal.md](../../software/visws/nt-hal.md#memory-banks-and-the-graphics-split)). The firmware's
sixteen bank registers at `0xc6000048` upward therefore describe up to the 540's four groups; which registers belong to which group
is not shown by any source held.

## Processors

The 320 takes one or two processors (a primary and a secondary, with a processor-count jumper, guide chapter 6). The 540 has
slots for up to four (the interior figure labels the primary, "0", and processors 1 to 3); each unused slot holds a terminator
card, voltage regulators go with processors, and speed jumpers change with each processor (guide chapter 6). Established as guide text.
The HAL takes the processor count and the entries from the firmware's table at `0x1e00` with no upper bound of its own
(`HalpGetProcessorInfo`, established), starts each enabled non-bootstrap entry by INIT and startup IPIs, and uses the same
`halborg.dll` for both machines; the 320 and 540 differ for it only through the SYS TYPE byte (0 and 1). Linux accepts at most four.
The local APIC id of the bootstrap processor is whatever the firmware's table carries. The HAL writes destination 0 into every device entry, so a processor with local APIC id 0 must exist and be started; that does not show which processor is the bootstrap one (inferred; unknown).

## Board generations the HAL selects

SYS TYPE and BOARD REV come from the firmware's ARC tree ([boot-path.md](../../software/visws/boot-path.md)).

| Generation | Boards | Vector table, route tables | PCI pin tables |
|---|---|---|---|
| 1 | 320 below revision 6; 540 revision 0 | the oldest (entries 1, 3, 4, 6 differ) | five full rows on bridge A, four rows plus the PIIX4 on B |
| 2 | 320 revisions 6 to 11 | the middle (entries 4, 5, 13, 14, 15 differ) | A devices 0 and 1 and the Ethernet; B device 0 |
| 3 | 320 revision 12 and later; every 540 except revision 0 | the newest | A devices 0 and 1 full, 2 and 3 pin A only; B devices 0 to 3 full |

Established, decoded from the image's tables. Reboot by the Cobalt CPU register `+0x18` rather than port `0xcf9` applies to
the 320 below revision 12 and the 540 revision 0.

## PCI slots and the Lithium bridges (inferred)

The guides give: 320, three option slots on two buses, one half-length 32-bit slot on "bus:0" and two full-length 64-bit slots
on "bus:1", 3.3 V cards only; 540, two buses, one with four slots (slots 1 to 4, 5 V and universal) and one with two (slots 5
and 6, 3.3 V and universal), all 33 MHz and 64 bit. The NT HAL numbers Lithium bridge B (window `0xfd000000`, the PIIX4's
bus) as bus 0 and bridge A (`0xfc000000`) as bus 1 (established), which is the guide's numbering for the 320. Reading the pin
tables with it:

| Bridge, device | Wiring in the tables | 320 | 540 |
|---|---|---|---|
| B (bus 0), device 0 | entry 8, pins B to D shared | the one 32-bit slot | a slot of the four-slot bus |
| B, devices 1 to 3 | full rows only in generation 3 (and 1) | no slot (the 320 has one on this bus) | slots of the four-slot bus |
| B, device 4 | PIIX4: only pin D wired, entry 7 (USB) | PIIX4 | PIIX4 |
| A (bus 1), devices 0 and 1 | entries 0 and 1 with shared pins | the two 64-bit slots | the two-slot bus (slots 5 and 6, 3.3 V) |
| A, device 2 | pin A only, entry 2 (generation 3) | not a slot | not a slot; some on-board device (not identified) |
| A, device 3 | pin A only, entry 3 | on-board Ethernet (Linux's header comment) | on-board Ethernet |

The count of fully wired rows (four on B, two on A) and the voltage split agree with the 540's four-slot bus being bridge B
and its two-slot 3.3 V bus being bridge A. Which physical slot number (1 to 4, 5 and 6) is which device number on its bus is
unknown: the guides number slots only within a group and the HAL numbers devices; the natural order (slot 1 is device 0) is a guess.
A card behind a PCI-to-PCI bridge in a slot of B would push bridge A's bus number up ([nt-hal.md](../../software/visws/nt-hal.md#pci-numbering-and-resource-assignment)).

## The byte at port `0xfb2`

Pages cited as "PIIX4 p. N" are from Intel's 82371AB PIIX4 datasheet, order 290562-001, April 1997; "spec update p. N" is
its specification update, 297738-017, January 2002. Both are printed-page numbers.

The PIIX4 power-management block is at `0xf80`. The firmware sets the base through function 3 offset `0x40` (PMBA), and the
HAL reads status at `+0` (established). Bits 15:6 of PMBA hold the base and bit 0 is hardwired to 1, so the register reads
back `0x0f81` (PIIX4 p. 120). The general-purpose input register (GPIREG) is at `+0x30` and the output register (GPOREG) at
`+0x34` (PIIX4 pp. 147, 148).

Port `0xfb2` is GPIREG byte 2. Its bits 5:2 are GPI21 to GPI18 and its bits 1:0 are GPI17 and GPI16. All of them are
non-multiplexed inputs (PIIX4 Table 1, pp. 35 and 36), and bits 7:6 are reserved (p. 147). So the four board-type inputs
exist as always-available pins, and the firmware's expression `(inb(0xfb2) >> 2) & 0xf` reads exactly those four (established,
[boot-path.md](../../software/visws/boot-path.md)), giving 0 on the 320 and 1 on the 540. The datasheet allows strapping but
does not show that SGI strapped these pins. No held source gives the wiring, so the board-type reading stays inferred.

Port `0xfb0` is GPIREG byte 0. Its bit 2 is GPI2, which is also REQA# and GNTA# and GPO9 (PIIX4 Table 1, p. 36). The select is
GENCFG bit 8 (function 0 offset `0xb0`, p. 66), which resets to 0, so the pin reads as GPI2 (established). The 1.1005
PIIX4 write sequence sets `0xb0` to `0x4d` and `0xb3` to `0x60` and does not touch bit 8, which is in byte `0xb1`
(established for that sequence; other GENCFG writes were not traced).

Port `0xfb5` is GPOREG byte 1. Its bit 0 is GPO8, which is non-multiplexed and driven low when core power is removed
(PIIX4 Table 2, p. 37). So the HAL's write to bit 0 drives a pin the chip always provides. The other bits are GPO9 to GPO15.
Bits 1 to 3 are GPO9 to GPO11, shared with the REQ and GNT pins and selected by GENCFG bits 8 to 10. Bits 4 to 6 are GPO12 to
GPO14 (APICACK#, APICCS#, IRQ0), selected by XBCS bit 8. Bit 7 is GPO15, shared with SUSB# (GENCFG bit 17). The GPOREG reset
value is `0x7FFFBFFF` (p. 148; spec update p. 23, erratum 3, gives the same value), so `0xfb5` resets to `0xbf`. Port `0xfb7`
bit 4 is GPO28, a non-multiplexed output (Table 2, p. 38). The datasheet names these pins but not what SGI connected to them.

The datasheet's Tables 1 and 2 label these controls "PCI Function 1", but GENCFG and XBCS are function 0 registers
(Table 4, p. 43; section 4.1.19). The offsets here are function 0's.

The HAL does not use `0xfb2`. It takes the board type from the firmware's ARC tree.
