# PIC

Mode: **no-spec** (see [references/documents/specs.md](../../references/documents/specs.md): no specification is held). Every fact below comes from the
IRIX 6.5.30 IP35 objects `pic.o` and `pcibr.o`, the IP35 CPU PROM and the IP27/IP30 kernels as cited.
Hypothesis, not evidence: PIC descends from Bridge and XBridge, so a Bridge-like layout is a guess to test, never a
fill for a gap. Census: [census/](census/census.md) (`census.tsv`, `fields.tsv`, `context.tsv`,
`census-sites.tsv`, and `shim-run.txt` from `retools/tools/chips/run_routine.py`).

## What identifies a PIC (established, `pic_attach2` in `pic.o`, read in full)

- `pic_attach2` builds the per-chip record (2752 bytes) and stores chip type 2 in the halfword at record +114
  and a count of 1024 in the halfword at +112 (the number of internal address-translation entries it clears,
  below). It stores slot numbers 0 and 3 in the bytes at +56 and +57 (four slots numbered 0 to 3) before the
  hints may change them. `pic_attach2` returns -1 when `pcibr_hints_get` returns a hints record whose word at +12 is nonzero
  (this check runs before the 2752-byte record is allocated) and returns 0 on the normal path.
- It reads the 64-bit identification register at +0x0 (`pcireg_id_get`) and forms `revision | (part << 4)` from
  bits 31:28 and 27:12. It accepts parts 0xd102 and 0xd112, each at revisions 1, 2 and 3 (the six constants
  0xd1021, 0xd1022, 0xd1023, 0xd1121, 0xd1122, 0xd1123). Any other value is not rejected: it only changes the
  revision name in the attach debug message (revisions 1, 2, 3 print `A`, `B`, `C`, anything else prints `unknown`;
  the mapping of the string pointers to those names is inferred from the strings at the offsets the code adds) and
  attach carries on (audited: every branch rejoins at the same debug call). `pic_init` registers the driver for
  part 0xd102 with manufacturer 36 only.
- The shared accessor routines in `pcibr.o` (`pcireg_*`) choose among four chips by that halfword at +114
  (0 and 1 are Bridge-family, 2 PIC, 3 a fourth chip TIOCP) and, when given a raw pointer, by the part number in
  the identification word (0xc002, 0xd002 for the Bridge family; 0xd102, 0xd112 PIC; 0xe000, 0xe010 TIOCP).
  Which of those numbers is which chip is read from the compare-and-branch structure plus `pic.o` setting type 2
  with 0xd102 and 0xd112 (established for PIC); the Bridge-family and TIOCP names are inferred.
- The window pointer of the second head is the first plus 0x800000 (inferred: the pointer-returning routine
  `pcibr_bridge_ptr_get` adds 0x800000 for its second argument on the PIC path; two heads per PIC).

On an Itanium host the same 64-bit registers are read with `ld4` at `+0` for the low word, not `+4`; see [How the Itanium sees widget registers](../shub_ii/README.md#how-the-itanium-sees-widget-registers).

### Registers whose use is established by reading the code

- `+0x0` identification (read, 64-bit): see above. Fields used: 31:28 revision, 27:12 part number, 11:1 a
  manufacturer number that the `pcireg_*` accessors in `pcibr.o` compare with 36 when given a raw pointer to a PIC,
  TIOCP-part or 0xd002 chip, and with 54 for part 0xc002 only; bit 0 not used by the code. (established for the
  fields the code isolates; the compare lives in the accessors, not in `pcibr_bridge_ptr_get`)
- `+0x20` control: written through `pcireg_control_set`, `_bit_set`, `_bit_clr`; the attach sets bit 21
  (0x200000) always, and bit 29 (0x20000000) when the identification revision is not 1 (established: the revision
  test is `(1 << revision) & 2`); it also ORs 0xc0000000 (bits 31:30) and writes the caller's value into bits 55:48
  after clearing them. The two literal-pool masks are established (audit): the object's own options section gives
  gp 0x7800, so the lowest literal displacement is literal 0; they are 0xff00ffffffffffff (clears 55:48) and
  0x9fff00ffffffffff (clears bits 62:61 and 47:40, which the first draft of this page left out). The write goes
  through `pcireg_control_set`, which on the PIC path stores the doubleword and reads it straight back. Bits 5:4 are
  returned by `pcireg_speed_get` as the bus speed field (established: the code shifts right 4 and masks 3).
  Reset value: unknown.
- `+0x28` request timeout: `pcireg_req_timeout_set(0x750)` on revision 1 of the PIC only (established).
- `+0x38` interrupt destination: `pcireg_intr_dst_target_id_get/set` use bits 51:48 as the target widget
  (established: shift 48, mask 0xf in the getter); `intr_dst_addr_get/set` the address bits. Written by
  `pcibr_setwidint` (read in full in IP27; same accessor names in IP35) with target, address and the vector
  passed on to `+0x128`.
- `+0x100` interrupt status, `+0x108` enable, `+0x110` reset (clear), `+0x118` mode, `+0x120` device,
  `+0x128` host error field, `+0x130 + 8n` per-pin host address, `+0x170` and `+0x178` (view and multiple), `+0x180 + 8n`
  force-always, `+0x1c0 + 8n` force-with-pin: roles inferred from the accessor names only (`intr_status_get`,
  `intr_enable_*`, `intr_reset_*`, `intr_mode_*`, `intr_device_*`, `intr_host_err_*`, `intr_addr_*`,
  `intr_view_get`, `intr_multiple_get`, `force_always_set`, `force_intr_set`). Per-pin host address: bits 55:48
  are the vector (established: shift 48, mask 0xff in `pcireg_intr_addr_vect_get`) and the next field is an
  address (mask 10:0 after shift 1, inferred).
- `+0x200 + 8n` device, `+0x240 + 8n` write-buffer flush, `+0x280` and `+0x288` read response buffers (index 0 even,
  1 odd, established by running `pcireg_rrb_bit_set` in the harness: index 0 touches +0x280, index 1 +0x288),
  `+0x290` status, `+0x298` clear: inferred from names. Bits 19:16 and 3:0 of both response-buffer registers are
  set by the attach for revision 1 (established: constant 0xf000f). The buffer fields are established from the allocator
  `do_pcibr_rrb_alloc` (devices/bridge/README.md, "Response buffer fields"): eight 4-bit fields per register, the register chosen by
  slot parity (`slot & 1`: +0x280 even, +0x288 odd), and for the PIC each field is bit 3 valid, bits 2:1 virtual channel (0 to 3), bit 0 the device
  pair `slot >> 1` (slots 0 to 3 only). The revision-1 constant 0xf000f therefore marks fields 0 and 4 of each register valid, on virtual channel 3,
  for device pair 1 (slots 2 and 3); why the workaround reserves exactly those is not read.
- `+0x600` to `+0x630` (seven registers): PCI-X error address, attribute, data, split-address, split-attribute,
  request-error attribute and request-error address, in that order (inferred from the accessor names
  `pcix_bus_err_addr_get` ... `pcix_req_err_addr_get`; read-only).
- `+0x10000 + 8n` internal address translation entries: 1024 entries cleared one by one in the attach
  (`pcireg_int_ate_set(i, 0)`, established).
- `+0x18000`, `+0x18800`, `+0x19000`: three banks of 256 doublewords cleared with zero in the attach
  (established: `pic_attach2` at 0x954, 0x958 and 0x95c of `pic.o`; the loop, unrolled by two, stores a doubleword
  zero at base + 8i for i below 256, in each pass in the order +0x18000, +0x18800, +0x19000). They are the only accesses to the range in any
  of the three images the census covers (`pcibr.o`, `pic.o` and the IP35 PROM, the last with no unresolved window pointer), and no
  accessor names them, so nothing the shipped software does depends on their contents. What they hold is unknown; the end state is
  "no software dependency beyond the zeroing".
- `+0x20000` configuration windows and `+0x80000` external translation RAM accessors exist in the shared code
  (`pcireg_type0_cfg_addr`, `pcireg_type1_cfg_addr`, `pcireg_ext_ate_*`); whether they apply to PIC: unknown.

## Access sequences

**Attach and initialisation (established: `pic_attach2`, `pic.o`, read in full).** In order:

1. Read the identification register and check it against the accepted values.
2. Read the one-wire register address several times (`pcireg_nic_addr`) and the mode and speed (`pcireg_mode_get`,
   `pcireg_speed_get`): mode 1 selects the PCI-X path (later: a rbar calculation and a slot loop).
3. Zero three 256-doubleword banks at `+0x18000`, `+0x18800`, `+0x19000`.
4. `pcireg_intr_reset_set(0x7f)`: write 0x7f to `+0x110`. Meaning of the seven bits: inferred (clear pending
   interrupt/error groups); the value is established.
5. `pcireg_intr_device_set(0x6db6db)`: write 0x6db6db to `+0x120`: eight 3-bit fields each holding 3
   (established arithmetic; that a field names a device for a pin: inferred).
6. Initialise the direct map (`pcibr_directmap_init`, read in full, below).
7. Read control, mask, merge in the widget number and the constants above, write control. Then for each of the
   1024 translation entries write zero.
8. Allocate an interrupt for error reporting (`xtalk_intr_alloc`, `xtalk_intr_connect`), which reaches
   `pcibr_setwidint` and writes `+0x38` and `+0x128`; read the programmed destination back
   (`intr_dst_target_id_get`, `intr_dst_addr_get`) for a debug message.
9. Read enable, OR in `0x00003eff7ffffe00` (bits 30:9, 39:32 and 45:41), and write it back with
   `pcireg_intr_enable_set`. On revision 1 (chip type 2 only) the value is first ANDed with 0xffffff7ffffffdff,
   after the OR, so bits 39 and 9 end up clear, and `pcireg_req_timeout_set(0x750)` is called before the write.
   Constants: established (audit: literal 2 and 3 of `pic.o` against gp 0x7800).
10. `pcireg_intr_mode_set(0)`, read the target-flush register (`pcireg_tflush_get`, the read is the operation: inferred).
11. On revision 1 set the response buffer bits at +0x280 and +0x288 (above); then per slot: slot info, address
    space, device init, PCI-X rbar init, device attach; last, for a device whose two identity words equal 4116
    and 423, clear the low ten bits of the timeout register `+0xc0` (`pcireg_timeout_bit_clr(0x3ff)`;
    meaning unknown).

**Direct map set-up (established: `pcibr_directmap_init`, `IP35/.../IP35boot/pcibr.o` at 0x1080, 300 bytes, read in full, with the
four `pcireg_dirmap_*` setters at 0x11bac, 0x11d48, 0x11f38 and 0x120b8).** It takes the bridge record in `a0` (its Crosstalk widget handle at
+0, vertex at +4, window pointer at +8, widget number byte at +48) and returns nothing.

1. It reads the device-administration string `PCIBUS_DMATRANS_NODE` from the vertex (`device_admin_info_get`). When present, the string is a
   hardware-graph path: `hwgraph_path_to_vertex` and `nodevertex_to_cnodeid` turn it into a compact node number; a failure prints the text
   "Invalid hwgraph node path specified:" with the device-admin name and value (`cmn_err`, level 4) and uses node 0. With no string it uses node 0.
2. It asks `xtalk_dmatrans_addr` for a direct-map address on the widget, with device 0, the address `nasid << 33` (the NASID is the halfword for
   that node in `compact_to_nasid_node`), a length of 0x4000 and no flags. Call the result `x`.
3. It stores `x >> 31` through `pcireg_dirmap_diroff_set`, the widget number through `pcireg_dirmap_wid_set`, and copies the widget byte to +88
   of the record.
4. When `x` is exactly 0x20000000 it sets the add-512-MiB bit (`pcireg_dirmap_add512_set`) and keeps 0x20000000 at +80 of the record; for any other
   value it clears that bit (`pcireg_dirmap_add512_clr`) and keeps `x & 0x80000000` at +80.

The setters take either a chip window address (an address with bits 63, 60 and 57 set, the 0x92... window; they then read the identification word and
pick the path from its part number and manufacturer field) or a bridge record (they read the chip type from the halfword at +114 of the record).
The chip type selects the register access: 0 Bridge and 1 XBridge use the 32-bit word at `+0x84`, the low half of the doubleword at `+0x80`; 2 PIC
and 3 (the part with identification 0xe000 or 0xe010) use the doubleword at `+0x80`; type -1 or a null record calls `panic`, and any other value returns without a store. For the PIC (type 2) the fields are: widget number bits 23:20 (the setter clears `0xf00000` and stores
`(w & 0xf) << 20`), offset bits 16:0 (cleared with `0xfffffffffffe0000`, then ORed with the argument masked to 17 bits), add-512-MiB bit 17
(`0x20000`). The part of type 3 has one more field, bits 25:20 (mask `0x3f00000`, overlapping the widget field), which its offset setter writes first from bits 22:17 of the argument (the argument shifted left by 3, masked). So the PIC direct-map
register is `{widget:4 at bit 20, add512 at bit 17, offset:17 at bit 0}`, and the driver puts into it the widget number, the translated address in
units of 2 GiB, and the 512 MiB add-on only for the translation that equals 0x20000000. Established: the code. Inferred: that the register at `+0x80`
is the one meant (the setters touch `+0x80` in every chip-type path) and that "2 GiB units" is the offset granularity, from the shift of 31.

**Programmed-I/O flush workaround (established: `pic_pio_flush_new`, `issue_force_interrupt`, `pio_spin_wait`).**
For chip type 2 and certain devices, the driver takes a spin lock and picks a pin from a per-chip mask (the mask
is the byte-wide word at record +2744, initially 255, and the chosen pin is removed from it; which pins are allowed
depends on the device: the mask is ANDed with 0xd0 when a byte field of the device record equals 1 and its two
identity words are 4265 and 4106, otherwise with 0xcc, or 0x88 when `get_chimera_type` returns 3 and
`pciio_info_bus_get` returns 2; the meaning of those tests is not read). It writes the pin's per-pin host address vector 237 (0xed)
(`pcireg_intr_addr_vect_set`) and, as the address (`intr_addr_addr_set`), the address of the counter at +80 of the
caller's flush record. `issue_force_interrupt` then zeroes that counter and forces the interrupt by writing the value
1 to `+0x180 + 8*pin` (`pcireg_force_always_set`, pins 0 to 7; the chip-type 0 path of that accessor panics), and
`pio_spin_wait` spins until the counter equals 493. Nothing in these routines writes 493: the interrupt service
routine is not read. Purpose: ordering PIO writes by making an interrupt arrive: inferred from the structure.

**Error interrupt service (established: `pcibr_error_intr_handler` at 0x9bb4, the counting routine at 0x9a4c and `pcibr_error_dump` at 0x891c of IP35 `pcibr.o`, all read in full).**
The handler takes the bridge record in `a0`, finds it in the global list of bridge records (no match: `panic`, "is not a pcibr_soft!"), then:

1. Asks `hubii_check_widget_disabled` about the record's node and widget byte. If it says disabled, the handler schedules itself again one tick later
   (`timeout`), adds one to the word at record +2104 and returns without touching the chip.
2. Reads the interrupt status (`+0x100`, `pcireg_intr_status_get`). Only bits 63:8 count as errors; bits 7:0 (the pin interrupts) are not examined, and a status
   with none of 63:8 set returns at once. Bit 31 is dropped from the set the rest of the routine works on.
3. If status bit 11, 15, 34 or 38 is set (mask `0x4400008800`) it calls the routine at 0x9a4c, read in full: it reads the status and
   the PCI bus error address (`pcireg_pci_bus_addr_get`), walks every device of every slot of the bridge, and for each programmed-I/O
   mapping of a device whose bus window contains the error address (window base from the slot's base-register table at +0x50 plus the
   mapping's own offset and size, at mapping +0x10 and +0x18) atomically adds one (`ll`/`sc`) to a word at mapping +0x48. It prints
   nothing and changes no chip state: it only counts, per mapping, the programmed-I/O errors that landed in it. Established.
4. Keeps a 12-byte record per status bit 8 to 63 at record +2276 + 12 * (bit - 8): an event count, a tick stamp and the count at
   that stamp. For each bit set in the working set it adds one to the count, then (ticks are the kernel `lbolt` counter):
   `elapsed = lbolt - stamp`, `delta = count - count at stamp`, `rate = delta / elapsed` (integer, skipped when `elapsed` is 0).
   Established from the full read of `pcibr_error_intr_handler` (0x9bb4 to 0xa168):
   - A bit is "excessive" when `elapsed` is above 100 ticks and `rate` is above 100 per tick. The handler then prints "Error rate
     N/tick" through `cmn_err` (level 5) with the bit's name, and restarts the window (stamp = now, count at stamp = count). It
     does not disable the bit on this path.
   - Bit 18 on bus 0 (the record word at +72 equal to 0) has an extra rule: when `delta` is at least 100 and `rate` is nonzero and above
     a global high-water mark, the handler prints "Excessive error interrupts : N/tick" (level 4), stores this rate as the new mark, and restarts the
     window; when `elapsed` is 0 it restarts the window if `delta` is 10000 or more. On bus 1 and for every other bit only the plain
     test above applies.

     set, and only for a bit whose count has reached 10001. The handler prints "Disabling error interrupt type" (level 5) and collects the
     bit; after the scan it clears the collected bits from the enable register (`+0x108`, `pcireg_intr_enable_bit_clr`) under the spin lock
     at record +140. Every other chip type and revision never disables a bit from this handler.

   and `pic_attach2` stores it at 0x858. The global mark is a zero-initialised `.sbss` word, so it starts at 0 and only ever rises; the tick rate of `lbolt` is the kernel's and was not read. The record word at +2120 is a guard: `test_and_set_long` is an

   returns early only when another caller has already stored the same status mask there, and the handler stores 0 at the end.

7. Fatal set: for a PIC (record chip type 2), working-set bits 21:20 (mask `0x300000`) are fatal on revisions 1 and 2 only (the test is `(1 << revision) & 6`). For every chip type, a bit in

   The bits with fatal status are the ones the shipped text names as parity errors, request and response packet errors and framing errors, the unexpected response, PCI-X data and address parity, PCI-X SERR, internal RAM parity and the split completion message parity error.

   For a PIC revision 1 with status bit 40 (arbitration error) set it then sets bits 23:20 of the arbitration register (`+0xa0`, `pcireg_arbitration_bit_set(0xf00000)`). Last it stores zero to the word at record +2120.

## Interrupt packets: edge-only delivery, recovery by software

Labels follow the rules at the top of the repository. A public driver or header statement is **established as that
author's statement**; it is not a measurement of silicon. Sources: the SGI SN2 Linux tree (branch `linux-2.4`, commit
`8ef7d46c94d54ae907217463caf30ad4de88211b`), file by file below, and the shipped IRIX 6.5.30 IP35 `pcibr.o`
(SHA-256 `5a79bfd6f2bf07f4c614b5794a9a3e6f5f973f8e60110e0ac2f6b293eb252a29`, offsets into `.text` after applying
relocations; `pcibr_force_interrupt` and `pcibr_intr_func` read in full).

- **Where the packet goes on a SHub 1 (established for the address, inferred for the data).** The 2.4 SN2 kernel built each
  pin's destination as the I/O interface interrupt register of the target node, `SH_II_INT0` (`0x1_1000_0000`, processor
  slice 0) or `SH_II_INT1` (`0x1_1000_0100`, other slices), with the NASID at bit 36 and bit 47 set, and stored it with the
  vector in bits 55:48 into the pin's per-pin address register (`shub_intr.c` `do_hub_intr_alloc`, `pcibr_intr.c`
  `pcibr_setpciint`; Linux/MIPS `linux-2.4` branch at `8ef7d46c94d5`). The data written is inferred to be `0x100 | vector`, which is
  the `SEND` bit and `IDX` field of `SH_II_INT0`. Later kernels get the address from firmware instead. Detail and grades:
  [SHub 1 interrupts](../shub/interrupts.md#where-a-pic-interrupt-lands-on-shub-1).
- **Status is the pin level, not the packet** (established: the header's own description,
  `include/asm-ia64/sn/pci/pic.h` lines 1298 to 1306). Status bits 7:0 hold the current state of the eight INT_N
  pins, active high for a pin driven low, and the register is read-only. Whether status changes before the packet
  leaves the chip: **inferred**, no source gives the internal order. Nothing read suggests a packet can precede its
  own status bit.
- **A set packet goes out on a transition, once** (established as the driver authors' statement,
  `arch/ia64/sn/io/sn2/pcibr/pcibr_intr.c` lines 236 to 270, which names XBridge and PIC). Two cases leave a status
  bit set with no packet in flight: a second device interrupt arriving about 60 ns after the first was cleared (no
  transition is seen), and a status bit shared by two devices where one re-asserts while the other's handler runs,
  so the line never goes inactive between them. The comment calls both a deadlock. So the chip is **inferred** not to re-send on
  its own while the pin stays active: that rests on a code comment by the SN2 driver authors, not on a measurement, and for PIC revision 3
  specifically it is a further step.
- **Software re-posts through the force registers** (established for the semantics the header describes, `pic.h`
  lines 1603 to 1622): a write to force-always (`+0x180 + 8n`) sends a set packet as if the pin had transitioned,
  and sends one more if the pin is already active; a write to force-with-pin (`+0x1c0 + 8n`) does the same only
  while the pin is active and is otherwise ignored. Both also perform the buffer flushes. Both are write-only and
  ignore the data written.
- **Both consumers call force-with-pin when an interrupt dispatch ends.** The SN2 driver calls its
  `pcibr_force_interrupt` after the last handler returns with no threaded handler running (`pcibr_intr.c` lines
  1034 to 1042; the routine itself, lines 272 to 291, writes `b_force_pin[bit].intr = 1`). In the IRIX 6.5.30 IP35
  `pcibr.o`, `pcibr_intr_func` (`0x863c`, 592 bytes) reaches `jal pcibr_force_interrupt` at `0x887c` by the branch at `0x87a8`
  when the running-handler word at record +0x18 is zero (established, read in full).
  `pcibr_force_interrupt` (`0x7678`, 232 bytes) reads the chip type at record +0x72. For a nonzero type (XBridge,
  PIC, the fourth chip) it calls `pcireg_force_intr_set` with the pin (established). For type 0 (Bridge, which has
  no force registers) it reads status and, if the pin's bit is set, the CPU stores `0x100 | vector` to the node's
  interrupt-modify address itself: the set packet written by software (established for the instructions; that the
  target is the Hub pending-modify register is inferred from the constant and the destination setup above).
  Both consumers therefore reissue by a register write at the end of each dispatch. Whether the chip also has a timer or
  retry of its own is **unknown** (see the refused-or-lost bullet below); none was found in the sources read.
- **A second software path is periodic, on another platform** (established for that driver: `arch/ia64/sn/kernel/
  irq.c` lines 295 to 360, `arch/ia64/sn/kernel/sn2/timer_interrupt.c`, interval constant 100 timer ticks). Every 100
  ticks it compares each registered pin's status with the previous scan. A pin high in both, with the interrupt
  neither pending in the CPU nor in service, gets a force. The tick rate of that tree was not read. It runs on
  Itanium with a different host chip, so it is not evidence about a Bedrock.
- **Early-revision enable toggle** (established: `pcibr_intr_func` `0x8674` to `0x8864`; the driver at `pcibr_intr.c`
  lines 943 to 966). For chip type 2 at PIC revision 1 only (the test is `(1 << rev) & 2`), the handler clears and
  sets the pin's enable bit under the chip lock on entry, a workaround for a runaway interrupt. A revision 3 PIC
  skips it. What the toggle does inside the chip, including whether re-enabling a still-active pin sends a packet:
  **unknown**.
- **A refused or lost packet**: **unknown**. No public header or shipped object describes a chip-side retry, timer
  or response for an interrupt write, and no register names a reissue period. The error-status table above has no bit
  for a refused interrupt write; bits 17 to 21 are the link layer's own retry counters (inferred: it retransmits a
  packet the far end did not accept), and bits 22 to 29 describe requests to the PIC and responses to its reads.
  Nothing in `pcibr_error_intr_handler` or `pcibr_error_dump` handles an interrupt-write failure. The consumers' recovery assumes a
  lost packet leaves the status bit set and stays lost until software forces another. Whether the Bedrock can refuse
  an inbound write to its pending-modify address, and what the PIC then logs, is open.
- **Does the enable bit gate a forced packet?** **Unknown.** What bears on it: the public header says force-with-pin
  needs the pin active and is otherwise ignored, and says nothing about the enable register
  (`pic.h` lines 1603 to 1622). Every force in the shipped IP35 objects read happens with the pin's enable set:
  `pcibr_intr_func` forces at 0x887c while the pin is connected (enable set by `pcibr_intr_connect` at 0x829c; the other
  writers of the pin enables are the revision-1 toggle, `pcibr_detach` and a routine at 0xebbc that was not read). The one force that may not: the
  programmed-I/O flush path writes only a pin's vector and address (`pic_pio_flush_new` calls `pcireg_intr_addr_vect_set`
  and `pcireg_intr_addr_addr_set`, no enable write; `issue_force_interrupt` then writes the force-always register)
  for a pin chosen from a per-chip mask whose meaning was not read, so whether that pin's enable was set elsewhere is
  open. Its packet's data is **inferred** to be `0x1ed`: what is established is that the spin routine waits for the word at the programmed address to equal 493,
  which is `0x100 | 0xed`, the vector; nothing read writes 493 (the interrupt service routine was not read). If so, a forced packet is a write of `0x100 | vector` to the programmed address,
  the same shape the type-0 software path stores. Settling route: one physical read, below.

- **A pending bit cleared at the Bedrock while the pin is still active**: no source read describes a Bedrock
  timer that sets it again. **Unknown**; the Bedrock page owns the processor-interface side.

- **Write width, partial-word and ragged-end behaviour at memory**: **unknown**. No public source or shipped object

## Device-register bit 19 (`swap_direct`): which level swaps

Labels as above. The question: for the 32-bit direct window, does a set bit or a clear bit select the byte-swapped
lane assignment? Short answer: **a set bit selects the swapper, and "swapped" means the address-preserving lane
map; a clear bit means the lane-preserving map.** This is **inferred** for the PIC, from the public header text, the
vendor driver's flag routine and what public software sets; no PIC specification is held and nothing measured the chip.

- **IRIX 6.5.30 IP35 `pcibr.o` treats chip types 1 and 2 identically (established, read in full; that type 1 is XBridge is inferred; type 2 is PIC as stated at the top of this page).**
  The device-register flag routine at `.text` 0x0 (it takes the bits it may change as its last argument: `0x898000` from `pcibr_dmamap_alloc` at 0x24e8 and
  `pcibr_dmatrans_addr` at 0x33cc, `0x8f8000` from them at 0x254c and 0x3474, `0x1100000` for the translated path; it reads the
  chip type halfword at record +0x72; the call targets are relocation-free `.text`+0, checked against the routine's prologue
  and its compares of that argument with `0x898000` and `0x1100000` at 0x3c to 0x54):
  the byte-stream flag (0x1000) sets bit 19 only for types 1 and 2 (0x148-0x170, 0x3e0), and bits 20:19 together for
  type 0 (Bridge); the word-values flag (0x2000) clears bit 19 only for types 1 and 2 (0x174-0x198, 0x3ec-0x3f4)
  and bits 20:19 for type 0. The 64-bit attribute routine at 0x2228 maps the same two flags to address bit 55 (set for
  byte stream, clear for word values) for types 1 and 2. So the vendor driver treats "set" as the byte-stream setting
  on a type 2 chip exactly as on a type 1 chip, with no PIC-specific branch. `pcibr_endian_set` (0x3d70) is a second, older
  route: when the caller's two endianness arguments differ it sets bits 20:19 together on every chip type, otherwise
  clears them.
- **Public SGI code carries the same convention in words (established as the authors' statement).** Linux 2.4 at
  `8ef7d46c94d54ae907217463caf30ad4de88211b`, `arch/ia64/sn/io/sn2/pcibr/pcibr_dvr.c` lines 379 to 384 (byte stream sets
  `BRIDGE_DEV_SWAP_DIR` for XBridge and PIC, bits 20:19 for Bridge; word values clears), lines 2766 to 2772 (the
  64-bit path, bit 55), and `include/asm-ia64/sn/pci/pciio.h` lines 115 to 184: the byte-stream flag asks for the
  swappers to be set so a sequence of bytes arrives in memory in its written order; the word-values flag is for a
  little-endian device that moves multi-byte quantities, keeps 32-bit units intact, and makes the CPU flip the low
  address bits when it touches halfwords or single bytes of such a structure (the header gives the flip as 2 and 3). That
  matches the lane maps above in both directions.
- **Public consumers (established as software expectation, not silicon).** Linux `linux-ip35` at
  `9f613a321ea03fb91bd9947cca7dda2888ccb447`, `arch/mips/pci/pci-sgipic.c` line 257 sets bit 19 and coherent on each PIC
  slot, line 226 sets address bit 55, and the PCI-ID fixup at line 432 clears bit 19 for the IOC3. Mainline Linux
  `arch/mips/pci/pci-ip27.c` sets bit 19 on every Bridge slot (line 263 in the `linux-ip35` tree) and clears it for the
  IOC3. OpenBSD `2df91d80c104636deeef8124252ddd5951b55fbf`, `sys/arch/sgi/xbow/xbridge.c` lines 2456 to 2467, sets
  bits 20 and 19 on every device except IOC3, IOC4 and RAD1, and clears both for those three. The pattern is the
  same everywhere: ordinary little-endian cards get the swapper on, SGI's own big-endian-aware IOC chips get it off.
  None of these ran with the level inverted, and none states the sense in words, so they cannot by themselves rule
  the inverted sense out for PIC.
- **What IRIX does for the three IO9 devices (established for the flags, from the shipped objects).**
  - ISP12160, driver object `ql.o`: byte-stream plus 64-bit-address flags on every mapping (`fill_sg_elem` at 0x5618 to
    0x5648 builds `0x2001460` and `0x1001460` (the 64-bit-address flag is absent from the second); `ql_download_fw` at 0x6480 builds `0x2001060`; `ql_reset_interface` at 0x6acc builds
    `0x2001050`). Address bit 55 is set; the flag routine also sets bit 19 as a side effect of the byte-stream flag.
    The queue entries are still reversed in software per 32-bit word, which is what a byte-stream (address-preserving)
    path of a little-endian card needs on a big-endian host.
  - BCM5701, `if_tg.o`: no byte-stream or word-values flag, 64-bit and command flags only (`0x2000050`, `tg_init_card`
    at 0xad48 to 0xad60; `0x2000061`, `if_tgattach` at 0x9388). Bit 55 is clear and bit 19 is never requested; the
    driver clears the card's own swap group, so the card sees the lane-preserving map.
  - IOC4 IDE, `ide.o`: for the SGI vendor identity the base flag word is zero (the store at 0x614 on the branch taken at
    0x418); the per-mapping flags are only 0x10, 0x20 and 0x100, with no 64-bit flag. So the IOC4 uses the **32-bit
    direct window** and bit 19 is left as found.
  So no IO9 driver requests bit 19 for a 32-bit transfer, and the two drivers that rely on a particular lane map use
  the 64-bit address attribute. Whether that path consults the Device register on a PIC is **unknown**. Bit 19's effect on a real PIC 32-bit transfer is therefore not
  exercised by these three drivers except for the IOC4, whose value is whatever the PROM left.
- **What the PROM expects in the Device registers (established for the comparison; what it implies is inferred).**
  Conflict: the check below sits on the path where the mode word's 0x40 bit is clear, while this page says a PIC takes the
  0x40-set path (see the identification-word paths above), so it may never run for a PIC and the conclusion may be vacuous.
  On the path where the mode word's 0x40 bit is clear, `bridge_sanity` (0xc00000001fc4d0d8 to 0xc00000001fc4d174) compares
  the low words at +0x204, +0x20c, +0x214 and +0x21c with `0x18001000`, `0x18001002`, `0x18001004` and `0x18001005`, and
  counts and prints a mismatch. Bit 19 (`0x80000`) is clear in all four, so a part passing that check has bit 19 clear
  in Device 0 to 3 at that point. Whether the check runs on a real boot, and so whether these are real reset values,
  is **unknown**. A search of the whole PROM for a store that sets bit 19 was not made: **unknown**. The IOC4's
  32-bit transfers therefore run with bit 19 clear unless something between reset and the driver sets it; the
  IRIX IOC4 driver does not.
- **IOC4 on a PIC numbers its bytes big-endian across the lanes (inferred from public SGI Linux, established per fact).**
  See devices/ioc4/README.md, "IOC4 behind a PIC". With bit 19 clear on a big-endian host that is what the chip needs;
  the IOC4's own byte order follows the PIC's bit-19 sense, as for the IOC3 behind a Bridge.
- **Consequence of bit 19.** Hardware-visible rule (inferred for PIC): for 32-bit direct DMA
  with bit 19 **set**, a byte written at PCI byte lane `k` of an aligned word lands at the lowest-address-plus-`k`
  byte; with bit 19 **clear** it lands at `k ^ 3`.
- **Unknown, and the one route that settles it for PIC.** No held document or captured run measures a PIC's 32-bit
  direct transfer at either bit value. A physical read is the only remaining route: see the proposal in
  `questions/README.md` (PIC direct-window lane sense).

## Against SGI's Altix Linux code (linux-5.3 pin 4d856f72c10e)

The PIC is also the PCI-X bridge of the Altix 3000 generation, and SGI wrote its Linux provider for it. Under the evidence
rule for that generation (SGI's own platform code defines what it declares) the register names and layouts below are
established as software definitions, not measurements. Files read in full: `arch/ia64/include/asm/sn/pic.h`
(`struct pic`), `pcibr_provider.h`, `pcibus_provider_defs.h`, and `arch/ia64/sn/pci/pcibr/` (`pcibr_provider.c`,
`pcibr_reg.c`, `pcibr_dma.c`, `pcibr_ate.c`). An earlier section of this page cites a 2.4-era tree of the same code;
v5.3 is the last release before the Altix tree was removed and differs from it only where noted.

**Where the PIC sits in an Altix.** The provider treats the PIC and the TIOCP as two bridge kinds behind one interface
(`pcibr_init_provider` registers the same functions for both) and tells them apart only by the type the PROM reports.
A PIC hangs off a Crosstalk widget of a SHub (an even NASID: `sn_dma_flush` looks its widget up through the SHub's

**What the provider confirms or adds** (S = SGI Linux v5.3):

- **Control bit 21 is the I/O page size.** S clears it for 4 KiB pages and sets it for 16 KiB pages (`pcibr_bus_fixup`). The
  IRIX attach sets it unconditionally (established above), so the IRIX I/O page is 16 KiB (inferred from the bit's meaning in S). Agree.
- **Every register write is a full 64-bit write** (the header's note on erratum PV854697: the chip does not accept a
  write of just bits 31:0 of a 64-bit register). S implements set and clear of bits as read-modify-write of the whole
  doubleword (`__sn_setq_relaxed`). The chip does not accept narrower writes, and this agrees with the IRIX path, which does 64-bit
  accesses everywhere except the PROM's 32-bit sequences, which are a conflict: see the question
  [PIC erratum against the PROM's 32-bit accesses](../../questions/altix-io-sn2-cross-check.md#pic-32-bit-register-writes).
- **Translation entry layout** (S, `pcibr_dmamap_ate32`, 1024 entries, `PCI32_ATE_*`): bit 0 valid, bit 1 coherent (PIC
  only; the same bit is programmed-I/O on the TIOCP), bit 2 message-signalled interrupt, bit 3 prefetch, bit 4 barrier, the target widget from bit 8
  (the hub's Crosstalk widget id; four bits is inferred from the page address starting at bit 12), bits 12 and up the page-aligned address in the DMA view (`PHYS_TO_DMA`: the NASID bits
  shifted down two places, the address-space bits squeezed out). The census never decodes an entry, so each bit is new.
- **32-bit PCI map** (S, `pcibr_provider.h`): `0` to `0x3fffffff` is the local window, `0x40000000` to `0x7fffffff` goes through the
  translation entries (index = (address minus the base) shifted by the I/O page shift), `0x80000000` upward is the direct
  window offset from the direct-map register. Bit 29 of a translated address selects swap and is set only when the
  device's Device register copy already has bit 19 set. The kernel never writes Device bit 19 or the 64-bit swap attribute
  itself; the Device register values come from the PROM (`pbi_devreg`), so on this platform the sense of bit 19 is a PROM choice.
- **PCI-X mode limits** (S): the PIC cannot page-map 32-bit addresses in PCI-X mode, the direct 32-bit window and prefetch
  are not available there, and a PCI-mode function other than 0 uses the second virtual channel. A bus's mode comes
  from the PROM's description (`pbi_bridge_mode` bit 0), not from a register read by the kernel.
- **Device numbering is off by one** (S, header comment and `pcibr_dmamap_ate32`): the PIC is PCI device 0 on its bus, so
  PCI slot n is internal device n minus 1 and configuration window n + 1. Agrees with the four-slot numbering recorded
  in the identification section. Four devices only (`p_device[4]`).
- **Interrupt retargeting** (S, `pcibr_target_interrupt`): clear the pin's enable bit, replace the 48-bit address field of
  its per-pin address register (clear the field, then OR the address in), set the enable bit, then force the pin. Forcing is
  a 64-bit write of 1 to the force-with-pin word of that pin. Agrees with the force-with-pin semantics above.
- **Read ordering by forced interrupt** (S, `sn_dma_flush`): after a programmed-I/O read from a PIC device, the kernel stores
  the 32-bit value 1 to a PROM-supplied force address, then spins until a PROM-supplied memory word equals `0x10f`. That is
  the packet the interrupt write deposits, and `0x10f` is `0x100 | 0x0f`, the same `0x100 | vector` shape this page infers from the shipped
  routine ("Does the enable bit gate a forced packet?" above, which inferred `0x1ed` for another vector). One more independent
  reading of the shape; still not a hardware measurement. The force store is 32 bits wide, which meets the same erratum question.
- **PCI error handling is in the PROM.** The bridge error interrupt (`SGI_PCIASIC_ERROR`, vector `0x33`) calls a firmware
  routine through the platform's firmware call interface and panics on a negative result; the kernel never reads the PIC error
  registers. So the SN2 code says nothing about error-register semantics.
- **Identity numbers**: the provider's ASIC type numbers (`PIC` 2, `TIOCP` 3) and the bridge-type numbers it keeps (also 2
  and 3) equal the halfword at bridge record +114 in IRIX (2 PIC, 3 the fourth chip). All three schemes are software choices; the provider
  code never reads the identification register, so it adds nothing on part numbers `0xd102` and `0xe000`.
- **Bus-visible DMA addressing differs by bridge**: a PIC uses the DMA view with the NASID bits shifted down two places; a TIOCP uses
  a view with the NASID in bits 53:40 and a network address below (`PHYS_TO_TIODMA`). See [../tio/README.md](../tio/README.md).

## Register field layouts (SGI's 2.4-era Linux PIC header)

The layouts are in [registers-extra.md](registers-extra.md) as 64-bit words (`ID_REG`, `STATUS_REG`, `CONTROL_REG`,
`INT_STATUS_REG` and so on), one per register or register family; the table there gives every field, its bits and its grade.
Source: the PIC register structures in `include/asm-ia64/sn/pci/pic.h` and the control, interrupt and device masks in
`include/asm-ia64/sn/pci/bridge.h`, both in the pinned 2.4.37-era tree (SGI platform code, GPL). Under the rule for
this generation a field the header defines is **established** as a software definition. Three limits on that grade:

- The header's own register structure leaves bits reserved that its mask list names. Control bits 62:61 (no-snoop and
  relaxed ordering), 55:40 (bus, device and function number) and 31:29 (parity enables) come from the masks, and
  interrupt status bits 45:42 (PCI-X unexpected completion, split timeout, split error message, split message parity
  error) likewise. The extra unit gives each of those fields its own source line. The IRIX attach constants agree with
  them: it clears 62:61 and 55:40, sets 31:30 and sets 29 unless the revision is 1, and its enable mask covers 45:41.
- Names that describe an effect (`mem_swap`, `sys_end`, `f_bad_pkt`, `en_clr_pkt`) are the header's names; no source read
  says what the two states do, so the unit's text says "name only". What a field does on the chip is not established
  by a field name.
- **The header contradicts itself on where the PCI-X error group sits.** Its offset list puts the PCI-X error address,
  attribute, data and read-request-timeout registers at 0xe0 to 0xf8. Its structure in `bridge.h`, SGI's v5.3 `struct pic`
  and the IRIX code (0x600 to 0x630, read in full above) all put the group at 0x600 and up, with a separate `pcix_timeout`
  at 0x638 and 0xe0 to 0xf8 as padding. The census agrees with 0x600. The 0xe0 list reads as an earlier layout of the
  chip's documentation; which layout the silicon uses at 0xe0 to 0xf8 is **unknown**, and the read-request-timeout layout
  (`PCIX_TIMEOUT_REG`) is not attached to a slot for that reason. The attribute layout is attached to 0x608 by IRIX use
  of that slot (inferred for the other attribute slots by shared name).

**Reset values.** Only one register has a stated reset. The header's text for the interrupt enable register (0x108) says
all bits are zero after reset. That is established as the header's statement and not a measurement; the generated
register table stays `unknown` because the census unit is machine written and the TIOCP unit shares its configuration.
Every other reset value is unknown. The PROM's write of zero to the enable register before the kernel runs is not a reset
value (it proves nothing about the state before it).

## Revision differences (what the 2.4-era SGI driver sources say)

SGI's driver of the same generation as the IRIX code carries a table of PIC workarounds, each a mask over part
revisions where revision 1 is "A", 2 is "B" and 3 is "C" (`(1 << revision) & mask`; the `PV` numbers are SGI's erratum
identifiers as printed in `include/asm-ia64/sn/pci/pcibr_private.h`, with the uses in `arch/ia64/sn/io/sn2/pcibr/pcibr_dvr.c`, `pcibr_error.c`, `pcibr_intr.c`, `pcibr_rrb.c` and `pcibr_slot.c`, same pinned tree). The IRIX objects use the same revision test, so these entries explain code this
page already read. All eight are **established** as what that driver does; why the chip needs them is as SGI's comments
say, and none is a measurement.

| Erratum | Applies to | What the driver does | Matches the IRIX attach |
|---|---|---|---|
| PV854697 | all revisions | write 64-bit registers with 64-bit stores | yes: every PIC accessor is `ld`/`sd` |
| PV854827 | all revisions | fake the "widget 15 present" bit | not read in IRIX; meaning unknown |
| PV855271 | revision 1 | virtual channel enable (device bit 25) only for 64-bit devices; the default device value leaves it off | not read |
| PV855272 | revision 1 | runaway interrupt: drop and restore a pin's enable bit around handling | not read |
| PV856155 | revision 1 | after a PCI-X arbitration error write ones to the four device-broke bits (23:20) of the arbitration register (the driver's comment calls this clearing them) | not read |
| PV856864 | revision 1 | clear enable bits 39 and 9 and set the request timeout to 0x750, so locked read tags time out sooner | yes: the same two bits and 0x750 |

as far as these sources go; no source describes any other behaviour difference between revisions, and none states what
each revision changed in silicon (unknown).

## Reset expectations

Unknown for every register: no routine reads a register before writing it in the attach sequence, apart from
read-modify-write of control and enable (so it expects whatever the hardware presents, and clears or sets
listed bits). The attach itself writes: `+0x110` 0x7f, `+0x120` 0x6db6db, `+0x118` 0, the banks and entries zero.

The IP35 PROM routine at 0xc00000001fc41f38 (read in full, 0xc00000001fc41f38 to 0xc00000001fc41fb4) clears the interrupt registers before the
kernel runs, and it has two paths on the identification word. For parts 0xd102 and 0xd112 with manufacturer 36 it
stores 64-bit zero to `+0x108` and 64-bit all-ones to `+0x110` (established). Only for any other part does it use
the 32-bit stores at `+0x10c`, `+0x114` (0xffff) and `+0x12c` (true of that routine only: the bridge diagnostic below does 32-bit accesses on the PIC path). So the census rows of the PROM `sw` stores at those
three offsets belong to a Bridge-family path, not to the PIC: the scanner assigned them to the PIC because it kept the part-number
variant after the manufacturer check failed, and it missed the PIC stores because the PROM image was split after each
return. Both are fixed: a failed manufacturer check withdraws the variant and routines are cut by control flow, so the
census now has the 64-bit PIC stores under `pic` and the 32-bit stores under `probe?` (chip not named). The register table's `4,8` widths for
`+0x108`, `+0x110` and `+0x128` and the `+0x110` constant 0xffff come from those rows; the PIC value the PROM
writes to `+0x110` is all-ones, the kernel's is 0x7f.

## PROM bridge diagnostic (0xc00000001fc4ca98)

The routine that prints the "Running %s diag (Bridge base = 0x%08x)" start message and names itself
`bridge_sanity` takes the window base in `a1` and a mode word in `a0`. The census scanner now seeds it
(`prom_c00000001fc4ca98` in `tools/configs/pic.json`); before, the routine was reached through a pointer the scan
did not follow, so none of these sites were in the census. Read in full, 0xc00000001fc4ca98 to 0xc00000001fc4cfcc:

- It reads the identification word (+0x4) through a helper that accepts parts 0xc002, 0xd002, 0xd102 and 0xd112
  and prints a warning for any other. Only 0xc002 gets an extra check (control word +0xc, bit 5). The path
  below does not branch on 0xd102 or 0xd112, so a PIC that reaches it runs the same sequence as a Bridge
  (established for the code). That a PIC reaches this path (mode bit 0x40 set, low mode nibble not 2) is
  inferred from a public capture that runs the diagnostic on PIC widgets; the mode word was not traced.
- Every access is a 32-bit `lw`/`sw` at an address of the form 8n+4, the low word of the big-endian doubleword at
  8n (established: the instructions). That this is the low half of a 64-bit PIC register is inferred from the
  byte order.
- Sequence for the path with mode bit 0x40 set (established: the instructions and their order): read +0x104
  (prints a warning if nonzero); write 0xa5a5a5a5 to +0x3c and 0x5a5a5a5a to +0x34 and read each back (+0x3c
  compared whole, +0x34 under mask 0xfffff against 0xa5a5a); write 0x01000000 to +0x10c. Then for test number
  n = 0 and 7 to 19: write n to +0x12c and read it back; if equal, write 0xdeadbeef to +0x7c; poll +0x104 up to
  1000 times (a delay call between polls) until the whole word equals 0x01000000, that is bit 24 set and nothing
  else; poll the doubleword at +0x98 of a Bedrock register block for bit n; write 8 to +0x114; write n to
  the doubleword at +0x90 of that block and read +0x98 again. At the end write zero to +0x10c, +0x34 and +0x3c.
  Which Bedrock register block the +0x90 and +0x98 accesses reach, and what they mean, is inferred from the
  constants that form the address and the "did not reach" message strings the routine prints, not read from a
  source.
- The write to +0x7c is on the low word of slot +0x78, which this page lists as read-only (its only accessor is
  a getter, `linkside_err_addr_get`: inferred). The routine does not check that the write was ignored. What a
  PIC does with it is unknown.
- Register roles are unknown from this routine. The 0xa5a5/0x5a5a pattern, the bit 24 test and the +0x10c and
  +0x114 values are what the code does, not what the registers mean.
- With mode bit 0x40 clear, another path reads +0x2c, +0x24, +0x204, +0x20c, +0x214 and +0x21c (all `lw`) and
  writes +0x24 (`sw`). These are census sites; the path was not read in full (unknown meaning).

## PROM set-up of a PIC in `main_three` (`0xffab0c00`)

SN2 SAL_B (snprom 10.54, `shub1snprom.bin`), read in the Ghidra listing. Offsets here are the Itanium's: a 64-bit register at
`8n` is accessed as `ld8`/`st8` at `+8n`, and the one 4-byte access is the identification word at `+0` (this page's earlier
MIPS-side sections say `+0x4` for the same word). The PROM reaches the PIC through its own copy of the `pcireg_*` accessor family
(names are in the image: `pcireg_control_get`, `pcireg_intr_reset_set` and so on, as in the IRIX driver). Each accessor first
reads the 4-byte word at `+0` of the window it is given; if bits 11:1 are `0x24` and bits 27:12 are `0xd102` or `0xd112` the chip
type is PIC (2), `0xe000` or `0xe010` with manufacturer `0x24` is type 3, anything else is type -1 and the accessor prints
"pcireg_*(): unknown bridgetype" and **does nothing** (established, `0xffab3f40` and every accessor between `0xffab41f0` and
`0xffabf2c0`; a pointer with bits 37:36 both set is taken as a soft-state record and skips the id read, which no window address on this path has). So a model that answers the identification read wrongly has its PIC writes silently dropped. All other accesses
are 8-byte `ld8.acq` / `st8.rel`.

Called from the link walk in `0xffab0f10` for an id part `0xd102`, once with the link window `W` (bus 0) and once with `W + 0x80_0000`
(bus 1); the bus is bit 23 of the pointer. Steps in order (for window pointer `W`, `n` = the widget number taken from `W`: bits 27:24
for an even NASID, bits 29:28 for an odd one):

| # | Site | Offset, width | Dir | Value, compare | Keeps the one-node path | 2.4 name (`pci/pic.h`, `pci/pcibr.h`); PROM name | Grade |
|---|---|---|---|---|---|---|---|
| 1 | `0xffab0c7c` | `+0x20`, 8 (and the 4-byte id read at `+0`) | R | | any; id as above | `p_wid_control` (`pic.h`, `struct pic`); `pcireg_control_get` | established |

**The three writes a model must accept (field decode, 2026-11-16).** All are plain 8-byte read/write storage on each head's window; none has a read side effect, and the PROM does not test any of them afterwards.

- `+0x280` and `+0x288` (`rrb`, even and odd response buffer map): `0x88889999` written to each, not read back in this stage. Per nibble, low to high: `9` = valid, virtual channel 0, device pair 1 (nibbles 0 to 3); `8` = valid, virtual channel 0, device pair 0 (nibbles 4 to 7). So each register hands four response buffers to each of two slots (even register: slots 0 and 2; odd register: slots 1 and 3), all on virtual channel 0. Reset value: unknown. The enable bits do not act on anything the PROM does next; the effect on the model is only that reads of these registers return what was written.

Values a model needs for this stage: id word `+0` with manufacturer `0x24` and part `0xd102` on bus 0's window and `0xd112` on bus 1's (the PROM accepts either part on either window; the SGI header names `0xd112` for bus 1), every
register above plain read/write storage (8-byte), a clock at `0x1_101c_0000` that advances (the waits), and no side effect on
reads of `+0x20`, `+0x48`, `+0x80`.

### Review (the three writes and the id-word guard, commit a132551)

Independent re-read on 2026-11-16 in Ghidra (IA-64, `--sn2-prom --no-analysis`) of snprom 10.54 (`shub1snprom.bin`): `0xffab0c00` and the accessors `0xffab3f40`, `0xffab41f0`, `0xffab5d90`, `0xffab6030` and `0xffabcfb0`. **Confirmed.**

- `0xffab0c00` runs for each head (`W`, `W + 0x80_0000`); the `+0x48` accessors are unconditional, so the write happens on both heads, while only the interrupt block is gated on bit 23.
- `+0x48` is `0xffab5d90` (load) then `0xffab6030` (store) of `(value & ~0x3ff) | 0x3e0`: bits 9:0 only. `pic_llp_cfg_u` is 25:16 `llp_maxretry`, 15:10 `llp_nulltimeout`, 9:0 `llp_maxburst`, and the header comment says the register is valid on bus 0 only. So maximum burst 0x3e0 (992) is right.

**Changed.**

- The model-requirement line said part `0xd102` on both windows. The PROM accepts `0xd102` or `0xd112` on either head (the guard is per window), and the header (`PIC_WIDGET_PART_NUM_BUS0` `0xd102`, `PIC_WIDGET_PART_NUM_BUS1` `0xd112`) names `0xd112` for bus 1. Only the link walk (`0xffab0f10`) tests for exactly `0xd102`, and it reads head 0's word. Fixed above. - "Not read back" holds for the PROM stage only. The SAL runtime's PIC attach (next section, row 10) read-modify-writes `+0x280` and `+0x288` for revision 1 (`0xf000f` set), so those two must read back what was written.

**Not checked.** Reset values of the three registers (no specification or firmware-independent source). Whether the real chip ignores `+0x48` on bus 1. The `0xe000`/`0xe010` (type 3) accessor branch beyond the id test.

**What the L1 must supply for an IO10 PIC to attach.** A `0x0013` reply (status 0, slot, type) whose type, once lower-cased, is one of `#`, `=`, `m`, `o`
or `v`. Of these only `o` (`0x6f`, Linux `L1_BRICKTYPE_OPUS`) names a product that could be an Altix 350 module; `#` and `=` are the PX and IX bricks,
`m` is the L1 letter `M`, which the sysco brick table gives as the C-brick (IP67); `v` is not tied to a product here. `0x66` (Opus TIO) is in the `pci_widget_to_bus` table, so its bus numbering exists, but `pic_attach2` does not
accept it. The model should therefore answer `O` (upper case on the wire, as the L1's own handlers send it) to `0x0013` and `0x0003`. Grade: the byte
path, the accepted list and the abort are established; that a real 350 answers `o` is **inferred** from the accepted list. Against it: the ARM L1 1.62.1 handler of request `0x0013` answers an `F` brick with one slot with status 0, integer 0 and the stored letter `F` (re-read in the review below, no case change), which the PROM lower-cases to
`0x66`; if that were what a 350 sent, the 10.54 PROM would print the error above and attach no PIC, which a booting 350 contradicts. The two are reconciled only by a
captured `0x0013` reply or a 350 L1 that reports `O`.

### The bits 55:48 write in `pic_attach2`

The reported oddity is real in the listing: at `0xffb6e3c6` the code loads `0xff00ffffffffffff` into r15, ANDs the control word with it (`0xffb6e3e0`), ORs
`r34 << 48` (`0xffb6e3dc`, `0xffb6e3f6`, r34 the third argument, the bus index 0 or 1, never modified in the function) and ANDs with r15 again
(`0xffb6e406`, r15 not reloaded in between). Bits 55:48 are therefore zero afterwards; only bits 15:8 of the argument, which are zero, could reach 63:56. The decompiler
folds the second AND into `(param_3 & 0xff00) << 0x30` (only bits 15:8 of the argument survive into 63:56) and keeps one clear of 55:48 on the control word, so it shows the same value as the listing; the combined mask `0x9ffff8ffffffffff` has `0xff` in byte 6 only because 55:48 are already clear by then. The result does not depend on the second AND: the OR cannot reach 55:48. The IRIX attach
sequence earlier on this page clears and then sets 55:48 with a different second mask (`0x9fff00ffffffffff`). Whether the PROM's second mask is a deliberate
choice, a compiler artefact or a latent bug is unknown; the observable fact is that this PROM never leaves a bus number in bits 55:48 of `+0x20`. A model
that keeps those bits writable will read them back as zero after attach (established for the write sequence; hardware effect of a non-zero value unknown).

### Probing a slot (`pcibr_slot_info_init`, `0xffb36020`)

For each slot: read the word at register 0 (above). Absent if the protected read failed, or if the low 16 bits are `0xffff`
(`0xffb36250`). A failed read does not mark the slot; a slot that answered (including `0xffffffff`) is first marked in the record's
valid-device mask (`+0xac`). A slot whose id is vendor `0x10a9` device `0x100a` (an IOC4) records itself in the board
(`0xffb32680`). Then header type (register `0xe`, bit 7 = multifunction); with that bit set, functions 1 to 7 are read the same way. The
IP35 PROM reads only function 1 (see [facts outside the census](facts-outside-census.md#empty-slot-configuration-reads)); this
runtime reads 1 to 7. An empty slot may return `0xffffffff` with no machine check, or fail the protected read: either is "absent". What
the real PIC does for an unclaimed configuration cycle is traced in [Config read to an empty slot](#config-read-to-an-empty-slot); the PROM clears
nothing but `+0x110 = 0x40` after the read.

Recognised devices in the later device set-up: vendor `0x10a9` with device `0x100a` (IOC4) or `0x0003` (IOC3), allowed only in slots
0 to 2 ("ERROR: IOC3/IOC4 devices must be located in one of the first 3 slots", `0xffb38260`, slot 3 fails and the allocation returns 0);
The bus provider method `0xffb3f810` makes an unconditional first call through its method table for every device it attaches (not shown to be IOC-specific); vendor `0x1077` with device `0x1240`, `0x1280` or

### BAR sizing and window assignment (`0xffb36020`, `0xffb37520`, `0xffb37e70`)

Run in `pic_attach2` for each slot in the record's range, as three loops (slot info, address space, Device register), before the ioboard switch above.
Configuration accesses use the wrappers in the previous section (4-byte reads and writes). `0xffb3bec0`, which an earlier reading took for the
mapping step, is only a lookup-then-allocate wrapper over the bus provider's resource methods at `+0x28`, `+0x10`, `+0x20` and `+0x18`.

Sizing, per function (`0xffb36020`; functions 1 to 7 only if the header type, register `0xe`, has bit 7 set; functions 1 only, on a chip of record type 3 (a TIO bridge) at revision 1):

1. Read the command register (reg 4). For a non-bridge header whose latency timer (reg `0xd`) is zero and whose `Device(s)` bit 21 is clear, write the timer: the device's maximum latency (reg `0x3e`) times 8, `0x10`, `0x18` or `0x20` by bus mode, or four times that unit if the product is zero or over `0xff`; the unit comes from the bus speed and mode word at record `+0x36` (`7` gives `0x20`, `5` gives `0x18`, `2` or `3` give `0x10`, else 8). Skipped for IOC3 (`0x10a9:0x0003`). When record `+0x36` has bit 0 set (the PCI-X mode bit, inferred) and the cache line size (reg 0xc) is zero, write `0x20`. Established for the writes.
2. For BAR `i` from 0 to 5 (header type 0; two BARs for a bridge header): write `0xffffffff` to the BAR, read it back, then record: bit 0 set = I/O (mask `~3`, record type 2, flags = bits 1:0); else memory (mask `~0xf`, record type 4, flags = bits 3:0). The size is the lowest set bit of `(readback & mask)`. A readback of zero (after masking) means no BAR. If bits 2:1 = `0b10` (64-bit) the next BAR is written 0 and skipped. The loop stops after the first non-empty BAR of an IOC3 only (`0x10a9:0x0003`; listing `0xffb36960`, tested again at the first BAR). An IOC4 (`0x10a9:0x100a`) gets a separate provider call at the top of the function (`0xffb32680`) but its BAR loop runs over all BARs the header type allows, so BARs 1 to 5 of an IOC4 are written all-ones and must read back 0 (or a sized BAR). Established; this corrects the earlier IOC4 stop.
3. Nothing is written back to the BARs here beyond that all-ones probe and the zero for a 64-bit upper half; the base is assigned later.

So a device model needs only standard BAR behaviour: a BAR whose writable bits are the size mask, with the memory or I/O flag bits readable. No size is special-cased. For the IOC4 and the Vitesse SATA controller no vendor-specific code runs in sizing (the vendor/device constants in this runtime are IOC3, IOC4 and the QLogic parts listed above); their sizes are whatever the devices answer.

Assignment (`0xffb37520`), per function and BAR with a size: allocate a window through `0xffb38260` (type 2 for I/O; type 4 for memory whose flag bits 2:1 are `0b01` (below 1 MiB), else type 5; memory sizes are rounded up to at least `0x1000`) and write the returned base to the BAR with a 4-byte configuration write. An allocation that returns 0 prints a message and marks the slot failed (return -1). The expansion ROM BAR (offset `0x30`, or `0x38` for a bridge header) is probed with `0xfffffffe`, sized the same way and given a type-5 window, except for IOC3 and IOC4. Then the command register gets bits 2:0 ORed in, written only if one of those bits is not already set (bits 2 and 0 only for Adaptec `0x9004:0x1160`). The window pools are the record fields `pic_attach2` fills just before the probing loops: pairs (base, last) of `0x200000`/`0x3fffff`, `0x400000`/`0x5fffff`, `0x600000`/`0x6fffff` and `0`/`0xfffff` at record `+0x120`, `+0x140`, `+0x160`, `+0x180`, the same three pairs at `+0x348`, `+0x368`, `+0x388`, and `0x1000`/`0xfffff`, `0x700000`/`0`, `0x10000`/`0x9ffff` at `+0x3a8`, `+0x3c8`, `+0x3e8` (stores established; which field is which bus-space window inferred, from the Device register rule below). The address translation from a window offset to a bus address is the bus provider's `+0x38` method (`0xffb38260` with `0xffb7de00` / `0xffb8def0` behind the hub providers of types 4 and 5): type 1 adds the slot base and `0x40000000`, type 2 `0x3000000`, types 4 to 6 `0x8000000` (checked against 128 MiB), type 7 `0x1000000` (checked against 256), device BARs 8 to 13 the per-BAR offset (decompiler reading, not cross-checked in the listing).

Device register (`0xffb37e70`, per slot `s`): read `Device(s)` at `+0x200 + 8s`, then write it back with bit 27 cleared and bit 25 set (revision 1 of a type-2 chip: bits 27 and 25 both cleared), bit 18 set, bit 13 cleared, and bits 11:0 = `(window >> 20) & 0xfff`, where the window value is the slot's direct-map window word masked to 2 MiB alignment for slots 0 and 1 and 1 MiB for the others, and to 30 bits (`0x3fffffff`) for every slot except 3 (slot 3 takes a different branch and also sets the word at slot-record `+0x170` to 2); bit 12 is set for every slot except 3. The numbers depend on the allocated windows, so they are not constants; the bit operations are established, the window field inferred. Then the shadow value is also written to the slot's second-level register by `0xffabc800`.

### Interrupt allocation and the PIC registers it writes

Two things are allocated, in this order. Established unless marked.

1. **Per-device interrupt record, during the scan (`0xffb3ef90`, run per device by `0xffb2be00`).** For each device with a non-zero interrupt pin (config register `0x3d`, read with `0xffb3c0c0`), the bus provider's `+0x50` method (`0xffb6c4f0`) allocates an `sn_irq_info`-shaped record (`0x50` bytes, `0xffb8fee0`): the irq is the first unused number in `0x3c` to `0xe6`, or the least-shared one if all are in use, cookie from a counter at I/O state `+0x40`, flags bit 0 set, share count 1. The PCI interrupt line (config register `0x3c`) is written with that irq. The line index is `0xffb6c460(pin)`: pin 1 or 3 gives the slot number, pin 2 or 4 gives `(slot + 4) & 7`, anything else 0. IOC3 and IOC4 also get a provider `+0x68` call (endianness, `0xffb321f0`) with arguments 1, 0; the QLogic parts get their response buffers (previous section).
2. **Connect, the provider's `+0x58` method (`0xffb6c720`), called per device by `0xffb3ede0` during the scan (config byte `0x3d` read, this method, config byte `0x3c` written with the irq, or `0xff` on failure).** It asks the hub provider's `+0x28` method (`*(bus + 0xe0) + 0x28`, five arguments: the bridge NASID at record `+0x102`, the irq, the target NASID halfword at record `+8` (starts `0xffff`), the slice word at `+0xc` (starts `0xffffffff`), an out pointer) for the cross-bar address, which lands in record `+0x20`, then programs the PIC with these accessors (the register offsets are the accessor stores, `pcireg_*` names by function):

| Register | Offset | Write | Site | Grade |
|---|---|---|---|---|
| device select (`int_device`) | `+0x120` | clear 3 bits at `3n` (`7 << 3n`), then OR in `slot << 3n`, `n` = line index, `slot` = record `+0x278` of the host function | `0xffabaf30`, `0xffabac70` | established |
| per-pin interrupt address | `+0x130 + 8n` | bits 55:48 = the irq (`0xffabb9e0`), bits 47:0 = the address the hub provider returned (`0xffabbcf0`), each as a read-modify-write | | established |
| interrupt enable | `+0x108` | OR `1 << n` | `0xffaba1a0` | established |
| flush read | `+0x50` | read | `0xffab62d0` | established |

The value left in `int_device` after the attach reset (`0x6db6db`, all lines to device 3, written once at `0xffb6e38c`) is replaced one field at a time. For an IOC4 in slot 1 and a SATA controller in slot 3, each with interrupt pin A (pin 1; the pin value is the device's, not read here), the lines are 1 and 3 (these are the scan's slot numbers, which are Linux device number minus one: Linux devices 1 and 3 give lines 0 and 2, see the pin rule below): `int_device` field 1 becomes 1 (`0x6db6cb` from `0x6db6db`; field 3 becomes 3, which it already is), `+0x138` gets the IOC4's irq in 55:48 and the address, `+0x148` gets the SATA controller's, and bits 1 and 3 of `+0x108` are set (on top of the late-init OR constant below). The irq numbers are the first free ones in `0x3c` to `0xe6` unless the kernel requests one through `SN_SAL_IOIF_INTERRUPT` (alloc, a request of -1 picks one); with no request, the first line allocated in the scan gets `0x3c` and the next `0x3d`; devices on the same bus and line index get the same irq number in separate records, which share one target. The address is the hub provider's, `nasid << 36 | 1 << 47 | SH_II_INT0` (chosen slice 0) or `SH_II_INT1` (any other slice) with the **target** node's NASID: read in full and checked in the listing (`hub_intr_alloc` `0xffb73df0`, address builder `0xffb739e0`; the hub table is `0xffc2b8e8`, node record `+0x2d8`), the same expression as the 2.4 kernel. How the target node and slice are chosen, the irq search, and the stores that point `SH_II_INT0`/`SH_II_INT1` at a processor are in [the SHub interrupt page](../shub/interrupts.md#the-firmwares-interrupt-allocator-sn_sal_ioif_interrupt) (established, SAL 5.04 and 4.90 identical). The tables at `0xffc2b0b8` (type 4) and `0xffc2b188` (type 5) mentioned earlier are address-translation methods, unrelated. Two lines of one bus that map to the same line index get the same irq number in separate records (share count 2), as the SHub page states.

### Which widget a PIC sends its interrupts to (`+0x38` bits 51:48; SAL 5.04 `shub1snprom.bin`)

Read in the Ghidra decompiles, with the accessor bodies and their callers checked in a binutils listing of the same image.

- **The field.** `pcireg_intr_dst_target_id_set` (`0xffab5230`) is a read-modify-write of `+0x38`: it loads the doubleword, ANDs it with
  `0xfff0ffffffffffff` and ORs in `(value & 0xf) << 48` (listing `0xffab53a0` to `0xffab53e0`; it acts only when the id word says PIC).
  `pcireg_intr_dst_addr_set` (`0xffab57a0`) replaces bits 47:0 and keeps 63:48, so a later address write leaves the target id alone.
  Established. The PROM writes no other register that picks a host port.
- **The writers.** There are two callers, and the image holds no pointer to `0xffab5230` that a table could call through: `pic_attach2` at
  `0xffb6e68c` (once per bus head, so twice per PIC) and `tiocp_attach` at `0xffb4819c`, where the accessor does nothing for a TIO bridge.
  `pic_attach2` passes the byte at `+0x60` of its soft-state record, which it copied (`0xffb6dd3c` to `0xffb6dd56`) from byte `+0xc` of the
  per-widget record it was handed. Every record of a node is built with the same byte, the node's own widget id: `0xffb745e0` reads the
  node's interrupt-interface widget control register (`nasid << 38 | 0x8_01c0_0020`, bits 3:0) and `0xffb45770` stores it at node `+0x2f2`;
  the per-widget records at node `+0x940 + 0x30 * widget` copy that byte (`0xffb451e0`, `0xffb499a0`). Established.
- **Result for the three PICs.** Widgets 12, 13 and 15 of one host node get the same target id: the host SHub's own widget id, bits 3:0 of
  its widget control register, which `main_three` wrote from the crossbar face's source-id field (`W0 + 0x08` bits 9:6, see
  [the SHub interface page](../shub_ii/README.md)). The middle PIC (15) is not treated differently from the outer ones (13, 12), and
  nothing writes a PIC's own widget number or an enclosure number into `+0x38`. Established for the code path. The number itself is
  unknown, because the crossbar hardware assigns it. Inferred value: `0xa` for a host on the first XIO port, `0xb` for the second. The PROM
  special-cases widget ids 10 and 11 as the hub's own link (`0xffb45510` tests 10; `0xffb73050` tests 10 and 11 before printing "Xtalk Link
  failed") and prefers link `0xa`, falling back to `0xb`. The field is four bits wide and 12, 13 and 15 are the PICs, so none of them can be the
  host id.
- **The address half.** Bits 47:0 of `+0x38` get the error interrupt's address (`0xffb6cfec`, late error set-up below): target NASID `<< 36`,
  bit 47, and `SH_II_INT0` or `SH_II_INT1` (the allocator section of [SHub interrupts](../shub/interrupts.md)). The three PICs are widgets of
  the host node, so they share its NASID; each interrupt's target node and slice come from the allocator (a node with no processor retargets to
  the nearest one that has one, established there).
- **`int_device` is not a port.** `+0x120` holds eight 3-bit fields, one per interrupt pin, set to the PCI device's scan slot (0 to 3, Linux
  device minus 1) by the per-device connect step above; the attach resets it to `0x6db6db`. It never names a host, bridge or widget. Values
  per PIC depend on the cards fitted. On the IO9's bus (widget 12, bus 1) INTA of the IOC4 at device 1, the SCSI at 3 and the Ethernet at 4
  gives pins 0, 2 and 3 slots 0, 2 and 3 (the pin rule below); unused pins keep 3. No register capture of a real PIC is held.
- **What public SGI Linux expects.** Linux v5.3 never touches `+0x38` or `+0x120`: `pic.h` declares `p_wid_int_upper`, `p_wid_int_lower` and
  `p_int_device`, and `pcibr_provider.c` only clears the pin's enable bit, rewrites the low 48 bits of `p_int_addr[n]` (mask
  `PIC_HOST_INTR_ADDR`, `0x0000ffffffffffff`) with the firmware's `irq_xtalkaddr`, sets the enable bit and forces the pin. It relies on the
  PROM having set the target id. The 2.4 tree (`linux-2.4` at `8ef7d46c94d5`, `arch/ia64/sn/io/sn2/shub_intr.c`) set the interrupt's target to
  the master widget id of the device's widget info, and `hub_widget_id` returns the widget control register's `wcr_widget_id`: the host's
  widget id, not the PIC's. Established as source. Whether the 2.4 `pcibr_setwidint` layout (the Bridge one, `0x000F0000 & (targ << 16)` in an
  upper word) matches this PIC's `+0x38` is unknown.

Not checked: SAL 4.43 and 4.90 (the allocator routines agree there; these accessors were not re-read); which node's table `pic_attach2`
reads when the bridge node's `+0xe` field is not `0xffff` (an I/O-only node); the widget control value on a real host.

### Which PIC pin an INTA to INTD lands on, and what SAL call `0x02000057` returns (snprom 10.54 and 4.43, SHub 1)

Read in the Ghidra decompiles of both images, each function in full. Established unless marked.

**The handler.** The runtime's SAL dispatch (`sal_0200005e` at `0xffb1e660` in 10.54; `sal_02000060` at `0xffadf9d0` in 4.43) switches on the call id; `case 0x2000057` calls `0xffb3dbc0` in 10.54 (`0xffb31770` in 4.43, same body). Arguments, matching Linux's `sal_get_pcidev_info`: segment, bus, devfn, a pointer for the device record and a pointer for the interrupt record. It finds the device's record in the bus's list (`0xffb2aeb0`, 4.43 `0xffb22700`): the node whose device byte at `+0x64` equals `devfn >> 3 & 0x1f` and whose function byte at `+0x65` equals `devfn & 7` (a record with the id word at `+0x68` equal to `-1` never matches). It then:

1. Rewrites qword 7 of the device record (Linux `pdi_slot_host_handle`) as `(host function's device << 3 | host function's function) | host bus number << 32 | segment << 40` (bus number read from the bus record the host function points to, `+0x80`, word at `+8`; the host function is the record at `+0x238`).
2. Copies 12 qwords (`0x60` bytes) of the device record to the caller: seven mapped BAR addresses (qwords 0 to 6), the host handle (7), then four pointers (8 to 11); qword 11, at `+0x58`, is the pointer to the interrupt record.
3. If that pointer is non-zero, copies the 10 qwords (`0x50` bytes) it points at to the second buffer; otherwise leaves the buffer alone. Returns 0 either way, so a device with no interrupt pin returns a success with an untouched interrupt buffer.

**The interrupt record (`0x50` bytes, built by the bus provider's `+0x50` method `0xffb6c4f0` in 10.54; the pin function in 4.43 is `0xffb43e50`).** Field offsets agree with Linux `struct sn_irq_info` (`v5.3:arch/ia64/include/asm/sn/intr.h`):

| Offset | Linux field | Value the PROM stores |
|---|---|---|
| `+0x08` | `irq_nasid` (16 bits) | `0xffff` until the interrupt call picks a target |
| `+0x0c` | `irq_slice` | `-1` until then |
| `+0x14` | `irq_irq` | the allocated vector, first unused in `0x3c` to `0xe6` |
| `+0x18` | `irq_int_bit` | the PIC pin, formula below |
| `+0x20` | `irq_xtalkaddr` | the crosstalk address, written by the connect step above |
| `+0x28` | `irq_bridge_type` | first word of the record the device's `+0x88` pointer names (read as the bridge type, 2 for a PIC: inferred from the Linux field name) |
| `+0x30` | `irq_bridge` | the word at `+0x20` of the bus record that the host function's `+0x80` points to (read as the bridge pointer: inferred from the Linux field name) |
| `+0x38` | `irq_pciioinfo` | the device record (a PROM pointer; Linux replaces it) |
| `+0x44`, `+0x48`, `+0x4c` | cookie, flags, share count | counter, 1, 1 (from the earlier paragraph) |

**The pin formula.** `0xffb6c460(host, pin)` returns `host.slot` for config pin 1 (INTA) and 3 (INTC), `(host.slot + 4) & 7` for pin 2 (INTB) and 4 (INTD), and 0 for any other value. It reads `host.slot` at `+0x278` (10.54; `+0x274` in 4.43) of the host function's record, written by the slot scan `0xffb36020` with its slot argument; the same call stores the record's device byte `+0x64` as `slot + 1` (`0xff` stays `0xff`). A function other than 0 of a slot, or a device behind a PCI-to-PCI bridge, uses the host function's `slot`, and for a device behind a bridge the pin is first rotated through each bridge on the way by a table lookup (`0xffb43680`, "pciio_ppb_intr_map"; the table was not read). Nothing in the formula looks at the bus number, the ioboard type or the PIC revision.

**Linux's device number is the scan's slot plus one.** The runtime's config read (`salruntime_pci_config_read`, 4.43) addresses `bridge base + 0x20000 + device * 0x1000` with `device = devfn >> 3 & 0x1f`, and refuses a device outside 1 to 4 (`0x10000b230`: `device - 1 < 4`). The scan's `slot * 0x1000 + 0x21000` is the same address, so Linux `PCI_SLOT(devfn)` is the scan's `slot + 1`.

**Result.** For Linux device `d` on a PIC bus (valid 1 to 4), with `s = d - 1`:

| Config pin | Pin | PIC pin number (`irq_int_bit`, status bit, `+0x130 + 8n` register) |
|---|---|---|
| INTA, INTC | 1, 3 | `d - 1` |
| INTB, INTD | 2, 4 | `(d + 3) & 7` |

so device 1 INTA is pin 0 and INTB pin 4; device 3 INTA is pin 2; device 4 INTA is pin 3. INTA and INTC of a device share a pin, as do INTB and INTD. The `int_device` field for pin `n` is then written with `s`. This is the same as "PIC input = device - 1" for INTA, and the pins the MIPS Origin 350 capture reports (0, 2, 3 for the devices the Altix PROM would place at 1, 3, 4). Each PIC bus has its own register file (head 1 at `+0x80_0000`), so the eight pins are per bus and the rule is the same on both. On the IO9 and IO10 the PROM does not depend on the board: IOC4 at device 1 (pin 0), ISP 12160 or VSC 7174 at device 3 (pin 2), Ethernet at device 4 (pin 3) if the device placement is as the base I/O page states (inferred; the formula is established).

**What Linux reads.** `sn_io_slot_fixup` makes the call once per `pci_dev` (`v5.3:arch/ia64/sn/kernel/io_init.c`), takes `pdi_pio_mapped_addr[]` for the BARs and, in `sn_pci_fixup_slot`, uses the interrupt record only when `irq_irq` is non-zero (`v5.3:arch/ia64/sn/kernel/io_common.c`). It reads `irq_irq` (the device's `dev->irq`), `irq_int_bit` (`>= 0`: line interrupt, the pin number used as a bit index in `pcibr_target_interrupt`, `1 << bit`, and in `pcibr_force_interrupt`), `irq_bridge_type` (selects the provider and the lost-interrupt workaround, PIC only), and `irq_bridge`/`irq_xtalkaddr` through the `SN_SAL_IOIF_INTERRUPT` call. Established from the Linux source: `sn_check_intr` ANDs `irq_int_bit` itself, not `1 << irq_int_bit`, with the status byte, so the workaround never fires for pin 0 and tests the wrong bits for other pins; a model that wants Linux's lost-interrupt recovery to run should not rely on it for the IOC4 on pin 0. The kernel never computes a pin.

Not read: the EFI side's use of the record (`AltixPciDeviceInit`, `0x285f40` in the 10.54 EFI), the bridge rotation table at `0xffb43680`, and 10.40 (the 4.43, 5.04 and 10.54 images agree).

### Late error interrupt set-up (`0xffb6cef0`, bus provider `+0x88`, run by `IOIF_INIT` and the first `0x55`)

Short and read in full. Allocate irq `0x33` from the hub provider's `+0x28` (NASID at record `+0x102`, target and slice both all ones); a negative result prints "WARNING: pcibr_error_intr_init: Interrupt allocation failed!" and the code carries on with whatever the record held. Then: `+0x38` low 48 bits = the allocated record's address word (`0xffab57a0`, a read-modify-write that keeps bits 63:48), `+0x128` = the record's irq (`0xffabb4a0`); for a type-3 bridge only (a TIO, not this PIC) the eight per-pin address registers are initialised. Then `+0x108` (interrupt enable) is read, ORed with `0x7eff7ffefe00` and written (`0xffab9980`, `0xffab9c30`); for a PIC whose revision test passes (revision 1: bit 39 and bit 9 are cleared from the constant, `& 0xffffff7ffffffdff`) `+0x28` is first written `0x750`. A flush read of `+0x50` follows. The OR constant `0x7eff7ffefe00` and the two ANDs (`0xffffff7fffffffff`, then `-513`) were read in the listing (`0xffb6d0d6`, `0xffb6d1a6`, `0xffb6d1c0`); the `0x00003eff7ffffe00` constant in the audit notes at the end of this page belongs to a different binary and is not a conflict.


### Review (SAL runtime PIC attach and PCI scan)

Independent re-read on 2026-11-16 in the Ghidra decompiles of `pic_attach2` (`0xffb6d9c0`), `pcibr_slot_info_init` (`0xffb36020`), the configuration address helpers and the slot-device helpers (no IA-64 objdump was available; no listing was dumped for this runtime). At a model stop inside the leaf helpers `0xffa0e5a0` (load) and `0xffa0e640` (store), which run in a frame of two (`sof=2`), registers `r34` and above are out of frame and show stale values, so a register read there is not evidence.

**Confirmed.**
- Configuration address for bus 0: `W + 0x20000 + (device + 1) * 0x1000 + function * 0x100 + (register & ~3)`, with device = slot, so slot 0 is `0x21000` (the accessor returns a pointer and counts in 4-byte units). Type 1: `+0xc8` = `bus << 16 | device << 11` (8-byte store), then `W + 0x28000 + function * 0x100 + (register & ~3)`.
- Empty slot: the probe marks a slot in the valid-device mask (`+0xac`) when the protected read succeeds, and treats it as absent when the low 16 bits are `0xffff`; a failed read is absent and unmarked; nothing is printed. The header-type read (register `0xe`, one byte) tests bit 7 and then reads functions 1 to 7 (a bridge-type-3 record at revision 1 reads 1 only).
- Device IDs: IOC3 (`0x10a9`, `0x0003`) and IOC4 (`0x10a9`, `0x100a`) are accepted only in slots 0 to 2; slot 3 or more prints "ERROR: IOC3/IOC4 devices must be located in one of the first 3 slots of a pci bus" and the allocation fails. The IOC4 test in the probe calls the board-record helper. QLogic vendor `0x1077` with device `0x1280`, `0x1240` or `0x1216` gets response buffers (`0xffb33880`) from the provider method `0xffb3f810`, with "Unable to allocated RRBs for qlogic scsi" on failure. No other vendor or device constant occurs in the functions read.

## PIC widget space and PIO windows

Where a processor access to a PIC widget lands, per head. A PIC widget has two PCI heads in one widget address space: head 0
at widget offset 0, head 1 at `+0x80_0000` (the PROM's window pointer for head 1). Source: the SAL runtime's resource-to-Crosstalk
translation (`0xffb31010`, SAL_B of the 5.04 image, read in Ghidra and cross-checked with objdump) and the PCI scan above;
the XBridge address map is a sibling and fills no field. The public Linux 2.4 `include/asm-ia64/sn/pci/bridge.h` (`8ef7d46c94d5`) defines the
PIC layout in its own words: bus 1 at `PIC_BUS1_OFFSET` `0x800000`, configuration at `0x20000` + 4 KiB per device, device windows, and the PIC memory aliases
(`PICBRIDGE0_PIO32` `0x4000_0000` to `0x7fff_ffff`, `PICBRIDGE0_PIO64` `0x8000_0000` to `0xbfff_ffff`, `PICBRIDGE1_PIO32` `0xc000_0000` to `0xffff_ffff`,
`PICBRIDGE1_PIO64` `0x1_0000_0000` to `0x1_3fff_ffff`), with a comment citing the PIC programmer's reference (revision 0.8, not held) and saying PIC has no I/O alias.
Grades are **established** as the PROM's computation unless marked; the hardware decode is **established as a published-driver definition** where that header
states it (head 1 offset, the four aliases, no I/O alias, device-window sizes) and **inferred** elsewhere.

| Widget offset, head 0 | Head 1 | What the PROM uses it for |
|---|---|---|
| `0` to `0x1_ffff`, `0x8_0000` up | `+0x80_0000` | the register file and the external translation RAM at `0x8_0000` (small window) |
| `0x2_1000 + slot * 0x1000 + reg` | `0x82_1000 + ...` | type 0 configuration, `slot` 0 to 3, `reg + size` at most `0x100` per function (function `f` adds `0x100 * f`) |
| `0x20_0000`, `0x40_0000` | `0xa0_0000`, `0xc0_0000` | device windows 0 and 1 (2 MiB each): memory or I/O BARs the PROM allocated from the device's direct-window pool; I/O BARs are mapped only here |
| `0x60_0000`, `0x70_0000` | `0xe0_0000`, `0xf0_0000` | device windows 2 and 3 (1 MiB each), same rule |
| `0x4000_0000` + PCI address | `0xc000_0000` + PCI address | memory BARs outside the pools. The mapper takes this path when the range ends at or below 1 MiB, or starts at `0x70_0000` or above and ends at or below `0x3fff_0000`; PCI `0x10_0000` to `0x6f_ffff` is not served here. Head 1 uses `0xc000_0000` only on a part whose chip type is 2 |
| anything else | | unmapped: the mapper prints a failure. The PROM does not use the 64-bit aliases (`0x8000_0000` head 0, `0x1_0000_0000` head 1, defined by the public header) and there is no I/O alias; what the chip does there is **unknown** |

Reaching them from the SHub: widget offsets below 16 MiB (registers, config, device windows) go through the widget's small
window `w` (`0x8_0000_0000 | nasid << 38 | w << 24`); the `0x4000_0000` and `0xc000_0000` memory aliases need a big window,
so a PIC memory BAR is reached at `0x8_0000_0000 | nasid << 38 | n << 29 | (PCI address & 0x1fff_ffff)`, `n` being the big window whose ITTE the mapper set
([PIO windows](../shub_ii/README.md#pio-windows)). Example: widget 15, head 0, PCI memory `0x70_0008` is
`0x4070_0008` on the widget, ITTE offset 2, window-relative `0x70_0008`; the first mapping gets window 6, giving
`0x8_c070_0008` (the BAR address is read off a stop, **inferred**). Whether the alias is a 1:1 map of PCI memory and what
bits 31:30 of a device window's PCI address do (`Device(n)` window base) is **inferred** from the PROM's arithmetic only.
The Device-register window base is the bits-11:0 field in 1 MiB units above (`(window >> 20) & 0xfff`); it is the direct window the device-window rows above reach.

**Config space.** Offsets as above, 4-byte aligned words, no byte swizzle in the address (see the PCI scan section below);
the PROM issues only 4-byte config accesses, so 1- and 2-byte lane behaviour is not exercised there.

**Byte lanes and swap.** No held PIC source states the lane rule; the Bridge (rev 4.0) and XBridge (rev 0.5) specifications, appendix "Byte Swapping",
do for their own chips (siblings: **inferred** for PIC). Two separate controls: Device(n) bit 13 `dev_swap` swaps PIO through the device windows, and Control bit 22
`mem_swap` swaps PIO to PCI memory above widget space, which is the `0x4000_0000` alias. On a little-endian system those tables give lane identity with the bit
clear (the byte at address a on PCI byte lane a mod 4) and, with it set, a byte reversal inside the access width (2-byte `AB` becomes `BA`, 4-byte `ABCD` becomes `DCBA`); half-word and word
swapping are not offered. What the PROM does (**established**, `0xffb31010`, `0xffab4760`, `0xffab44a0`): per slot it clears Device bit 13, and a device-window mapping is refused for a request
carrying flag `0x1000` (byte stream). For the alias, a request with `0x1000` sets Control bit 22 and any other request clears it; the first alias mapping on a bus fixes the mode and a later
request for the other mode fails. Control bits 31:30 and 29 are the parity enables for the translation RAM, the response and the request path (`PIC_CTRL_PAR_EN_*`, established as names), not a lane rule. The IOC4 and
QLogic parts are driven with plain little-endian register accesses of their own size (EFI's 2-byte store of 5 at BAR + 8 is one). A model should
serve 1-, 2- and 4-byte accesses at the alias with identity lanes while Control bit 22 is clear, reverse them inside the access width when it is set, and leave the device
windows to Device bit 13 (the II adds no rule). Whether the PIC matches the sibling tables, and which flag the QLogic request carries, are **unknown**; the Bridge errata
list says Bridge's own `mem_swap` and `io_swap` did not enable the swapper on that part.

## PCI scan and the protected read (stop at `0xffb5cf50`)

Traced on snprom 10.54 (SHub 1) in Ghidra with the repository's IA-64 module, beside an objdump listing. Decompiler output is navigation; each claim below was checked against the listing or a constant.

**Which code runs it, and from where (established).** The scan belongs to the physical-mode SAL procedures, not to SAL_B's `main_three` and not to EFI's own code. EFI triggers it: the first `SN_SAL_IOIF_GET_HUBDEV_INFO` (`0x55`) or `IOIF_INIT` (`0x5f`) call reaches `0xffb2d450` (both ids, and `0x5e`, share the SAL handler `0xffb1e660`, which calls it at `0xffb1e99c` and `0xffb1f2bc`), then, through the bus-mapping code and a method table (the descriptor of `pic_attach` is at `0xffc4ad60`; the indirect call site was not located), the bus provider's `pic_attach` (`0xffb6d740`) and `pic_attach2` (`0xffb6d9c0`), which calls the slot probe `pcibr_slot_info_init` (`0xffb36020`) at `0xffb6e89c`. The read goes `0xffb36020`, `0xffb34860` (4 bytes), `0xffb351d0`, `0xffaeb170`, the protected-read wrapper `0xffb0f4b0`, and the sized-load leaf `0xffb5cf20`. Its `ld4` is at `0xffb5cf50`; `b0 = 0xffb0f740` is the return address in the wrapper.

**Order.** Bus 0 (window `W`) first, then bus 1 (`W + 0x80_0000`). Per bus, `pic_attach2` makes three passes over the slot range (probe and BAR sizing, BAR assignment, Device register), before its ioboard-type check. In the probe pass, per slot `s`: a protected 4-byte read of configuration register 0, function 0, at `W + 0x20000 + (s + 1) * 0x1000`. So slot 0 is `W + 0x21000`: the type 0 address helper `0xffabed10` adds 1 to the device number, and the PROM never reads `W + 0x20000`. If the vendor half is `0xffff` the slot is absent and nothing else touches it. Otherwise plain (unprotected) loads follow: the header type (register `0xe`, taken from a 4-byte load at `+0xc`), and, if bit 7 is set, protected 4-byte reads of register 0 of functions 1 to 7 at `+ 0x100 * f`. The three passes run slots 0 to 3 on both buses: `pic_attach2` stores the first and last slot (record bytes `+0xf0` = 0 and `+0xf1` = 3) at `0xffb6dc56` and `0xffb6dc90`, before any ioboard test, and each loop runs to `+0xf1` (established). The narrower ranges of the [attach section](#sal-runtime-pic-attach-and-pci-scan-pic_attach2-0xffb6d9c0) (another byte pair, `+0xe8` and `+0xe9`, set by the ioboard switch after the passes) only feed the response-buffer accounting. No type 1 cycles are issued on an Altix 350.

**The protected read (established).** `0xffb351d0` (alignment and size checked) brackets the read: `0xffb34720` clears bits 11 (`pci_master_tout`), 34 (PCI-X master timeout) and 44 (`pcix_split_emsg`) of the interrupt enable register `+0x108` (`0xffab9ee0` clears, `0xffab9980` reads, `0xffaba1a0` sets) and reports whether any was set. After the read it writes `+0x110 = 0x40` (multiple-error clear; `0xffaba460`), and re-sets those bits if they had been set (`0xffb347c0`). The wrapper `0xffb0f4b0` first registers a recovery entry (`0xffb5d040`): a table of 32 entries in a per-processor state block, code range `0xffb5cf20` to `0xffb5cf80`, resume address `0xffb5cf90`, protected by a lock it spins on for 100000 timer ticks (if the lock is not obtained the entry is not registered and the read runs unprotected; the result is ignored). It also writes the address to a per-CPU word at state `+0x5308` and clears PSR.i around the access if it was set. The leaf returns status 0 and the data on completion; the resume address returns status 1 and data 0, and the wrapper then stores all ones (`0xffffffffffffffff`) as the result whenever the leaf reports a fault.

**What a fault does (established for the handler path, inferred for the hardware).** A machine check takes SAL_B's check entry (`0xffa01020`, branching to `0xffa01080`, which saves state and calls `0xffa02ff0`). `0xffa07230` classifies it; with processor state parameter bits 9 (`us`) and 18 (`cm`) clear it calls `0xffa05610`, which compares the two saved instruction-pointer slots (min-state `+0x1a0` and `+0x1b8`) with each registered range. On a match it replaces them by the entry's resume address (clearing PSR.ri, setting the data-translation bit from the entry) and the handler reports the check as recovered, so the PROM resumes at `0xffb5cf90`. No match, or either bit set, takes the other paths of `0xffa07230` (not traced; treated as fatal). Therefore the PROM survives an unclaimed configuration read in exactly two ways: the read completes with the vendor half `0xffff` (a master-abort that returns all-ones), or it ends as a machine check delivered through PALE_CHECK. Any other exception type, or a model that halts on an access error, ends the boot at `0xffb5cf50`. The PROM does not read `+0x100` or `+0x170` after the read, and it prints nothing for an absent slot.

**Why the first read is slot 0 of bus 0 (established).** Slot 0 is the first slot of the range, and bus 0 is attached first. Which device sits there on a real machine is on [the base I/O page](../../platforms/sn2/altix-350-base-io.md#devices-on-the-pics-buses).

### What the PROM needs from the model

The PROM registers a recovery range because the read can machine-check; with a plain all-ones return it would not need one. The check path (`0xffa01020` to `0xffa02ff0` to `0xffa07230`, read in Ghidra again for this section) recovers only when all of these hold:

- the check is type 0 (a machine check, not an INIT);
- the processor state parameter (r18 at the SAL check entry, saved at record `+0x578`) has bit 9 (`us`, uncontained storage damage) clear and bit 18 (`cm`, corrected) clear. Bits named from `pal_processor_state_info_t` in Linux `arch/ia64/include/asm/pal.h`; the [earlier text](#pci-scan-and-the-protected-read-stop-at-0xffb5cf50) gave the numbers without names;
- either saved instruction pointer (`+0x1a0`, `+0x1b8`) lies in a registered range. `0xffa05610` then replaces it with the resume address and clears the restart-instruction bits of the saved status.

Another condition, PSR.ic clear at the fault with the bus-error assertion flag (`0x1_2001_0100` bit 3) set, rewrites the parameter to "uncontained" and ends in the unrecovered path. A hardware bus check on a normal read is not that. Nothing else in the check path reads the PIC; the PSP.mi bit (12) only makes SAL call `PAL_MC_ERROR_INFO` (`0xffa1d870(0x19)`) to fill its record, and a failure there does not stop recovery. A machine check has no ISR; PAL builds the parameter and min-state itself, so a model that raises the check must run the PAL_B code or hand SAL an equivalent state. What the Madison PAL puts in the parameter for a bus check from a hard-error response is unknown here.

### Model recommendation

Make the load take a synchronous machine check, with these effects:

1. PIC `+0x100` bit 11 (PCI mode) or bit 34 (PCI-X mode) set; `+0x170` shows the same bit; the PCI error address registers hold the configuration address. If the matching enable bit is set, the error interrupt fires, which the PROM avoids by masking.
2. A bus-check machine check, contained (`us` = 0, not corrected), reaching PALE_CHECK with the faulting IIP.
3. Writing `+0x110` bit 6 clears the view and multiple-error registers; leave the status bits alone unless the group-clear bits are written.
4. Leave the SHub II and processor-interface error registers unmodelled until a source names the SHub 1 ones: the 2.4 SN2 tree's `hubii_check_widget_disabled` reads SN1-style widget registers and was not shown to apply.

"All ones plus the PIC bits, no machine check" also boots this PROM (vendor `0xffff` is absent), but it takes a different path: the slot is marked in the valid-device mask (`+0xac`), which a faulted read never does. It also contradicts SGI's statement that a read gets a bus error. Treat it as an approximation, not the hardware behaviour.

### Not settled

- That a PIC returns an error response on the read rather than all ones with a latch: only SGI's comments and wrapper names say so.
- Whether `+0x100` latches with the enable clear, and whether anything clears bit 11 after the PROM's probes before the late error enable ORs bit 11 back in.
- The SHub 1 registers that record the failed read (II widget error, PI error detail) and the Madison PAL's parameter for it.
- A capture of one empty-slot read on an Altix 350 would settle all three; it needs the physical-test proposal the repository rules require.
