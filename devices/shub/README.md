# SHub (SN2 node controller), SHub 1 and SHub 2

SHub is the node controller of the Altix 3000 family and its successors (SGI's SN2 platform): one chip per node that joins one or two Itanium 2 processors and their memory to the NUMAlink fabric and to Crosstalk I/O. It is the Itanium counterpart of the Origin 3000's Bedrock, a different chip with different field positions and register offsets. The kernel for this platform distinguishes two generations, SHub 1 (Altix 3000) and SHub 2 (later Altix, up to the 4000 series), at run time. Register contracts are in [registers.toml](registers.toml) (SHub 1), [registers.shub2.toml](registers.shub2.toml) (SHub 2, an overlay on it, the way [bridge](../bridge/README.md) holds XBridge) and, for the I/O interface, [../shub_ii/](../shub_ii/README.md). Generated references: [registers.md](registers.md), [registers.shub2.md](registers.shub2.md). The SHub 2 firmware's view (address map, identification register, reset accesses, memory set-up): [shub2.md](shub2.md). The node address layout is [../../platforms/sn2/address-map.md](../../platforms/sn2/address-map.md); the firmware calls the kernel makes are [../../software/sal/README.md](../../software/sal/README.md).

**Mode: no-spec.** No SHub specification, PROM or SAL image is held, and none is public. Every fact here comes from SGI's own Linux platform code for SN2 (Linux v5.3: `arch/ia64/include/asm/sn/` and `arch/ia64/sn/`; the real-time clock driver at v4.9; the SN2 platform was removed in v5.4). That code is the vendor's software source: what it defines is **established** (an offset, a field position, a call sequence), what it implies about hardware behaviour is **inferred**, and what it leaves out is **unknown**. The only chip documents held are the Altix user's guides, which are not register specifications. Reset values are unknown throughout, except three register families the header names with an INIT macro (the RTC interrupt configuration and enable, and the comparators; graded inferred).

**PROM view.** The SHub 2 first-stage firmware (SAL_A, SAL 1.40 and 1.11) writes `SH2_IPI_ACCESS0` to 1 and `SH2_IPI_ACCESS1..3` to 0 at reset, among other registers the kernel header does not name: [software/firmware/snprom](../../software/firmware/snprom/README.md#shub-registers-the-first-stage-writes-shub-2-sal_a-established). `SN_SAL_GET_SN_INFO` in the SHub 2 build derives the NASID mask and shift from the register at `0x2_2011_0000` and the sharing-domain size from bit 54 of `0x2_1006_0f00` (established by reading the function). The SHub 1 build reads five bits (52:48) of `0x81_1006_0580` for the region size and returns mask 0x7ff, shift 38 as constants. Reads of these after the firmware ran are not reset values.

**PROM view, SHub 1 (SAL 5.04, inferred from reading and an interpreter trace of the image).** The PROM reads the chip identification at node offset `0x1_0000_0000` (revision bits 31:28, part number from bit 12; `0x4363` selects the first of four method tables, three other part numbers select the others and any further value calls through a null table) and the node id at `0x1_1006_0580` bits 42:32; programs the memory/directory block (offsets `0x1_0001_0000` to `0x1_0001_0078`, `0x1_0003_0200`, `0x1_0005_0200`, `0x1_0183_0200`, `0x1_0185_0200`, `0x1_0003_0400`, `0x1_0005_0400`) from the L1's DIMM data; and keeps firmware state in scratch words at `0x1_5003_1500` to `0x1_5003_1560` (progress history, a per-processor bit word, and the debug-switch word, the low 16 bits of which are the L1's DIP-switch reply; bit 11 makes the PROM skip NUMAlink discovery). The memory controller block is decoded for one DIMM set, the memory-test completion bits are bit 40 and bit 41 of `0x1_0002_0088`, and the block transfer engine's IBLS0 is at `0x8_01c1_0000` in the global window. Detail and gaps: [boot path](../../software/firmware/snprom/boot-sequence.md#memory-discovery-what-is-read-and-what-an-interpreter-run-of-the-image-shows). Every access from reset to the console start, with the value each read must return: [prom-reset.md](prom-reset.md). The memory bring-up registers, the memory-test engine's commands and poll, and what a device model must return to pass "Testing memory": [memory-init.md](memory-init.md). The interrupt delivery the PROM and the SAL runtime program and expect (`ipi_int`, `event_occurred`, the real-time clock comparators, the destination and enable registers), with every site, the vectors and delivery types, and what each read must return: [interrupts.md](interrupts.md).

**What the public header gives, and what it does not.** The register header, `shub_mmr.h`, defines about two dozen register names, not the hundreds a chip reference would. It is a subset the kernel needed: interrupt, clock, PIO write status, TLB purge and BTE registers, plus two memory/directory privilege vectors. There is no network interface register at all, no memory controller register beyond those two, no processor interface register beyond the few named, and no local-block register beyond the identification, clock and interrupt ones. Everything the PROM programs before the kernel starts is invisible in this source. This page covers what the kernel the source describes touches; a full register description of the chip needs more evidence ([questions/shub-registers-unnamed.md](../../questions/shub-registers-unnamed.md)).

## The functional units, as the header and code have them

The header does not say which unit holds a register. The unit named below is inferred from the register's name prefix and its address block (bits 31:28 of the offset, which differ by name family: 0x0 memory/directory, 0x1 local block, 0x2 processor interface on SHub 1).

| Unit | What the sources show | Registers |
|---|---|---|
| Processor interface (PI) | PIO write status, one per processor slice; CRB CAM access control (SHub 1 only) | `pio_write_status`, `pio_write_status_alias`, `pi_cam_control`; TLB purge registers (`ptc`) are in the local-block address block but act on the processor side (inferred) |
| Memory and directory (MD) | two privilege vectors named for the "DQLP" and "DQRP" queue ports, no use by the kernel | `md_dqlp_dir_privilege_vector`, `md_dqrp_dir_privilege_vector` (SHub 1) |
| I/O interface (II) | the Crosstalk port, access protection, the CRBs and two block transfer engines on SHub 1 | [shub_ii](../shub_ii/README.md); on SHub 2 the BTEs move to their own block (below) |
| Network interface (NI) | the LLP link registers and flow limits the PROM sets before memory discovery, one-node values in [prom-reset.md](prom-reset.md#the-ni-port-set-up-before-memory-discovery-0xffa483d0-and-slot-55-0xffa5d850) | `ni_llp_stat`, `ni_llp_reset`, `ni_llp_reset_en` (the partition fence, [prom-reset.md](prom-reset.md#partition-fences-0xffa51200-intcon_pttn_erect_reset_fences)), `ni_llp_chan_mode`, `ni_llp_config`, `ni_llp_test_ctl`, `ni_llp_err`, `xnni*_link_flow`, `xnni_*_flow`; router and vector-route registers unknown |
| Local block (LB) | identification, interrupt event and send, IPI access, the real-time clock and its comparators | `shub_id`, `event_occurred`, `ipi_int`, `ipi_access`, `rtc`, `rtc_int_*`, `int_cmp` |
| Junk bus | four LED registers; a UART whose interrupt is an event bit | `junk_bus_led` |

## Telling SHub 1 from SHub 2 at run time

- **Firmware tells the kernel (established).** At start-up each processor calls (the boot processor twice, early and again after platform setup) the SAL entry `SN_SAL_GET_SN_INFO` and stores the answer: bits 7:0 of the first result are 0 for SHub 1 and 1 for SHub 2 (comment in the SAL header). The kernel's `is_shub1()` and `is_shub2()` read that field; every chip-specific choice below branches on it. The same call returns the NASID mask and shift, the system size, the sharing-domain size, the partition and coherency ids and the region size ([SAL page](../../software/sal/README.md)).
- **Fallback (established).** If the PROM does not implement the call the kernel assumes SHub 1 with a fixed NASID layout and reads the nodes-per-bit field of the SHub 1 identification register for the region size. Nothing checks the identification register to decide the chip type.
- **Registers the generic names hide (established).** Many registers have a generic name (`SH_IPI_INT`) that the header defines as a run-time choice between the `SH1_` and `SH2_` constant (`is_shub2() ? SH2_x : SH1_x`). The header comment says there is "a small performance penalty" and tells hot paths not to use the generic names; the kernel keeps chip type, address shifts and the PIO status address in per-processor data.
- **Names for monitoring (established).** The performance and topology code reports a node as "SHub 1" or "SHub 2.x" by string, and recognises SHub 2 nodes by the prefix `SHub 2.`; the string comes from firmware, so it does not give a register-level test.
- **Revision (established for SHub 1 only).** The identification register's revision field is read only on SHub 1, to find chips of revision 2 or lower ("SHub 1.1") that need workarounds. The header names no SHub 2 identification register.

## What differs on SHub 2 (from the kernel's branches)

| Item | SHub 1 | SHub 2 |
|---|---|---|
| Register offsets | `SH1_` set in [registers.toml](registers.toml) | `SH2_` set in [registers.shub2.toml](registers.shub2.toml): mostly the SHub 1 offset minus 0x1_0000_0000, the clock 0x2_101c_0000 |
| Local and global MMR windows | 0x80_0000_0000 and 0x8_0000_0000 | 0x2_0000_0000 and 0x3_0000_0000 ([address map](../../platforms/sn2/address-map.md)) |
| Processors per node, as the PIO status table implies | 2 (slices 0 and 2) | up to 4 (slices 0 to 3) |
| PIO write status | two registers; idle when the count field reads all ones | four registers, slices mapped to instances 0, 2, 1, 3; idle when the count is zero; the recovery code reads the alias instead of writing 7 to it |
| TLB purge (PTC) | two registers per node written back to back; region id and address in data | one register per node; region id added to the address; address in the data |
| BTE | two engines inside the I/O interface, started by writing length then control | four engines in their own block; one store to the control register starts a transfer with busy, mode and length together; six-bit error code in the status |
| Interrupt events | bits 20, 24 to 26, 28, 29, 30 | adds bits 33 and 34 (external I/O interrupts 2 and 3) |
| Workarounds | SHub 1.1 (revision 2 or lower): PI CAM write on every timer tick, a global lock round IPI stores; lost-interrupt check from the timer for PIC | none named ("none yet" in the kernel) |
| Cached-address requirement for cache flush | the flush needs a cached address (uncached ones are converted) | not needed |
| Error handling | hub error interrupt: PROM call, then CRB scan in the kernel | PROM call only for TIO errors; BTE errors handled by the kernel through a PROM BTE recovery call |
| CPU disable | not supported | the kernel sends all error interrupts to the boot processor when the PROM advertises CPU disable support (a PROM feature bit) |
| AMO cache | none | the kernel flushes four AMO lines through a scratch page before a BTE zero fill |
| IA-64 simulator I/O base | `0xc0000087cc000000` | `0xc00000028c000000` |

The SHub 2 contract is therefore thinner than SHub 1's: its offsets for the SHub 1 registers come from the same header, and what the header adds for SHub 2 alone is the purge register, the four BTE engines' four registers, two more PIO write status instances and three more IPI access registers; and the II block's layout on SHub 2 is not given (the kernel uses neither the II registers nor the CRBs on SHub 2 except through firmware).

## Interrupts and IPIs

- **Sending an IPI (established).** The sender stores one 64-bit message to the target node's `ipi_int` register: send bit, target processor id (the id the processor's SAPIC holds), a type (0 interrupt, 2 platform management interrupt, 4 NMI, 5 INIT), a vector, and a constant base. The store is an uncached physical-mode `st8.rel` after a memory barrier. On a SHub 1.1 the kernel serialises under a global lock: it takes the lock, makes the store, waits for the PIO write status to drain, then drops the lock. The receiving processor sees an ordinary external interrupt with the given vector; the event register shows `ipi_int` (bit 28) pending until cleared.
- **Pending events and acknowledge (established).** The interrupt acknowledge reads the event register, ANDs it with the mask of the bits it manages (junk-bus UART, IPI, II 0, II 1, and on SHub 2 the two external I/O bits) and writes the result to the alias register. The RTC comparator bits (24 to 26) are not in that mask; the clock driver clears them itself through the alias. The header's mask lists the II 1 bit twice and leaves out nothing else; harmless.
- **Processor id layout (established as a fallback).** For an old PROM the kernel decodes a processor id as NASID in bits 11:0, slice in bits 13:12 and the subnode in bit 13; the code that does it contradicts itself on the subnode bit, so only the NASID field is firm. The normal path asks SAL (`SN_SAL_GET_SAPIC_INFO`).
- **Vectors the platform reserves (established).** XPC activate 0x30, II error 0x31, crossbow error 0x32, PCI ASIC error 0x33, ACPI SCI 0x34, TIOCA error 0x35, TIO error 0x36, TIOCX error 0x37, RTC comparator timer 0x38, then device vectors 0x3c to 0xe6, XPC notify 0xe7, UART 0xe9.
- **Device interrupts (PIC established from the 2.4 kernel; firmware and TIO unknown).** How a bridge interrupt reaches a CPU is set up by firmware (`SN_SAL_IOIF_INTERRUPT`: allocate, free, redirect); the kernel never programs the bridge-to-SHub path itself and keeps only what firmware returns (`sn_irq_info`: target node and slice, the Crosstalk address the bridge writes to). For a PIC the address names `SH_II_INT0` or `SH_II_INT1` (`0x1_1000_0000`, `0x1_1000_0100`) of the target node, as the 2.4 SN2 kernel built it; see [interrupts](interrupts.md#where-a-pic-interrupt-lands-on-shub-1). What the firmware's own allocator builds, and the path behind a TIO, are not read.
- **Lost-interrupt check (established).** On SHub 1 the timer interrupt scans the PIC interrupt status every hundred ticks and forces an interrupt for a pin whose status bit is set but whose vector is neither pending nor in service. The kernel comment says only PIC bridges need this, because bridges attached to a TIO do not target the SHub's interrupt registers: so a PIC interrupt is a store into a SHub interrupt register (established as the comment's statement; which register, see below).

## Real-time clock and comparators

A 55-bit free-running counter at `rtc` (clock source, delays, user-mapped by the clock driver). The frequency is not in a register: the kernel asks firmware (`SAL_FREQ_BASE`, the generic SAL real-time clock query), and if that fails guesses 1,000,000,000,000 / 30,000 (about 33.3 MHz). Three comparators (`int_cmp` B, C, D) fire an interrupt when the counter reaches the compare value; each has a configuration register (same layout as the IPI message) and an enable. The clock driver programs them in the order: disable, set compare to all ones, clear pending, write configuration, enable, write expiry. A fourth comparator exists and is "used by SAL" (driver comment).

## TLB purge

`ptc` makes the SHub purge a translation range on all processors of a node (**inferred** from the name "purge translation cache"; the kernel's use is the only evidence). The kernel's use is the global TLB flush on SN2: for each node that has a processor running the address space it does the register stores, waits for the PIO write status to drain, and recovers from a deadlock by repeating the stores one node at a time in physical mode. The local node uses the processor's own global purge instruction on SHub 1. On SHub 1 the purge uses two stores per page (control word, address word); on SHub 2 one store (address and region id in the address). After every group of up to 32 (SHub 1) or 7 (SHub 2) nodes it waits for the write count to drain; on a deadlock indication it drops to one node per group. The hardware's purge behaviour (does the SHub issue the purge in the local node's processors too, is it acknowledged) is **unknown**.

## PIO write ordering

PIO writes from different processors of a node are not guaranteed to reach a target in order (kernel comment on task migration); the memory-mapped I/O barrier is to spin on the processor's PIO write status until the count shows idle. This is why the status register is meaningful, not constant: idle reads as the value the kernel waits for (all ones for the count field on SHub 1, zero on SHub 2).

## Block transfer engines on SHub 2

Four engines, one per interface, at 0x30040000 + engine x 0x10000: control and status, then source (+0x80), destination (+0x100), notify address (+0x180). The kernel writes source, destination and notify address, then one 64-bit store to the control register with busy (bit 20), mode (shifted left 24) and the length in cache lines. Completion is written to the notify address like on SHub 1. Errors appear as a six-bit code in bits 41:36, which the kernel decodes both from the control and status register (error handler) and from the notification word the engine writes (`bte_copy`); inferred. The kernel's names for the bit values are 0x1 short response, 0x2 long response, 0x4 (the kernel's name is RESP_DSP), 0x8 access, 0x10 CRB timeout and 0x20 NACK limit. When the field is non-zero the kernel's status decode treats the transfer as failed and ORs the error flag in itself. Source, destination and notification addresses are written in the network address form ([address map](../../platforms/sn2/address-map.md)). Error recovery asks firmware to reset the BTEs (`SN_SAL_BTE_RECOVER`).

## Junk-bus window at 0x7_ff80_0000: the PROM flash

Local offset `0x7_0000_0000 + a` is the PROM space: the processor's 32-bit compatibility address `a` (established: Linux 2.4 `prominfo_proc.c`, `LB_PROM_SPACE` 0x7_0000_0000 "Local LB PROM", FIT pointer rebased by that constant; SAL 5.04 PROM image at `0xffa0_0000` is at `0x7_ffa0_0000`: the image's FIT pointer at `0xffff_ffe0` is `0x8000_0000_ffa0_0000`, and the kernel rebases its low 36 bits by that constant; the image starts with the FIT signature). The kernel reads that pointer at node offset `0x6_ffff_ffe0` (`LB_PROM_SPACE` minus 32), one 4 GiB window below the top of the `0x7_xxxx_xxxx` space; whether the flash decodes both is unknown (software expectation), so a model should answer that read from image offset `0x5f_ffe0` too. The junk-bus LED and UART rows sit in the same space below the flash. `0x7_ff80_0000` is flash byte 0, the lowest 2 MiB below the 6 MiB PROM image (inferred: the driver's size constant `0x800000` at `0xffacf050` is 8 MiB, and `0xffaceb80` fails the probe when the CFI size, `1 << word 0x27`, is under `0x800000`). The image then sits at flash offset `0x20_0000` (`0x7_ffa0_0000` minus `0x7_ff80_0000`); the PROM log (sectors 0 and 1) and the EFI store (sectors 16 to 31) are both below it.

- **What it is (established, SAL 5.04 `shub1snprom.bin`).** An AMD-command-set CFI flash driver on 16-bit words. Open (`0xffacea70`) builds the base `0x8000_000f_ff80_0000 | nasid << 38` (`0xffaceaa6`; bit 35 is the kernel's global-MMR selector, so the node offset is `0x7_ff80_0000`). The one flash store is `st2.rel` at `0xffad0da0` (`0xffad0d80`, word index times 2; `0xffad0dd0` is the byte-offset twin). Callers: reset `0xf0` at word 0 (`0xffad22b0`); autoselect `0xaa`@0x555, `0x55`@0x2aa, `0x90`@0x555 (`0xffad0e20`); CFI query `0x98`@0x55 (`0xffad0de0`); program `0xaa 0x55 0xa0` (`0xffad0fa0`); erase `0xaa 0x55 0x80 0xaa 0x55` then `0x30` at the sector (`0xffad0ec0`, `0xffad287c`).
- **Probe (`0xffad22f0`, established).** reset; autoselect, read word 0 (manufacturer, kept, not compared); reset; autoselect, read word 1 (device, kept, not compared); reset; `0x98`@0x55, then words 0x10 to 0x12 must be `0x51 0x52 0x59`, word 0x13 `2` and word 0x14 `0` (the command-set code 0x0002; the decompile tests it equal to zero), word 0x28 passing `(x + 1) & 2` (the decompile; this admits more than 1 or 2 and is unverified without the instruction listing), word 0x2c at most 4; geometry from words 0x27 (size `1 << n`), 0x2a and the erase regions from word 0x2d (stored in reverse order); reset. Any miss returns -1. The wrapper `0xffaceb80` then fails the probe if the size is under 8 MiB.
- **Reads (established).** 16-bit `ld2.acq` in the probe and polls; bulk reads are aligned 8-byte `ld8.acq` (`0xffad1640`) with the bytes handed one at a time to a callback descriptor; `0xffc4d690` is a table of descriptors whose first entry, `0xffad2920`, stores the byte (a 28-byte read is four loads at +0, +8, +16, +24; which op reaches `0xffad1610`, which has no direct caller, was not resolved).
- **The first access in a boot (inferred chain).** The first `0xf0` is the probe's (`0xffad22b0` from `0xffad22f0`). Statically its caller is `0xffaceb80` (call at `0xffacebd0`), reached from the node-ops method `0xffacf1b0` (call at `0xffacf1d0`; slot +0x40 of the table at `0xffbd7c58`) and from the erase-top function `0xffacf050`; the log open wrapper `0xffad6b30` calls through that slot. Which boot caller runs first was not traced. After `0xf0` the PROM reads the PROM-log header: 28 bytes from sector `(base + n) << 16`, n = 0 then 1 (`0xffadb3c0`, from log init `0xffadbe30`; base 0 stored at `+224`, `0xffadbe90`). A header is valid when its dword at byte 16 is `0x504c4f49` (bytes `49 4f 4c 50`); with neither valid the init returns -2. The log open (`0xffad67c0`, flags in its fourth argument) prints "PROM log appears uninitialized (see initlog command)" (`0xffad6a86`) only if flag 4 is set and flag 1 is clear, then returns -2; with flag 1 set it goes on to `0xffadc090` and initialises the log (writes flash), as the operator's clear-log command (`0xffb0b1c0`, flags 5) does. Both valid: the larger dword at byte 24 wins and a tie keeps header 0. The EFI variable store is later in the same flash: the checksum and sync code (`0xffaf6d10`, `0xffaf6640`) read 64 KiB blocks from sector 16 to 31, offsets `0x10_0000` to `0x1f_ffff`.
- **What a model returns (inferred).** Accept 16-bit stores. Erased data (`0xff` everywhere) takes the uninitialised-log arm and gives no CFI answer. Boot is not stopped there as far as traced: the log lookup wrapper `0xffad6e30` (about 40 callers) gets -2 from the open, and then either calls the default-value fallback `0xffad6640` or clears the caller's buffer and returns the error; what each caller does with that error was not traced. For the probe, answer the CFI query as above after a `0x98` write and leave read-array after `0xf0`.
- **Other junk-bus devices (established as absent from the PROM's SAL_B immediates).** Only the UART `0x7_fed4_0000` (`0xffa942d6`) and the LED rows (`0x87fed10000`, `0x87fed30000` in a table at `0xffc4e886`). `0x7_ff00_0000` and `0x6_ffff_ffff` at `0xffa32506` are an address-class test, not accesses. PAL_B holds `0x7fc400000` and `0x7fff00000` immediates, not read.


### Review

Independent review of this section at chips commit ec6f28e, by a reviewer who did not write it. Ghidra (IA-64 processor, `--sn2-prom --no-analysis`) decompiled the functions named below; the instruction listing was not available (the host `objdump` has no IA-64 and the container one did not start under load), so conditions read only from the decompile are marked. Linux 2.4 `prominfo_proc.c` and `sn2/addrs.h` read from the Linux/MIPS tree at 8ef7d46c.

**Confirmed.**
- `LB_PROM_SPACE` 0x7_0000_0000 and the FIT rebase; `GLOBAL_MMR_SPACE` has bit 35 set, which explains the extra bit in the flash base.
- Image at flash offset 0x20_0000: the image's qword at `0xffff_ffe0` is `0x8000_0000_ffa0_0000`, the kernel's mask and offset give `0x7_ffa0_0000`, and image byte 0 is the FIT signature the kernel compares. The 8 MiB extent is hard-coded in `0xffacf050` (sectors from `(0x800000 - n) >> 16` to 128).
- One store (`0xffad0d80`, word index times 2); reset, autoselect, CFI, program and erase sequences, the 0x30 at `0xffad287c`, and the probe order. Manufacturer and device words are stored at +8 and +0xc and not compared in the probe; other readers of those fields were not searched.
- Promlog header: 28 bytes from sector `((base + n) & 0xffff) << 16`, base the literal 0 from `0xffad67c0`, magic at byte 16, sequence at byte 24, -2 when neither is valid, "Error reading header" with -1 on a read failure. EFI store: `0xffaf6d10` and `0xffaf6640` loop sectors 0x10 to 0x1f in 64 KiB reads (the sync also erases and writes).

**Changed.** Word 0x14 must be zero (the page said non-zero); the CFI size is compared (at least 8 MiB, in `0xffaceb80`); `0xffc4d690` is a descriptor table, not a single callback; the flash base digits were mis-grouped (`0xf_ff80_0000`); the FIT pointer is read at `0x6_ffff_ffe0`; the uninitialised-log arm and the first-`0xf0` chain are now written down.

**Grades.** Flash base, sequences, probe words and log header layout: established (software expectation from shipped firmware by address). Image at offset 0x20_0000: inferred (base, size and the FIT rebase agree; no direct access seen). Word 0x28 test and the 0x6_ffff_ffe0 alias: unverified. Which op reaches the bulk read `0xffad1610`: unknown (the table at `0xffbd7c58` has a compare at +0x70, not a read). What callers do with -2: not traced.
## Unknown
