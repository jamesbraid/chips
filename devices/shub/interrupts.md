# SHub 1: the interrupt delivery the SAL 5.04 PROM and its SAL runtime program and expect

What `shub1snprom.bin` (SAL 5.04, banner "SGI SAL Version 5.04 rel081111 IP41", package snprom-10.54-70399, sha256 `51ccf9ad830b85ee6c88d6d73d2512322a86454e63db51c57454679283a34617`, 6 MiB at `0xffa00000`) and the SAL runtime component it carries do with the SHub 1 interrupt registers: which ones they write and in what order, which messages they send, what reaches a processor, and what each read must return. It is written so that a model of SHub 1 interrupt delivery can be built from this page and the generated register header alone. Neighbouring pages: the chip is [README.md](README.md), the register file [registers.toml](registers.toml), every register access from reset to the console start [prom-reset.md](prom-reset.md), the memory bring-up [memory-init.md](memory-init.md), the boot path [boot-sequence.md](../../software/firmware/snprom/boot-sequence.md), and the SAL calls the kernel makes [software/sal](../../software/sal/README.md).

**How this was read.** All reading of the PROM went through Ghidra with the IA-64 processor module of the retools checkout (`--ghidra-export ... --sn2-prom`): its function recovery, its call graph (the callers and call sites below) and its decompiled C of the SAL_B routines named. Every address constant, width, direction and value quoted was then checked against a binutils `ia64-linux-gnu-objdump -z` listing of the same bytes; the decompiler is navigation, the listing is the check. Two limits follow from that. Ghidra's import leaves the packed components (the SAL runtime, EFI) as data, so the runtime was read as listings of its expanded ELF (image offset `0x252000`, 918,824 bytes, with its dynamic symbol table); where SAL_B carries a copy of a runtime routine with the same instruction sequence (matched on the first 20 instructions), the Ghidra reading of the SAL_B copy is the reading of both, and the runtime site is listed beside it. Ghidra's function recovery missed three routines (`0xffa21470` the external-interrupt dispatcher, `0xffa23fb0` the error handler, `0xffa239a0` the error-pending test); those, the PTC and PIO status routines (`0xffa95c20`, `0xffa24ac0`, `0xffa24cc0`; the export runs for them were killed before they finished) and the whole runtime are read from the listing only, and the runtime sites are listed with their SAL_B copies. And Ghidra follows direct calls only, so everything reached through the chip's method tables or other function pointers has no recovered caller; this page says so wherever it matters.

**Grades.** *established*: the instructions, address constant, width and direction were read in full at the site named. *inferred*: a role or hardware behaviour reasoned from that code, with the reasoning given. *unknown*: not settled; the route that would settle it is named. A **software expectation** is something the PROM code needs the hardware to do. It says what a model must provide, not what the silicon does. Linux names are from `arch/ia64/include/asm/sn/shub_mmr.h`, `intr.h` and `arch/ia64/sn/kernel/{irq,setup}.c`, `sn2/{sn2_smp,timer_interrupt}.c` at v5.3, and `drivers/char/mmtimer.c` at v4.9 (v5.3 no longer has it). Where Linux has no name, the register is called by its address; those names are ours. The register names the PROM's own register-name table carries are given after an offset where Linux has none (the table lists names in offset order; pairing a name to an offset is inferred from that order, and the table's field encoding was not decoded).

**Site notation.** "site 0x..." is an address in the PROM image: `0xffa0....` to `0xffc4....` is SAL_B (SAL_A is `0xffc4e000`), and "runtime +0x..." is an offset in the expanded runtime ELF, with the symbol the ELF carries. A register is named by its offset in the node's register space (`0x1_1000_0380`); the PROM reaches it as the **global window** `0x8_0000_0000 + (nasid << 38) + offset` (bit 63 set, uncached) or the **local window** `0x80_0000_0000 + offset`. Every access is a 64-bit `ld8` or `st8` followed by `mf.a` (SAL_B `0xffa0e5a0` load, `0xffa0e640` store; runtime `chipset_load_mmr`, `chipset_store_mmr`).

## What a model has to do, in short

1. **Reset to the console start needs no interrupt delivery.** On the direct call paths from the SAL_B reset entry and `main()` (`0xffa19a20`) to the `sysctl_init` call (the L1 start, `0xffa19c0c`), the only code that touches an interrupt register is one routine (site 0xffa0b9a0, two alias writes), called from the node-object read `0xffa0bd20` (call at `0xffa0bf3c`) on its other-node branch before a request to another node's registers is sent; the single-node chip-identification read takes the local branch of that routine and never reaches it ([prom-reset.md](prom-reset.md), A39). SAL_A touches none of these registers. A model that keeps `ipi_int`, `event_occurred`, the RTC comparator registers and the registers in [the destination table](#destination-and-enable-registers-the-prom-programs) as plain storage lets the PROM reach the console. This is a search result over recovered direct calls, not a trace: [searches](#searches-behind-the-negative-claims).
2. **After the console start the PROM does use interrupt delivery**, in these places: a drain-and-replay of pending interrupts (second reset path), the wake-up of the other processors (`main_two`), the machine-check and INIT rendezvous, platform management interrupts (PMI) for errors, a timed "bus error" assertion through the RTC0 comparator, and the SAL calls that reset or flush. Each is a store to `ipi_int` or to a comparator whose result must arrive as an interrupt at the processor named in the message.
3. **A store to `ipi_int` with bit 63 set must deliver the message** (type, vector, target processor) to the processor named, including when the target is the sender: the PROM raises interrupts on itself this way and then reads `cr.ivr` or `cr.irr` (software expectation, established at the sites below). The base field is not needed (the PROM leaves it zero; Linux writes `0xfee`).
4. **Nothing in the PROM reads `ipi_int`, the alias, any comparator or the destination registers back** (reads of the comparator configuration are the one exception: [RTC](#real-time-clock-comparators)). Reads of `event_occurred` are limited to the sites in [that section](#event_occurred-and-its-alias).

## Processor id and message layout the PROM uses

Established from every site that builds an `ipi_int` value or a destination: the processor id carried in the `pid` field (bits 19:4 of the message) is the 16-bit value in bits 31:16 of that processor's `cr.lid`, and the PROM composes and decomposes it as

| pid bits | field | source in the code |
|---|---|---|
| 6:0 | low 7 bits of the NASID | `chipset_get_nasid`, `extr 0..6`; the same bits of `cr.lid` bits 22:16 |
| 10:7 | processor slice, 4 bits | `cr.lid` bits 26:23 (`extr.u cr.lid,23,4`) |
| 15:11 | NASID bits 11:7 | `cr.lid` bits 31:27 |

The target node of a message is not in the message: the PROM adds `nasid << 38` to the address it stores to, where nasid is rebuilt from the same pid fields (bits 6:0 of pid, then bits 15:11 shifted to 11:7). The message is the Linux layout: send bit 63, `idx` (vector) bits 59:52, `base` bits 49:21, `pid` bits 19:4, `agt` bit 3, `type` bits 2:0 (types seen: 0 external interrupt, 2 PMI, 5 INIT). Linux's text says the agent bit "must be zero for SHub"; the PROM sets it once ([BERR](#real-time-clock-comparators)). Linux's fallback decode of a processor id (NASID in bits 11:0, slice in 13:12) disagrees with all of the above; the PROM decode is established from the code and the Linux fallback is not used by this PROM.

## `event_occurred` and its alias

Linux: `SH1_EVENT_OCCURRED` `0x1_1001_0000`, `SH1_EVENT_OCCURRED_ALIAS` `0x1_1001_0008`. Bits Linux names: 20 UART, 24 to 26 RTC comparators 1 to 3, 28 IPI, 29 and 30 I/O interface 0 and 1. The kernel reads the register, ANDs with `SH_ALL_INT_MASK` (bits 20, 28, 29, 30) and writes the result to the alias (`sn_ack_irq`, established); the clock driver writes a single comparator bit to the alias to clear it (`mmtimer_clr_int_pending`, established). Not found anywhere in SAL_A, SAL_B or the runtime: a read of bits 20, 24 to 26, 28, 29 or 30, a write to the alias of bit 28 (IPI), or any use of `0x1_1001_0080` other than writing its alias at `+0x88` (above). The PROM's register-name table lists four names for the four offsets `0x1_1001_0000`, `+8`, `+0x80`, `+0x88`: `SH_EVENT_OCCURRED`, its `_ALIAS`, `SH_EVENT_OVERFLOW` and its `_ALIAS` (pairing by table order: inferred). So `+0x80` is probably an overflow word with its own clear alias at `+0x88`; the PROM writes 8 to the alias and never reads or writes `+0x80` itself.

**What the PROM tolerates, and the reset value.** *Unknown.* No document held and no code settles it: Linux defines `_INIT` macros for the comparators and their enables only. What the PROM tolerates: before the console start nothing reads the register. `shub_error_interrupt_config` programs the error destinations and enable masks first, then reads the register and clears `event & 0x7ef` (`0xffa30b40`), so error bits set from reset are cleared there without having raised an interrupt through the freshly programmed destination (they may have been latched before it; the order is the code's). Bits outside `0x7ef` are never looked at by a PROM read except bit 21. Zero is the simplest model; any value is tolerated except bit 21 set when the INIT path reads it.

**What a read must return.** Bits are pending flags: each stays 0 unless the modelled source asserts it. A write of ones to the alias clears exactly those bits (inferred from the PROM writing back exactly what it read, and from the single-bit clears; neither Linux nor the PROM reads the alias). A write to the primary register sets the bits written (inferred, above); a model that ORs the written value in satisfies both uses. Bit 21 must read 0 for the INIT path to proceed to the comparator test.

## Real-time clock comparators

Linux (v4.9 `mmtimer.c`): comparators RTC1, RTC2, RTC3 with config `0x1_1000_1480 + 0x100 n` (message layout, bits 59:52 vector, 19:4 pid, type 0), enable `0x1_1000_1500 + 0x100 n` (bit 0), compare `0x1_101b_0080 + 0x80 n` (55 bits), events 24 to 26. The driver programs each as: disable, compare ← all ones, clear the pending bit through the alias, write config, enable, write the real compare value. The comment in the driver says "RTC0 is used by SAL"; the PROM confirms it, with unnamed (in Linux) registers at the same stride: config `0x1_1000_1380`, enable `0x1_1000_1400`, compare `0x1_101b_0000` (the PROM's name table lists the three as the RTC0 interrupt configuration and enable and the first compare register; inferred pairing).

**RTC0, used by SAL_B and the runtime for a delayed "bus error" assertion** (SAL_B `0xffa318a0`, runtime `plat_assert_berr`; the argument is a delay in microseconds):

1. read-modify-write `0x1_2001_0100`, OR 8 (bit 3);
2. if the delay is zero, store the immediate `ipi_int` message to the local window instead and stop (table above); otherwise (in the simulator-marker case `cpuid[2] == 0xaeeeeeee8badbeef`, the delay is forced to 1):
3. write `0x1_1000_1380` ← `pid << 4 | 8` (type 0, agent bit set, vector 0, base 0, no send bit);
4. read the tick period in nanoseconds (`0xffa0da00`, `10 * (f + 1)` from `rtc_ctl`, see [prom-reset.md](prom-reset.md#the-real-time-clock)), read the counter `0x1_101c_0000`;
5. write `0x1_101b_0000` ← counter + (delay * 1000) / period;
6. write `0x1_1000_1400` ← 1.

The undo (`0xffa31d20`): clear bit 3 of `0x1_2001_0100`, write `0x1_1000_1400` ← 0, write `0x800000` to the event alias. Order differs from Linux's: the PROM writes the configuration, then the compare, then the enable; it does not first set the compare to all ones. Established for all of it; the roles ("bus error", the agent bit meaning, bit 23 as RTC0's event) are inferred. A model should fire the configured message when the free-running counter reaches the compare value while the enable is 1, and set the event bit; whether a compare below the counter fires at once or only on equality is **unknown** (Linux's `mmtimer` retries "on interval retry", suggesting it can be missed).

**RTC1 to RTC3 are only read by the PROM** (`0xffa316d0`, called from `0xffa0299c` in `0xffa02710`): for each pair it reads the configuration and tests that the type (bits 2:0) equals 5 (INIT), and if so reads the enable and tests bit 0; the result is "an OS comparator is armed to deliver INIT". Established (instructions); inferred (purpose: a watchdog the OS armed). **Must return** what was written, with zero from reset: type 0 or any value other than 5 means "not armed". Linux always writes type 0 and so never trips it. If a model returns type 5 with the enable set the PROM sends INIT to every other processor (below).

The counter's reads and the period register are as in [prom-reset.md](prom-reset.md#the-real-time-clock); the PROM's `chipset_rtc_time` and Linux's clock read the same 55-bit counter.

## The INIT and machine-check path

`0xffa02710` (called from `0xffa029d0` and `0xffa02ff0`; the latter also calls the rendezvous routine, which is why this is read as part of the machine-check and INIT handling: inferred), in the order Ghidra shows: fetch the per-processor SAL record; return if its field at +0x18 is zero or `0xffa03e50` returns 0; test whether the interrupt vector in the record at +0x80 is pending (`0xffa100e0`); call `0xffa03930`; if that succeeds and event bit 21 is **clear** (`0xffa314f0`) and any of RTC1 to RTC3 is armed for INIT (`0xffa316d0`), send INIT to every other present processor (`0xffa04ae0`); then continue to the SAL return call `0xffa35e10`. The instruction-level reading of `0xffa03930` and `0xffa03e50` was not done. `0xffa02c20` does the converse: if bit 21 is set it clears it through the alias and continues. What bit 21 means is **unknown** (Linux names no bit 21; the PROM's name table has several unrelated candidates); its role here is "an INIT-class event is already being handled". Established (control flow); inferred (the reading of bit 21).

Order: the routine `0xffb73a40` is in one of the chip's method tables (the function-descriptor entry at `0xffc4d570`; Ghidra recovers no caller). `0xffa23a20` is slot `+0x2b8` of the SHub 1 method table (the table array at `0xffbd8a18`, first table), reached through `plat_interrupt_config` (runtime `0x6a7b0`; callers `error_late_install_nasid`, `sal_event_register_headless`, `sal_event_register_cpe_ivn`); `0xffa31290` has no recovered caller. **None of these is on a direct call path from the reset entry or `main()` to the console start; whether any runs before the console start through a method table is unknown.** The reviewed method-table walk in [prom-reset.md](prom-reset.md) (A39) only calls the identification, node-object and memory methods before the console start.

The error-interrupt arrangement, as the PROM sees it, is therefore (inferred): the node has six configuration and enable pairs ("local interrupt 0 to 5") at `0x1_1000_0480 + 0x100 n` and `0x1_1000_0500 + 0x100 n`; each pair names a destination message and a mask of event sources; slice pairs 0/1 and 2/3 share interrupt 0 and 1 for errors, slices 0 and 2 have an INIT pair each in interrupts 2 and 3, and interrupt 5 carries vector `0xe9`. How an enable mask bit maps to an `event_occurred` bit is unknown: `0x7ef` equals the error bits that `shub_error_pending` tests in `event_occurred` (bits 0 to 3 and 5 to 10), which suggests the same numbering for the low ones, but `0x4000` and `0x2000` do not match a bit Linux names.

## What reaches the CPU, in one view

| Source | Vector | Delivery type | Taken or polled by the PROM |
|---|---|---|---|
| `ipi_int` self-replay after drain | the drained vector | external interrupt | polled: `cr.ivr` read until spurious, then re-raised |
| PAL cache-flush return | PAL's value | external interrupt | by the OS or PROM handler (not traced) |
| CPE notice | the OS-registered vector | external interrupt | none in the PROM: it only raises it |
| PROM wake of slaves | 0 | external interrupt | slaves in a wait state; handler not traced |
| Rendezvous | the OS's rendezvous vector | external interrupt | by the OS |
| Cross-calls | `0x12`, `0x13` | external interrupt | by the PROM's slave loop (not traced) |
| PMI (`plat_assert_pmi`, `mcrz_node_pmi`, vector 0x36 escalation, error destination) | 1 | PMI (type 2) | by PAL's PMI entry into SAL |
| INIT (`SYSTEM_RESET`, power-down, INIT path, rendezvous failure, INIT destination) | 0 | INIT (type 5) | by PAL's INIT entry into SAL |
| RTC0 expiry (`bus error`) | 0, agent bit set | type 0 | unknown how the processor sees it |
| L1 console (TIO) | `0xe9` | external interrupt | by the OS (`SGI_UART_VECTOR`) |
| PROM's own timer | `0xef` | the processor's `cr.itv` | taken in the PROM IVT |
| Corrected machine check | `0x1f` | `cr.cmcv` | taken in the PROM IVT |
| TIO error interrupt | `0x36` | external interrupt | taken: escalated to PMI to self |

The SAL runtime never installs a vector table: it runs in the OS's context, so the OS takes whatever the runtime sends. The runtime polls only `cr.ivr`/`cr.irr` in `cpu_interrupt_clear` and `cpu_interrupt_pending`. The runtime sets the interrupt-enable bit (`ssm 0x4000`) at four sites only: `salruntime_set_interrupt_state`, `cpu_timer_start`, `sal_log_get_record` and `sal_event_probe`.

## TLB purge and PIO ordering

**PTC.** The PROM and the runtime do not use SHub's purge-translation-cache registers the way Linux does. Searches (below) find no `ptc.g`, `ptc.ga`, `ptc.l` or `ptc.e` instruction in any code of SAL_A, SAL_B or the runtime (the byte patterns that decode as `ptc` are inside data tables at `0xffbc5ca0` and higher, among register-description records); the only purge instructions are `ptr.d` and `ptr.i`, in one SAL_B helper at `0xffaeb9c0` (`0xffaeb9e0`) that purges a translation register; and no code stores to `SH1_PTC_0` (`0x1_101a_0000`) or `SH1_PTC_1` (`0x1_101a_0080`): those two offsets occur only as entries of the register-dump table at `0xffbfd150` and `0xffbfd160`. **One thing beyond Linux:** the routine at `0xffa95c20` (slot `+0x110` of the SHub 1 method table, so not on a direct call path from `main()`) writes `0x1_101a_0100`, the next register in the same 64 KiB block (the PROM's table lists it next to the two PTC registers, and names a timeout field in the entries that follow; inferred pairing), at `0xffa960a6`. Its value is built from a value read just before and the constant `0x23c34600`, which is used when bit 31 of a call result is set (instructions `0xffa96076` to `0xffa960b6`); the exact packing and the meaning (a purge timeout) were not decoded. The routine also writes `0x1_1004_0100`, `0x1_1004_0180`, `0x1_1004_0300`, `0x1_2000_0080` and `0x1_2000_0100`, and reads `0x1_1004_0000`, `0x1_2000_0180` and `0x1_2000_0000`, in the same routine. Established (the address, the width, the direction and the constant); inferred (the role).

**PIO write status.** Beyond Linux (which only reads the pending count and, on deadlock, writes 7 to the alias), the PROM has two users: `0xffa24ac0` (called from `0xffa24e7c`, inside `pio_wt_st_force_err` at `0xffa24cc0`, in `main_two`, named in node-bringup.md): it writes `0x3fffffffffffd` to the alias at `0x1_2007_0208` (slice pairs use `0x1_2007_0200` and `0x1_2007_0280`; tables at `0xffbd9678` to `0xffbd96a0`) and then polls the status up to 1000 times (calling the delay routine at `0xffa10010` each time) until bits 61:56, the pending write count, are all ones; and `0xffa24cc0` itself stores to `0x1_1005_0608`, then polls the status until bit 0 or bit 2 is set, clears through the alias, and checks `0x1_1005_0280` and `0x1_2006_0500`. Both are already described in [node-bringup.md](../../software/firmware/snprom/node-bringup.md); added here: the alias value, the retry bound and that idle means count all ones on SHub 1, as Linux's `PIO_WRITE_STATUS_IDLE`. The runtime has the same routine (`pio_wt_st_force_err`, runtime +0x30d00) and no other user of the status registers beyond the table entries. **So: the PROM and runtime use the PIO status registers beyond Linux only in this self-test and its wait, and the PTC block only through the `0x1_101a_0100` write.**

## Searches behind the negative claims

The PROM and runtime listings were scanned for (a) every 64-bit `movl` immediate, in the global-window, local-window and bare-offset forms, whose offset is in the local block `0x1_1000_0000` to `0x1_1002_0000` and the neighbours `0x1_101a_0000` to `0x1_101c_0000`, `0x1_2007_0000` and `0x1_2005_0000`; (b) every 8-byte word of SAL_B and SAL_A that equals those offsets, with or without the flag bit used by the PROM's own table form (tables at `0xffbbc750`, `0xffbd9568`, `0xffbd9678`, `0xffbdd088`, `0xffbfad10`, `0xffbfd150`); (c) every `ptc.*`, `ptr.*`, `ssm`, `cr.ivr`, `cr.irr`, `cr.eoi`, `cr.lrr` and `cr.itv` use. Reachability from the reset entry (`0xffa1de00`), `main()` (`0xffa19a20`), `main_two` (`0xffa1ade0`), `main_three` (`0xffad7280`) and the second reset path (`0xffa19850`) was computed over the recovered direct calls. Not covered: any code reached through a function pointer or method table with no recovered caller, a store whose address is formed by arithmetic from a base other than the constants above, and the SHub 2 build (`shub2snprom.bin` was not read).

## Unknown, and what would settle it

- The reset value of `event_occurred`, and which event bits the enable masks `0x4000` and `0x2000` and the INIT/UART pairs refer to. A weak lead: the PROM's field-name strings for the local-interrupt enable registers list `L1_NMI_INT` then `UART_INT` first, and read from the top bit down they would put the L1 NMI at bit 14 (the INIT pairs' `0x4000`) and the UART at bit 13 (the vector `0xe9` pair's `0x2000`), which fits both uses; the event register's names, read from bit 30 down, match Linux for bits 30 to 24 and would put `RTC0_INT` at bit 23. This rests on string order only. The PROM's register-description records (the data run from `0xffc12b40` on) hold the real positions; decoding them would settle it. Not done.
- Whether the error and INIT destinations of the table above are programmed before the console start, through the method tables.
- Whether a compare value below the counter fires an RTC comparator.
- What an agent-bit-set message to vector 0 does at the processor, and what vector 0 at type 0 does (the wake-up).
- The caller and purpose of `0xffa31290`, `0xffafd120`, `0xffb03790`, `0xffb07930`.
- Whether PAL's `PAL_CACHE_FLUSH` return register is the vector (from the PAL specification, not this image).
