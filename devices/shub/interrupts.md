# SHub 1: the interrupt delivery the SAL 5.04 PROM and its SAL runtime program and expect

What `shub1snprom.bin` (SAL 5.04, banner "SGI SAL Version 5.04 rel081111 IP41", package snprom-10.54-70399, sha256 `51ccf9ad830b85ee6c88d6d73d2512322a86454e63db51c57454679283a34617`, 6 MiB at `0xffa00000`) and the SAL runtime component it carries do with the SHub 1 interrupt registers: which ones they write and in what order, which messages they send, what reaches a processor, and what each read must return. It is written so that a model of SHub 1 interrupt delivery can be built from this page and the generated register header alone. Neighbouring pages: the chip is [README.md](README.md), the register file [registers.toml](registers.toml), every register access from reset to the console start [prom-reset.md](prom-reset.md), the memory bring-up [memory-init.md](memory-init.md), the boot path [boot-sequence.md](../../software/firmware/snprom/boot-sequence.md), and the SAL calls the kernel makes [software/sal](../../software/sal/README.md).

**How this was read.** All reading of the PROM went through Ghidra with the IA-64 processor module of the retools checkout (`--ghidra-export ... --sn2-prom`): its function recovery, its call graph (the callers and call sites below) and its decompiled C of the SAL_B routines named. Every address constant, width, direction and value quoted was then checked against a binutils `ia64-linux-gnu-objdump -z` listing of the same bytes; the decompiler is navigation, the listing is the check. Two limits follow from that. Ghidra's import leaves the packed components (the SAL runtime, EFI) as data, so the runtime was read as listings of its expanded ELF (image offset `0x252000`, 918,824 bytes, with its dynamic symbol table); where SAL_B carries a copy of a runtime routine with the same instruction sequence (matched on the first 20 instructions), the Ghidra reading of the SAL_B copy is the reading of both, and the runtime site is listed beside it. Ghidra's function recovery missed three routines (`0xffa21470` the external-interrupt dispatcher, `0xffa23fb0` the error handler, `0xffa239a0` the error-pending test); those, the PTC and PIO status routines (`0xffa95c20`, `0xffa24ac0`, `0xffa24cc0`; the export runs for them were killed before they finished) and the whole runtime are read from the listing only, and the runtime sites are listed with their SAL_B copies. And Ghidra follows direct calls only, so everything reached through the chip's method tables or other function pointers has no recovered caller; this page says so wherever it matters.

**Grades.** *established*: the instructions, address constant, width and direction were read in full at the site named. *inferred*: a role or hardware behaviour reasoned from that code, with the reasoning given. *unknown*: not settled; the route that would settle it is named. A **software expectation** is something the PROM code needs the hardware to do. It says what a model must provide, not what the silicon does. Linux names are from `arch/ia64/include/asm/sn/shub_mmr.h`, `intr.h` and `arch/ia64/sn/kernel/{irq,setup}.c`, `sn2/{sn2_smp,timer_interrupt}.c` at v5.3, and `drivers/char/mmtimer.c` at v4.9 (v5.3 no longer has it). Where Linux has no name, the register is called by its address; those names are ours. The register names the PROM's own register-name table carries are given after an offset where Linux has none (the table lists names in offset order; pairing a name to an offset is inferred from that order, and the table's field encoding was not decoded).

**Site notation.** "site 0x..." is an address in the PROM image: `0xffa0....` to `0xffc4....` is SAL_B (SAL_A is `0xffc4e000`), and "runtime +0x..." is an offset in the expanded runtime ELF, with the symbol the ELF carries. A register is named by its offset in the node's register space (`0x1_1000_0380`); the PROM reaches it as the **global window** `0x8_0000_0000 + (nasid << 38) + offset` (bit 63 set, uncached) or the **local window** `0x80_0000_0000 + offset`. Every access is a 64-bit `ld8` or `st8` followed by `mf.a` (SAL_B `0xffa0e5a0` load, `0xffa0e640` store; runtime `chipset_load_mmr`, `chipset_store_mmr`).

## What a model has to do, in short

1. **Reset to the console start needs no interrupt delivery.** On the direct call paths from the SAL_B reset entry and `main()` (`0xffa19a20`) to the `sysctl_init` call (the L1 start, `0xffa19c0c`), the only code that touches an interrupt register is one routine (site 0xffa0b9a0, two alias writes), called from the node-object read `0xffa0bd20` (call at `0xffa0bf3c`) on its other-node branch before a request to another node's registers is sent; the single-node chip-identification read takes the local branch of that routine and never reaches it ([prom-reset.md](prom-reset.md), A39). SAL_A touches none of these registers. A model that keeps `ipi_int`, `event_occurred`, the RTC comparator registers and the registers in [the destination table](#destination-and-enable-registers-the-prom-programs) as plain storage lets the PROM reach the console. This is a search result over recovered direct calls, not a trace: [searches](#searches-behind-the-negative-claims).
2. **After the console start the PROM does use interrupt delivery**, in these places: a drain-and-replay of pending interrupts (second reset path), the wake-up of the other processors (`main_two`), the machine-check and INIT rendezvous, platform management interrupts (PMI) for errors, a timed "bus error" assertion through the RTC0 comparator, and the SAL calls that reset or flush. Each is a store to `ipi_int` or to a comparator whose result must arrive as an interrupt at the processor named in the message.
3. **A store to `ipi_int` with bit 63 set must deliver the message** (type, vector, target processor) to the processor named, including when the target is the sender: the PROM raises interrupts on itself this way and then reads `cr.ivr` or `cr.irr` (software expectation, established at the sites below). The base field is not needed (the PROM leaves it zero; Linux writes `0xfee`).
4. **Nothing in the PROM reads `ipi_int`, the alias, any comparator or the destination registers back** (reads of the comparator configuration are the one exception: [RTC](#real-time-clock-comparators)). Reads of `event_occurred` are limited to the sites in [that section](#event_occurred-and-its-alias).

## Processor id and message layout the PROM uses

Established from every site that builds an `ipi_int` value or a destination: the processor id carried in the `pid` field (bits 19:4 of the message) is the 16-bit value in bits 31:16 of that processor's `cr.lid`, and the PROM composes and decomposes it as

| pid bits | field | source in the code |
|---|---|---|
| 6:0 | low 7 bits of the NASID | `chipset_get_nasid`, `extr 0..6`; the same bits of `cr.lid` bits 22:16 |
| 10:7 | processor slice, 4 bits | `cr.lid` bits 26:23 (`extr.u cr.lid,23,4`) |
| 15:11 | NASID bits 11:7 | `cr.lid` bits 31:27 |

The target node of a message is not in the message: the PROM adds `nasid << 38` to the address it stores to, where nasid is rebuilt from the same pid fields (bits 6:0 of pid, then bits 15:11 shifted to 11:7). The message is the Linux layout: send bit 63, `idx` (vector) bits 59:52, `base` bits 49:21, `pid` bits 19:4, `agt` bit 3, `type` bits 2:0 (types seen: 0 external interrupt, 2 PMI, 5 INIT). Linux's text says the agent bit "must be zero for SHub"; the PROM sets it once ([BERR](#real-time-clock-comparators)). Linux's fallback decode of a processor id (NASID in bits 11:0, slice in 13:12) disagrees with all of the above; the PROM decode is established from the code and the Linux fallback is not used by this PROM.

## `event_occurred` and its alias

Linux: `SH1_EVENT_OCCURRED` `0x1_1001_0000`, `SH1_EVENT_OCCURRED_ALIAS` `0x1_1001_0008`. Bits Linux names: 20 UART, 24 to 26 RTC comparators 1 to 3, 28 IPI, 29 and 30 I/O interface 0 and 1. The kernel reads the register, ANDs with `SH_ALL_INT_MASK` (bits 20, 28, 29, 30) and writes the result to the alias (`sn_ack_irq`, established); the clock driver writes a single comparator bit to the alias to clear it (`mmtimer_clr_int_pending`, established). Every PROM access, with Ghidra's reading of the routine:

Not found anywhere in SAL_A, SAL_B or the runtime: a read of bits 20, 24 to 26, 28, 29 or 30, a write to the alias of bit 28 (IPI), or any use of `0x1_1001_0080` other than writing its alias at `+0x88` (above). The PROM's register-name table lists four names for the four offsets `0x1_1001_0000`, `+8`, `+0x80`, `+0x88`: `SH_EVENT_OCCURRED`, its `_ALIAS`, `SH_EVENT_OVERFLOW` and its `_ALIAS` (pairing by table order: inferred). So `+0x80` is probably an overflow word with its own clear alias at `+0x88`; the PROM writes 8 to the alias and never reads or writes `+0x80` itself.

**What the PROM tolerates, and the reset value.** *Unknown.* No document held and no code settles it: Linux defines `_INIT` macros for the comparators and their enables only. What the PROM tolerates: before the console start nothing reads the register. `shub_error_interrupt_config` programs the error destinations and enable masks first, then reads the register and clears `event & 0x7ef` (`0xffa30b40`), so error bits set from reset are cleared there without having raised an interrupt through the freshly programmed destination (they may have been latched before it; the order is the code's). Bits outside `0x7ef` are never looked at by a PROM read except bit 21. Zero is the simplest model; any value is tolerated except bit 21 set when the INIT path reads it.

**What a read must return.** Bits are pending flags: each stays 0 unless the modelled source asserts it. A write of ones to the alias clears exactly those bits (inferred from the PROM writing back exactly what it read, and from the single-bit clears; neither Linux nor the PROM reads the alias). A write to the primary register sets the bits written (inferred, above); a model that ORs the written value in satisfies both uses. Bit 21 must read 0 for the INIT path to proceed to the comparator test.

## Real-time clock comparators

Linux (v4.9 `mmtimer.c`): comparators RTC1, RTC2, RTC3 with config `0x1_1000_1480 + 0x100 n` (message layout, bits 59:52 vector, 19:4 pid, type 0), enable `0x1_1000_1500 + 0x100 n` (bit 0), compare `0x1_101b_0080 + 0x80 n` (55 bits), events 24 to 26. The driver programs each as: disable, compare ← all ones, clear the pending bit through the alias, write config, enable, write the real compare value. The comment in the driver says "RTC0 is used by SAL"; the PROM confirms it, with unnamed (in Linux) registers at the same stride: config `0x1_1000_1380`, enable `0x1_1000_1400`, compare `0x1_101b_0000` (the PROM's name table lists the three as the RTC0 interrupt configuration and enable and the first compare register; inferred pairing).

**RTC0, used by SAL_B and the runtime for a delayed "bus error" assertion** (SAL_B `0xffa318a0`, runtime `plat_assert_berr`; the argument is a delay in microseconds):

1. read-modify-write `0x1_2001_0100`, OR 8 (bit 3);
2. if the delay is zero, store the immediate `ipi_int` message to the local window instead and stop (table above); otherwise (in the simulator-marker case `cpuid[2] == 0xaeeeeeee8badbeef`, the delay is forced to 1):
3. write `0x1_1000_1380` ← `pid << 4 | 8` (type 0, agent bit set, vector 0, base 0, no send bit);
4. read the tick period in nanoseconds (`0xffa0da00`, `10 * (f + 1)` from `rtc_ctl`, see [prom-reset.md](prom-reset.md#the-real-time-clock)), read the counter `0x1_101c_0000`;
5. write `0x1_101b_0000` ← counter + (delay * 1000) / period;
6. write `0x1_1000_1400` ← 1.

The undo (`0xffa31d20`): clear bit 3 of `0x1_2001_0100`, write `0x1_1000_1400` ← 0, write `0x800000` to the event alias. Order differs from Linux's: the PROM writes the configuration, then the compare, then the enable; it does not first set the compare to all ones. Established for all of it; the roles ("bus error", the agent bit meaning, bit 23 as RTC0's event) are inferred. A model should fire the configured message when the free-running counter reaches the compare value while the enable is 1, and set the event bit; whether a compare below the counter fires at once or only on equality is **unknown** (Linux's `mmtimer` retries "on interval retry", suggesting it can be missed).

**RTC1 to RTC3 are only read by the PROM** (`0xffa316d0`, called from `0xffa0299c` in `0xffa02710`): for each pair it reads the configuration and tests that the type (bits 2:0) equals 5 (INIT), and if so reads the enable and tests bit 0; the result is "an OS comparator is armed to deliver INIT". Established (instructions); inferred (purpose: a watchdog the OS armed). **Must return** what was written, with zero from reset: type 0 or any value other than 5 means "not armed". Linux always writes type 0 and so never trips it. If a model returns type 5 with the enable set the PROM sends INIT to every other processor (below).

The counter's reads and the period register are as in [prom-reset.md](prom-reset.md#the-real-time-clock); the PROM's `chipset_rtc_time` and Linux's clock read the same 55-bit counter.

## The INIT and machine-check path

`0xffa02710` (called from `0xffa029d0` and `0xffa02ff0`; the latter also calls the rendezvous routine, which is why this is read as part of the machine-check and INIT handling: inferred), in the order Ghidra shows: fetch the per-processor SAL record; return if its field at +0x18 is zero or `0xffa03e50` returns 0; test whether the interrupt vector in the record at +0x80 is pending (`0xffa100e0`); call `0xffa03930`; if that succeeds and event bit 21 is **clear** (`0xffa314f0`) and any of RTC1 to RTC3 is armed for INIT (`0xffa316d0`), send INIT to every other present processor (`0xffa04ae0`); then continue to the SAL return call `0xffa35e10`. The instruction-level reading of `0xffa03930` and `0xffa03e50` was not done. `0xffa02c20` does the converse: if bit 21 is set it clears it through the alias and continues. What bit 21 means is **unknown** (Linux names no bit 21; the PROM's name table has several unrelated candidates); its role here is "an INIT-class event is already being handled". Established (control flow); inferred (the reading of bit 21).

## Destination and enable registers the PROM programs

Linux v5.3 names none of these; the 2.4 SN2 header (see the PIC section below) names `0x80`, `0x180`, `0x200` and `0x280`, and its names for the rest match the PROM's own. The SHub 1 PROM's name table (16-byte records from `0xffbfad08`: a 32-bit offset into the name pool at `0xffbfdef8`, a 32-bit field word, the 64-bit register offset) carries the same four names in their own records, so for these registers the pairing is read from the record, not from table order. All writes are 64-bit stores; none is read back. Names in code font after an offset are the ones the PROM's own register-name table carries (pairing by table order: inferred).

## TLB purge and PIO ordering

**PTC.** The PROM and the runtime do not use SHub's purge-translation-cache registers the way Linux does. Searches (below) find no `ptc.g`, `ptc.ga`, `ptc.l` or `ptc.e` instruction in any code of SAL_A, SAL_B or the runtime (the byte patterns that decode as `ptc` are inside data tables at `0xffbc5ca0` and higher, among register-description records); the only purge instructions are `ptr.d` and `ptr.i`, in one SAL_B helper at `0xffaeb9c0` (`0xffaeb9e0`) that purges a translation register; and no code stores to `SH1_PTC_0` (`0x1_101a_0000`) or `SH1_PTC_1` (`0x1_101a_0080`): those two offsets occur only as entries of the register-dump table at `0xffbfd150` and `0xffbfd160`. **One thing beyond Linux:** the routine at `0xffa95c20` (slot `+0x110` of the SHub 1 method table, so not on a direct call path from `main()`) writes `0x1_101a_0100`, the next register in the same 64 KiB block (the PROM's table lists it next to the two PTC registers, and names a timeout field in the entries that follow; inferred pairing), at `0xffa960a6`. It is a read-modify-write: the register is read, bits 23:0 are set to `0x186a0`, bits 35:24 to `0x3e8` (a `dep` of the constant 1000 at `0xffa96126`) and the rest is kept; the store is at `0xffa9612c` (the address constant is loaded at `0xffa960a6`). The constant `0x23c34600` (used when bit 31 of a call result is set, instructions `0xffa96076` to `0xffa960b6`) belongs to a different register: it is merged into the value stored to `0x1_2000_0100`; the meaning (a purge timeout) was not decoded. The routine also read-modify-writes `0x1_1004_0000` (bit 18 set, 63 times in a loop), `0x1_1004_0100`, `0x1_1004_0180`, `0x1_1004_0300`, `0x1_2000_0000`, `0x1_2000_0080`, `0x1_2000_0100` and `0x1_2000_0180`. Established (the address, the width, the direction and the constant); inferred (the role).

**PIO write status.** Beyond Linux (which only reads the pending count and, on deadlock, writes 7 to the alias), the PROM has two users: `0xffa24ac0` (called from `0xffa24e7c`, inside `pio_wt_st_force_err` at `0xffa24cc0`, in `main_two`, named in node-bringup.md): it writes `0x3fffffffffffd` to the alias at `0x1_2007_0208` (slice pairs use `0x1_2007_0200` and `0x1_2007_0280`; tables at `0xffbd9678` to `0xffbd96a0`) and then polls the status up to 1001 times (`0x3e9`; calling the delay routine at `0xffa10010` after each unfinished read) until bits 61:56, the pending write count, are all ones; and `0xffa24cc0` itself stores to `0x1_1005_0608`, then polls the status until bit 0 or bit 2 is set, clears through the alias, and checks `0x1_1005_0280` and `0x1_2006_0500`. Both are already described in [node-bringup.md](../../software/firmware/snprom/node-bringup.md); added here: the alias value, the retry bound (1001) and that idle means count all ones on SHub 1, as Linux's `PIO_WRITE_STATUS_IDLE`. The runtime has the same routine (`pio_wt_st_force_err`, runtime +0x30d00) and no other user of the status registers beyond the table entries. **So: the PROM and runtime use the PIO status registers beyond Linux only in this self-test and its wait, and the PTC block only through the `0x1_101a_0100` write.**

## Where a PIC interrupt lands on SHub 1

What a PCI-X bridge (PIC) behind a SHub 1 writes, and which SHub register takes it. Sources, all SGI's own SN2 Linux platform code: the 2.4-series tree as carried by the Linux/MIPS `linux-2.4` branch branch at `8ef7d46c94d5` (`arch/ia64/sn/io/sn2/shub_intr.c`, `arch/ia64/sn/io/sn2/pcibr/pcibr_intr.c`, `include/asm-ia64/sn/sn2/shub_mmr.h`, `include/asm-ia64/sn/pci/pic.h`), and Linux v5.3 for the later firmware-call form (`arch/ia64/sn/kernel/irq.c`, `arch/ia64/sn/pci/pcibr/pcibr_provider.c`, `arch/ia64/include/asm/sn/intr.h`). The v5.3 header carries none of these registers; the 2.4 header does.

**Who computes the address.** In v5.3 the kernel never does: `sn_intr_alloc` calls `SN_SAL_IOIF_INTERRUPT` and the firmware returns the Crosstalk address in `irq_xtalkaddr`; `pcibr_target_interrupt` only writes it (established, see [software/sal](../../software/sal/sn2-runtime.md)). In the 2.4 tree the kernel computed it itself, in `do_hub_intr_alloc` and again in `sn_shub_redirect_intr` (established, same expression in both):

    xtalk_addr = SH_II_INT0 (slice 0) or SH_II_INT1 (any other slice)
                 | nasid << 36 | 1 << 47

So the address the PIC is given is: bits 46:36 the target NASID (11 bits), bit 47 set, and the low 36 bits the offset of the I/O interface interrupt register in the node: `SH_II_INT0` is `0x1_1000_0000` and `SH_II_INT1` is `0x1_1000_0100` (2.4 header, established). The NASID sits two bits below its CPU-address position (`nasid << 38`), which is the same shift `PHYS_TO_DMA` applies to every DMA address (established; see [PIC](../pic/README.md)). Bit 47 is what the 2.4 `xtalkaddrs.h` header calls the I/O (register) access bit of the Crosstalk address (the header's text is inherited from the Origin generation; that SHub 1 decodes bit 47 the same way is **inferred** from the code setting it for a register address). A node with several processors uses `SH_II_INT0` for slice 0 and `SH_II_INT1` for the others (any non-zero slice, established). The processor an interrupt reaches is whatever the register's config holds, not the slice itself: the 2.4 kernel (`ml_SN_intr.c`, the same routine that sets up the UART interrupt) writes `SH_II_INT0_CONFIG` with the physical id of slice 0 and `SH_II_INT1_CONFIG` with that of slice 2, then 1 to both enables, exactly the PROM's stores, so a CPU in slice 1 or 3 would be reached through `SH_II_INT1` at slice 2's processor. The second register exists so that one node can aim interrupts at two processors (inferred).

**What the PIC is given.** `pcibr_setpciint` (2.4) stores, into the pin's `p_int_addr[pin]` register (`0x130 + 8 * pin`), `(vector << 48) & bits 55:48 | address & 0xffff_ffff_ffff` (established): bits 47:0 the address above, bits 55:48 the vector. The vector is the processor interrupt vector chosen by the allocator (`intr_heuristic`; v5.3 firmware picks 0x3c to 0xe6). `pcibr_target_interrupt` (v5.3) replaces only the low 48 bits, so the vector field survives a retarget (established, the v5.3 accessor is `pcireg_intr_addr_addr_set`).

**What the PIC writes.** The source gives no packet layout. The data is **inferred** to be `0x100 | vector` (a 64-bit write of that value to the address): `SH_II_INT0` has `IDX` in bits 7:0 ("targeted McKinley interrupt vector") and `SEND` in bit 8 ("send interrupt message to PI", a pulse); the IRIX software set-packet and the DMA flush wait word `0x10f` read in [PIC](../pic/README.md) have the same shape. The vector in `p_int_addr` and the `IDX` field therefore carry the same number. A SHub model should treat a write to `SH_II_INT0`/`SH_II_INT1` with bit 8 set as a send of vector bits 7:0 and ignore a write with bit 8 clear (the clear half of the shape; **unknown** whether bit 8 clear does anything).

**What the SHub does with it.** `SH_II_INT0_CONFIG` (`0x1_1000_0080`) and `SH_II_INT1_CONFIG` (`0x1_1000_0180`) hold the delivery type (bits 2:0; 0 interrupt, 2 PMI, 4 NMI, 5 INIT), agent bit 3 (must be 0), the target processor id in bits 19:4 and an optional vector base in bits 49:21, the same layout as `ipi_int` without send and vector; `SH_II_INT0_ENABLE` (`0x1_1000_0200`) and `SH_II_INT1_ENABLE` (`0x1_1000_0280`) have one enable bit, bit 0 (2.4 header, established). When the enabled register is sent, the interrupt reaches the processor named by the config with vector `IDX`. That the pending state shows up in `event_occurred` bit 29 (`II_INT0`) or 30 (`II_INT1`) is established as naming (Linux names the bits "II_INT0/1" and the kernel acknowledges them through the alias, `sn_ack_irq`); that the bit is set by this write is **inferred** from the names. The PROM programs these four registers, which the earlier table of this page listed as unnamed: `0x1_1000_0080` and `0x1_1000_0180` get the processor ids of slices 0 and 2, `0x1_1000_0200` and `0x1_1000_0280` get 1 (routine `0xffb73a40`). That makes them `SH_II_INT0_CONFIG`, `SH_II_INT1_CONFIG`, `SH_II_INT0_ENABLE` and `SH_II_INT1_ENABLE` by offset (established as the offsets of the 2.4 header; role of the PROM stores inferred, since the PROM does not use them for anything it reads back). The PROM's value for the config registers carries the pid shifted left by 4 only: type 0, no base. The PROM's own name table lists all six II registers and the 2.4 header agrees on every offset (read in this review).

**Shipped.** The ProPack 2.4.21 kernel's symbol map (`System.map-2.4.21-sgi300r3`) carries `do_hub_intr_alloc` (0x2c0 bytes), `sn_shub_redirect_intr` and `pcibr_setpciint`, so this code is what shipped for Altix. The kernel image itself is not held, so the constants were not checked in the binary.

**Behind a TIO.** Not the same path: Linux's `sn_check_intr` says bridges behind a TIO "do not target SHub II interrupt registers" (v5.3, established as the authors' statement). The TIOCE stores `vector << 56 | irq_xtalkaddr`; where that address points is **unknown** (see [TIO](../tio/README.md)).

**Allocator.** The routine behind `SN_SAL_IOIF_INTERRUPT` is not in the packed SAL runtime: it is in SAL_B. It is read in full in the next section, which answers what this paragraph used to leave unknown (the address it builds, the registers it picks, what a retarget does to the record).

## The firmware's interrupt allocator (`SN_SAL_IOIF_INTERRUPT`)

**Where it is and how it was read.** All of it is SAL_B code of the flat image (SAL 5.04 base `0xffa01000`); the inflated SAL runtime component of 4.43, 4.90 and 5.04 contains no `hub_intr_alloc`, `pcibr_irq_alloc` or `salruntime_sn_intr_handler` string, and its dynamic symbol table has no allocator symbol (the SAL call row for `0x0200004a` points into SAL_B, as [the SAL page](../../software/sal/sn2-runtime.md#ioif_interrupt-0x0200004a) already said). Method: the whole of SAL_B decompiled in the IA-64 Ghidra module (`--sn2-prom --sal-runtime`, 2069 functions; functions that only a method table reaches were decompiled by address), every routine below read in full in the decompile, and these facts re-checked in a binutils `ia64-linux-gnu-objdump` listing of the SAL_B component: the address builder (`0xffb739e0`), the irq search loop (`0xffb8fee0`), the PIC call order (`0xffb6c720`) and the callers of the hub late-init (`0xffb29390`). The SAL 4.90 image (package 10.40) and the 4.43 image were compared routine by routine (last subsection). The allocation routines themselves are bookkeeping and address arithmetic: **they store to no SHub and no PIC register** (established, listing: of the 449 direct calls to the SAL_B register-store helper `0xffa0e640` in the SAL_B listing, the only ones inside the allocator's routines are the 9 in `hub_intr_init` and the 2 in `hubii_eint_init`, both late-init, listed below). The PIC and SHub registers are programmed by the callers, listed in order below.

### Entry and the two callers (established)

SAL call `0x0200004a` is handled at `0xffb1f970` (`sal_0200004a`). Arguments: a1 operation (1 allocate, 2 free, 3 redirect), a2 NASID of the bridge (the index into the node table; above `0x7ff` the node pointer is taken as 0), a3 widget, a4 the physical address of the kernel's `sn_irq_info`, a5 to a7 as in the table below. It finds the *provider* for the (NASID, widget) pair at node record `+0x958 + 0x30 * widget` (no bound check on the widget was found); a null provider prints `salruntime_sn_xtalk: NULL provider pointer` and gives status -3. A missing operation prints `NULL intr_alloc`, `NULL intr_free` or `NULL intr_redirect`; any other operation prints `Invalid provider_call` and gives -3. Only r8 carries a result: 0 or -3.

| Operation | Arguments | Provider slot | What the handler does around it |
|---|---|---|---|
| 1 allocate | a5 requested irq (-1: any), a6 requested NASID (low 16 bits, 0xffff: any), a7 requested slice (low 32 bits, -1: any) | `+0x28` (SHub: `0xffb73df0`) | Passes a local out-pointer holding 0. On a non-negative result copies seven fields of the returned record into the kernel's: NASID (`+8`, 16 bits), slice (`+0xc`), irq (`+0x14`), crossbar address (`+0x20`), cookie (`+0x44`), flags (`+0x48`), share count (`+0x4c`). Status 0. Negative: -3, nothing copied. |
| 2 free | a4 irq, a5 cookie | `+0x30` (`0xffb740c0`) | Walks the per-irq list for the record whose cookie matches; calls the provider with it; status 0. No match: -3. |
| 3 redirect | a5 new NASID (16 bits), a6 new slice (32 bits); the record's irq (`+0x14`) and cookie (`+0x44`) are read from the kernel's copy | `+0x38` (`0xffb74210`) | Finds the record by irq and cookie; on provider result 0 copies back only NASID, slice and crossbar address and returns 0; otherwise -3. |

The kernel record fields the PROM does **not** return are `irq_int_bit`, `irq_bridge_type`, `irq_bridge` (the kernel's own MSI code says "Prom probably should fill these in, but doesn't": a match, `arch/ia64/sn/kernel/msi_sn.c` v5.3). The record the PROM keeps is `0x50` bytes: `+0` next in the per-irq list, `+8` target NASID (halfword, `0xffff` unset), `+0xc` target slice (`-1` unset), `+0x14` irq, `+0x18` the bridge line it serves, `+0x20` crossbar address, `+0x30` and `+0x38` the bus and device objects it belongs to, `+0x44` cookie, `+0x48` flags (bit 0 always set), `+0x4c` share count.

**Who calls the provider.** (1) The kernel through the SAL call, for message-signalled interrupts and for the free-then-allocate fallback when redirect fails (`sn_intr_alloc` at msi_sn.c and irq.c v5.3). (2) The PROM itself, per device interrupt pin, during the PCI scan run by the first `0x55` or `0x5f` call: the per-device routine `0xffb3ede0` (called from `0xffb2c31c`, `0xffb3512c`, `0xffb4398c`) reads the interrupt pin (config byte `0x3d`), calls the PIC provider's method at `+0x58` (`pcibr_intr_alloc`, `0xffb6c720`, in the PIC tables at `0xffc2b818` for type 2 and `0xffc2afd0` for type 3), and writes the allocated irq to config byte `0x3c`, or `0xff` after printing `pci_device_intr_alloc failed`. The PIC page's "caller not traced" is therefore answered, and the routine that page cites as `0xffb3ef90` is the one that follows `0xffb3ede0`. For an ordinary line interrupt the kernel does not call the allocator: it takes the record the PROM made at scan time from `SN_SAL_IOIF_GET_PCIDEV_INFO` (kernel `sn_pci_fixup_slot`, v5.3), so the kernel's first allocate call comes only for an MSI, or when it retargets with redirect unavailable. Both paths reach the same SHub method.

### The SHub provider methods (established)

The SHub's table is the array of function descriptors at `0xffc2b8e8`; node record `+0x2d8` is set to it when the node object is built (`0xffb45350`, `0xffb4584c`). The PIC reaches it as `*(bus + 0xe0) + 0x28`. Slots: `+0x20` `0xffb71440` (late interrupt init: `hub_intr_init` `0xffb73a40`, then `hubii_eint_init` `0xffb72e20`), `+0x28` `hub_intr_alloc` `0xffb73df0`, `+0x30` free `0xffb740c0`, `+0x38` redirect `0xffb74210`. The late-init slot is called for every hub by `0xffb29390`, from the `0x55` and `0x5f` cases of the I/O handler (call sites `0xffb1f0bc` and `0xffb1f77c`, each followed by the bus late init `0xffb2c370`); the scan routine `0xffb2d450` is called at `0xffb1e99c` ahead of those case bodies (order inferred from the addresses): so the register stores listed under [Destination and enable registers the PROM programs](#destination-and-enable-registers-the-prom-programs) for `0xffb73a40` run when the kernel or EFI makes its first `GET_HUBDEV_INFO` or `IOIF_INIT` call, not before the console start (the earlier page said the caller was unknown).

**Allocate (`hub_intr_alloc(bridge_nasid, irq, req_nasid, req_slice, &record)`).**

1. If `*record` is null, reserve a new record for `irq` (`0xffb8fee0`, below); failure prints `hub_intr_alloc(): intr_reserve_level() failed!` and returns -1. A fresh record has NASID `0xffff` and slice -1. The PIC passes the device's existing record, so only the kernel's path reserves here.
2. Choose the target (`hub_intr_heuristic`, `0xffb73750`, below). Failure prints `hub_intr_alloc(): tio_intr_heuristic() failed` (the string names the wrong function; it is the same text in the TIO copy), frees the record, and (5.04 only) clears `*record`; returns -1.
3. Build the crossbar address (`0xffb739e0`): `0x1_1000_0000` if the chosen slice is 0, otherwise `0x1_1000_0100`, ORed with `nasid << 36` and bit 47 (`0x8000_0000_0000`), where `nasid` is the **target** node. This is exactly the 2.4 kernel's expression (`SH_II_INT0` / `SH_II_INT1`, checked in the listing); established. Store it at record `+0x20`.
4. Add 1 to the per-slice interrupt count of the target node (node record `+0xc40 + 4 * slice`, four counters). Return 0.

**Target choice (`0xffb73750`).** A request is "any" when the requested slice or the requested NASID is -1, otherwise "specific".

- *Any:* take the bridge's own node. Pick a slice there (`0xffb8fc50`): scanning slices 3 down to 0, a slice qualifies if it is present (below); the qualifying slice with the lowest interrupt count wins, a tie going to the higher slice; an odd NASID (a TIO) has no slice at all. On a SHub whose revision (bits 31:28 of the target node's `0x1_1006_0580`, read through the global window) is below 3, which the PROM calls SHub 1.1, the first qualifying slice from the top is taken without a comparison (software workaround; established as code, the hardware reason is inferred). If the bridge's node has no qualifying slice (a node without processors, such as an IX-brick), choose another node (`0xffb8fb90`, `0xffb8f670`): every other node in the node table with an even NASID and a present processor is a candidate; the nearest wins by the distance the topology records give (`0xffa0b210`, a 16-bit value in the route table, `0xff` when none is recorded; inferred to be a hop metric), a tie goes to the lower total interrupt count over its present slices, with a further cut-off that stops a candidate once seven slices have been counted among equals (purpose inferred, not settled). The slice is then picked on that node as above. No candidate: `intr_cpu_choose_node() couldn't find non-headless node`, failure.
- *Specific:* read the requested node's SHub revision. Below 3, take the highest present slice on that node and print `hub_intr_heuristic: WARNING: SHUB 1.1 present, cant target nasid=..., slice=..., will target nasid=..., slice=... instead` if it differs from the request. Otherwise use the requested slice. In both cases the slice must be present, else `hub_intr_heuristic(): Cannot target interrupt to CPU` and failure.
- *Sharing:* when a PIC connects a line whose irq is already shared (share count above 1), it first copies the target NASID and slice from another record on the same irq, so all sharers of an irq go to one target (established, `0xffb6c720`); the request then takes the "specific" branch.
- *Present* (`0xffb8faa0`): bit `26 + slice` of the node's presence word (the `0x1_5003_1550` word of [node-bringup](../../software/firmware/snprom/node-bringup.md), tested through the per-node object method at `+0x100`) must be set **and** a second per-slice word read through the global window must have bits 51:50 equal to 2 (`0xffa03fc0`: the address is `0x1_5003_15e0` for slice 0 and `0x1_5003_1590` for slice 2; slices 1 and 3 have no table entry and take a different form, `0x180_0000`, that was not decoded). Established as code; that this means "processor present and not disabled" is inferred.

**Vector and bit allocation (`0xffb8fee0`, established, loop checked in the listing).** The irq (processor vector) space is one array of 0xe7 list heads in the PROM's I/O state, shared by every bridge on every node. Requested irq above `0xe6` fails. Requested irq in range: the new record joins that irq's list and its share count is the head's plus one. Requested -1: the lowest irq from `0x3c` to `0xe6` whose list is empty; if none is empty, the irq with the lowest share count, **the highest-numbered one on a tie** (the running minimum is stored plus one, so an equal count replaces it); share count is that count plus one. The record is allocated from the PROM heap (failure prints `Warning - cannot allocate memory for IRQ struct`), pushed at the head of the list, flags bit 0 set, cookie taken from a counter in the I/O state (`+0x40`, then incremented; the first value is not read) and, if the share count is above 1, written into every record of that list. Reserved vectors are requested explicitly: the late interrupt init asks for `0x31` (II error) and the PIC late init for `0x33` (PCI ASIC error).

**Free (`0xffb740c0`).** Subtract one from the slice's interrupt count on the record's node, unlink the record from its irq list, subtract one from the share count of the others, release it. No register is written: the kernel clears the PIC pin itself.

**Redirect (`0xffb74210`).** Takes a NASID and slice. Below SHub revision 3 it looks for the highest present slice of the requested node and fails (result 1, status -3) if there is none, warning if it moved the request; **otherwise it accepts the requested slice without a presence check** (unlike allocate). It then rebuilds the crossbar address for the new (NASID, slice), moves the interrupt count from the old slice to the new, and stores NASID, slice and address in the record. The PIC is not touched: the kernel rewrites the pin's address field itself (`pcibr_target_interrupt`, v5.3: enable bit clear, address low 48 bits written, enable set, force).

### Register writes in order (established, call order checked in the listing)

The stores that make one PIC interrupt work, in the order the firmware issues them:

1. **At scan, per device pin, `pcibr_intr_alloc` (`0xffb6c720`):** hub allocate (no stores), then on the PIC through accessor routines: `int_device` (`+0x120`) field of the line cleared (`0xffabaf30`, `7 << 3n`), the field set to the host function's slot (`0xffabac70`); `int_addr` for the line (`+0x130 + 8n`): bits 55:48 := irq (`0xffabb9e0`), then bits 47:0 := the crossbar address (`0xffabbcf0`); `int_enable` (`+0x108`) bit `n` set (`0xffaba1a0`); a read of `+0x50` to flush (`0xffab62d0`). Then the PCI config byte `0x3c` := irq. On failure the PIC's record pointer is cleared and the pin is left unprogrammed.
2. **At the first `0x55` or `0x5f` call, after the scan, per SHub, `hub_intr_init` (`0xffb73a40`):** the stores of the [destination table](#destination-and-enable-registers-the-prom-programs), in this order: `0x1_1000_0300` (only if the node has no processor of its own), `0x1_2005_0a80` := 0, `0x1_2005_0500` := 0, `SH_LOCAL_INT5_CONFIG` `0x1_1000_0980` := pid of the chosen slice `<< 4 | 0xe9 << 52`, `SH_LOCAL_INT5_ENABLE` `0x1_1000_0a00` := `0x2000`, `SH_II_INT0_CONFIG` `0x1_1000_0080` := pid(node, slice 0)` << 4`, `SH_II_INT1_CONFIG` `0x1_1000_0180` := pid(node, slice 2)` << 4`, `SH_II_INT0_ENABLE` `0x1_1000_0200` := 1, `SH_II_INT1_ENABLE` `0x1_1000_0280` := 1. The pid has bits 6:0 the NASID's low 7 bits, 10:7 the slice, 15:11 NASID bits 11:7 ([layout](#processor-id-and-message-layout-the-prom-uses)). So **INT0 always reaches the node's slice-0 processor and INT1 the node's slice-2 processor, whatever slice the allocator chose**: a chosen slice 1 or 3 is delivered to the slice-2 processor (inferred from the stores; no PROM code reads the registers back). The `II_INT*` registers are programmed with the node's *own* NASID, so a node without a processor gets an interrupt aimed at a missing processor unless `0x1_1000_0300` redirects it (inferred): the allocator never chooses such a node as a target.
3. **Same call, `hubii_eint_init` (`0xffb72e20`):** read-modify-write of the II-wrapper register `0x8_01c0_0128` (global window; bit 10 cleared when bit 13 is clear), allocate irq `0x31` on the node itself (else on any node), then store `irq | 1 << 24 | nasid << 9` to `0x8_01c0_0138` (the vector and the node number, not a crossbar address; the register's name was not read, inferred as the II error interrupt destination), then a call (`0xffb46430`) that was not read.
4. **Bus late init (`0xffb6cef0`), after the hub's:** the PCI error interrupt, already tabulated on the PIC page: irq `0x33`, `+0x38` low 48 bits, `+0x128`, `+0x108` OR constant.

The interrupt-pending state is never touched by the allocator or by these writes: bits 29 and 30 of `event_occurred` (`II_INT0`, `II_INT1`) are set by a PIC write to the matching register and cleared by the kernel through the alias, as before.

### Multi-node and multi-PIC (established unless marked)

- **The address names the target node, not the bridge's.** A PIC on a node with no processors (an IX-brick or any I/O-only node) gets the NASID and `SH_II_INT0`/`SH_II_INT1` of a node that has processors, chosen nearest by topology, and its write crosses NUMAlink to that node. A model must route a PIC's store by bits 46:36 of the address to any node's `SH_II_INT0` and `SH_II_INT1`, with vector bits 7:0 and the send bit (the layout, still inferred, is above).
- **Vectors are machine-wide, not per processor.** One list array serves all bridges: with two PICs the second PIC's lines continue the numbering (`0x3c`, `0x3d`, ... in scan order; the bridge order is the bus mapping list's, taken as the discovery order: inferred). Two lines of one PIC that share an irq number (two devices on one line index of one bus get the same irq in separate records) or lines of different PICs once all 171 vectors are taken, share the vector: the share count rises and every sharer of one irq is sent to the same target.
- **Several processors per node:** only slice 0 and slice 2 have a delivery register; the allocator's per-slice balance still counts four slices per node, so a node with processors on slices 0 and 2 only has its load split as the PROM sees it, but delivery follows the INT0/INT1 rule above.
- **A node with processors uses itself first;** a remote target is used only when the bridge's own node has no usable processor, when the kernel asks for a remote one, or for a sharer copy.
- **TIO bridges** take a parallel path (`tio_intr_alloc` `0xffb79bb0`, heuristic `0xffb798a0`, register manager `0xffb79030`, init `0xffb78ee0`): the target is again the nearest processor node, but the address is built from the TIO's own interrupt registers (an eight-entry configuration and enable family at `0x40_9000_1080 + n * 0x100` and `0x40_9000_1800 + n * 0x80` in the TIO window, each slot claimed by a matching processor id, returned as `0x40_9000_1000 + n * 0x100 | tio_nasid << 40 | bit 38`), and `tio_intr_init` writes `0x48_9000_0300` and `0x48_9000_0980` (the INT5 analogue, `0xe9` vector). Decompile only; not re-read in the listing; inferred. The Altix 350 and the Prism riser use the PIC path above.

### Implementer questions

1. **Does a store to `ipi_int` deliver when `0x1_1000_0400` is unset?** Unknown. Observed: the PROM writes 1 to it at two sites only, `0xffa10f40` (the sender's own node, before the wake stores) and `0xffa31290` (the node it programs the INIT pair on). Linux v5.3 (`irq.c`, `sn2_smp.c`, `setup.c`, `intr.h`, `shub_mmr.h`) never writes, reads or names it; `sn_send_IPI_phys` stores the message to the target node's `ipi_int` and nothing else (software expectation: Linux needs it either unset-tolerant or already set by firmware). Whether any PROM store to `ipi_int` precedes the write is not settled: the replay path (`0xffa101e0`) is on the second reset path whose selection was not decoded, and the immediate berr and PMI senders have no visible earlier write. What would settle it: a SHub 1 register specification entry for `0x1_1000_0400`, or a capture of a store before and after setting it. Until then a permissive model (deliver whatever the enable holds) breaks neither source, while a gating model would drop IPIs to nodes where neither firmware nor Linux ever sets it; treat any gate as a guess, grade unknown.
2. **Do RTC comparators fire on equality or when the counter has passed the compare?** Unknown. Software-expectation evidence only. `mmtimer.c` (v4.9, `mmtimer_setup`): after writing the compare it re-reads the RTC and treats `now <= expires` as armed; otherwise "we might've missed our expiration time" and the caller fires the timer in software ("Late setup, fire now"), or retries for interval timers. That reads as software not relying on a past compare firing, which favours equality-only, but it is also what a careful driver would write for a level comparator with an interrupt already pending. Its writing of all ones to the compare before enabling is needed under either rule. `mmtimer_interrupt` accepts `expires <= rtc_time()`, so a late interrupt is tolerated. The PROM (`0xffa318a0`) writes config, compare, then enable with no read-back, so a small delay whose compare is already past at the write is not handled either way. A model that fires when the counter is greater than or equal to the compare satisfies every site read; equality-only risks never firing a short PROM delay. What would settle it: the SHub specification's comparator description, or a hardware test writing a past compare with the enable set.
