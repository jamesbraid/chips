# SHub 2: address map, identification register, reset-path accesses and memory set-up

The SHub 2 node controller as the SHub 2 first-stage and second-stage firmware sees it, written for someone modelling the chip. The firmware image is `shub2snprom.bin` from snprom 10.54 build 70399 (sha256 `3ea833181fda8968a5297043f2260d2fc255983ecca1d418292ee008b5e2c793`, checked against the root's checksum list; 12 MiB mapped at `0xff400000`). Its banner reads "SGI SAL Version 1.54 rel081111 IP65 built 07:28:01 AM Nov 11, 2008" (the earlier SHub 2 build held is 1.40 from package 10.40; [images.md](../../software/firmware/snprom/images.md) did not record 10.54's version). The FIT places SAL_A at `0xff674000` (0x3000 bytes) and SAL_B at `0xff401000`. The chip family is described in [README.md](README.md); SHub 1 is the contrast throughout ([prom-reset.md](prom-reset.md)).

**Grades.** *established*: read in full in this image (code path, table or string) or defined by Linux v5.3. *inferred*: reasoned, reasoning given. *unknown*: not settled. A value the firmware tolerates is a software expectation, not a hardware fact. No SHub 2 reference manual is held; no register here has an established reset value.

**Tools.** Every code reading below was done in Ghidra with the IA-64 processor module (`re-run --ghidra-export IMAGE --sn2-prom`, decompiler output plus the module's slot listing for exact sites). Names marked "PROM name" come from the register-name table the image carries for its error decoder (strings in the shipped binary: a table of name, address and field list, with bit ranges); that table's bit ranges have not been decoded, so any field range quoted from it is unverified unless section 4 says the code confirms it. Linux v5.3 names (`arch/ia64/include/asm/sn/addrs.h`, `shub_mmr.h`, `arch.h`, `sn_sal.h`, `arch/ia64/sn/kernel/setup.c`) are cited as "Linux". Objdump was used only to cross-check one routine's bytes.

## 1. Address map

### Address forms the firmware issues

The firmware runs in physical mode with bit 63 set on every device address (uncached). Two MMR window bases, both in node-offset bits below the node number:

| Window | Base | Form | Source |
|---|---|---|---|
| Local MMR | `0x2_0000_0000` | `0x8000_0002_0000_0000 + offset` | SAL_A and SAL_B constants (established); Linux `SH2_LOCAL_MMR_OFFSET` (established) |
| Global MMR | `0x3_0000_0000` | `0x8000_0003_0000_0000 \| (nasid << (40 - V)) \| offset` | SAL_B routines at `0xff414e00`, `0xff414fa0`, `0xff4aeaa0` (established); Linux `SH2_GLOBAL_MMR_OFFSET` (established) |

Register offsets are the 32-bit values of the PROM name table and of Linux `SH2_` constants (Linux's `SH2_RTC` is `0x2_101c_0000`, which already carries the local window; the PROM's name table lists the same register as `0x101c_0000`). The offset space is 32 bits wide (up to `0x3fff_ffff` in the table), with a few registers at offset bit 32 (Linux `SH2_PTC` `0x1_7000_0000`).

### NASID shift and mask (established as the firmware's computation)

SAL_A selects the node-addressing parameters by V, the 64-bit value read from `0x2_2011_0000` (PROM name `SH2_ADDRESS_MODE`; field `CODE` bits 2:0, bits 63:61 reserved). It shifts V left by 3 and loads a row pointer from the five-entry array at `0xff676280` (`0xff6745e0` to `0xff674606`; no mask and no range check), and the pointers lead to rows of 0x80 bytes at `0xff676000 + 0x80 * V`. Row V holds, in order:

| V | NASID shift (40 - V) | NASID width (10 + V) | NASID mask | AS shift (38 - V) | node-offset mask |
|---|---|---|---|---|---|
| 0 | 40 | 10 | `0x3ff` | 38 | `0x3f_ffff_ffff` |
| 1 | 39 | 11 | `0x7ff` | 37 | `0x1f_ffff_ffff` |
| 2 | 38 | 12 | `0xfff` | 36 | `0xf_ffff_ffff` |
| 3 | 37 | 13 | `0x1fff` | 35 | `0x7_ffff_ffff` |
| 4 | 36 | 14 | `0x3fff` | 34 | `0x3_ffff_ffff` |

The row also holds the three AS values (1, 2, 3 shifted by the AS shift: GET, AMO, cacheable), the value `shift - 4` (36 at V=0, the same quantity Linux's `SH2_NETWORK_BANK_OFFSET` uses), a copy of the AS shift and the width. The NASID field therefore always ends at bit 49 and starts at 40 - V. The firmware stores the row's address (low 32 bits, bit 63 set) in a register, `0x2_101d_0c00` (PROM name `SH2_SCRATCH24`), and every later NASID shift is read back through it: that register is firmware scratch, not a chip identity register. The PROM's `SN_SAL_GET_SN_INFO` (SAL_B at `0xff5838b0`, read in full) returns mask `(1 << (V + 10)) - 1` in bits 15:0 and shift `40 - V` in bits 23:16 of its second value, and in the first value shub type 1 (bits 7:0), log2 of the maximum node count `V + 10` (15:8), a log2 sharing-domain size of 9 or 11 by bit 54 of the node-id register (23:16, section 2), the node's NASID shifted right by 9 or 11 as the coherency id (39:32) and a region size of `1 << (bits 2:0 of 0x2_0003_0000)` (47:40); the partition id is a byte of the node record that `0xff423310` fills (established). Linux then takes `as_shift = shift - 2`, which matches the table (established).

A value of V above 4 indexes past the pointer array (the word after it is `0x1f000404`); the firmware does not mask or check it (established as the code; the hardware never reports it on a working chip is inferred).

What V is on real hardware is unknown; the shipped table covers 10 to 14 bit node numbers, and Linux's `MAX_NUMALINK_NODES` of 16384 is the V=4 case (established).

### How the local and global windows split

The Linux offsets 0x2_0000_0000 and 0x3_0000_0000 are bit 33 and bits 33:32 of the address. With shift 36 to 40 the AS field starts at bit 34 to 38 and the NASID field above it, so both offsets lie inside the node-offset field (below the AS bits), not in the NASID or space-id field SHub 1 uses (SHub 1 puts the local MMR space id 2 in the NASID field: `0x80_0000_0000`). Reading of what the firmware does, all established as the addresses it forms:

- A local MMR access is `bit 63 | 0x2_0000_0000 | offset` with the NASID, AS and every bit above 33 clear. It needs no node number.
- A global MMR access to node n (including the issuing node itself) is `bit 63 | 0x3_0000_0000 | (n << (40 - V)) | offset`: the same address with bit 32 also set and the node number in the NASID field. The firmware computes `40 - V` from the register at `0x2_2011_0000` every time it forms such an address.
- So bit 33 selects MMR space and bit 32 selects "use the NASID field": inferred (it is the only reading that fits every address constant; no document states the decode). That the chip ignores bit 32 when the NASID field is nonzero, or treats AS bits as anything but zero in these accesses, is unknown.
- The SAL_B per-node scratch words are reached the same way: `0x3_0000_0000 | (id) << (40 - V) | 0x5003_15xx` (tables at `0xff5fa618` and `0xff5f73c0`): offsets `0x5003_1590`, `15b0`, `15e0`, `15f0` and `0x5003_12c0`, `1280`, `15c0`, `1b50` and the like (established as constants; use unknown).

The routine at `0xff414e00` builds a global address from a 16-bit compact id: bits 6:0 and 15:10 become the node number as `((id[15:10] << 7) | id[6:0]) << 1` (an even NASID, SHub), bits 9:7 index an eight-entry table at `0xff5fa618`: `0x5003_15e0`, `15f0`, `1590`, `15b0`, then `0x1000_0880`, `0980`, `0a80`, `0b80` (established). The routine at `0xff4150b0` forms the TIO form (odd NASID): `bit 63 | nasid << shift | (1 << (38 - V)) | 0x8000_0000 | offset` with no global bit, matching Linux's `(1 << AS_SHIFT)` TIO form (established as the arithmetic; chiplet meaning from Linux header comment, inferred).

### The memory window

- Cacheable memory space is AS = 3: `(3 << (38 - V))` (table entry; Linux `AS_CAC_SPACE`, established). The firmware addresses its own node's data area at node offset `0x100_0000` (16 MiB) through the local compatibility space as physical address `0x100_0000` with bit 63 clear (about twenty pointer loads at `0x100_0010` to `0x100_0070`, established) and another node's as `0x8000_0000_0100_0000 + (3 << (38 - V)) + (n << (40 - V))` (routine `0xff4d0350`, established). That the two address the same bytes on the local node is inferred.
- AMO space is AS = 2 and GET is AS = 1 (table entries, established; same values as SHub 1 per Linux).
- Remote flash remap: the register at `0x2_2011_0008` (PROM name `SH2_FIRMWARE_REMAP`: `ENABLE` bit 60, `OFFSET` bits 32:24) is written by `0xff420910` with `(arg & 0x1_ff00_0000) | 1 << 60` (established access; meaning inferred from the name).
- I/O: the firmware prints "SHUB2 does not support XIO I/O." (established string). SHub 2 has no II big or small windows (SHub 1's `0x1c0_0000` window arithmetic does not apply); I/O sits behind the TIO nodes (odd NASID, Linux `TIO_IO_BASE`, established).

### Differences from SHub 1

| | SHub 1 | SHub 2 |
|---|---|---|
| NASID field | bits 48:38 fixed, 11 bits, shift 38 (Linux fallback and SAL 5.04 constants) | bits 49:(40 - V), 10 to 14 bits, shift 40 - V, V from a register |
| AS shift | 36 | 38 - V |
| Local MMR window | NASID-field space id 2: `0x80_0000_0000` | bit 33: `0x2_0000_0000` |
| Global MMR window | node-offset top bit: `0x8_0000_0000` | bits 33:32: `0x3_0000_0000` |
| Register offsets | `0x1_xxxx_xxxx` (bit 32 set) | `0x xxxx_xxxx` below bit 32 (mostly SHub 1 offset minus `0x1_0000_0000`) |

Cross-check against [address-map.md](../../platforms/sn2/address-map.md): its constants for both windows agree. Its "SHub 2 NASID shift and mask: unknown" is settled here for the firmware's view: shift `40 - V`, mask `(1 << (V + 10)) - 1`. Its question "how SHub 2 splits local and global MMR" is answered above at inferred grade.

## 2. The identification register

**Address.** Local `0x2_1006_0f00`, global `0x3_1006_0f00 | (nasid << (40 - V))`. PROM name `SH2_NODE_ID`. The Linux v5.3 header defines only the SHub 1 counterpart (`SH1_SHUB_ID` at `0x1_1006_0580`, revision field bits 31:28 only) and no SHub 2 identification register, so nothing here is Linux-defined; the layout below is read from the image's own field table (established as the table's content; the field meanings are inferred from the names).

| Bits | PROM field name | Notes |
|---|---|---|
| 0 | `FORCE1` | reads 1 by its name (inferred) |
| 11:1 | `MANUFACTURER` | no code reads it (established: no reader found in SAL_A, SAL_B or the runtime) |
| 27:12 | `PART_NUMBER` | no reader found; value unknown |
| 31:28 | `REVISION` | read by the routine at `0xff4adaf0` (below); the encoding is unknown (Linux: SHub 1 revision at the same bits) |
| 45:32 | `NODE_ID` | the node number; the firmware reads `(value >> 32) & mask` with the mask from section 1 |
| 47:46 | `SHARING_MODE` | read as `(value >> 46) & 3`; the firmware also writes it |
| 53:48 | `NODES_PER_BIT` | the firmware reads bits 53:49 (5 bits) to size a bit vector, and writes the 6-bit field |
| 54 | `SHARERS_1K` | tested by the firmware: clear selects a sharing domain of 512 nodes (log2 9) and shifts the node id by 9, set selects 2048 (log2 11) and 11 (`SN_SAL_GET_SN_INFO`, `0xff5838b0`; and the coherence-id computation) |
| 55 | `RANGE_CHECK` | set by the firmware in a later phase |
| 56 | `NI_PORT` | no reader found |
| 57 | reserved | |
| 58 | `SYSTEM_TYPE` | no reader found |

Where it is read (established): SAL_A never touches it. Almost every later read of the node number goes through the routine at `0xff420290` (the routine at `0xff4d0350` has about 40 inlined copies of it), which returns `(read(0x2_1006_0f00) >> 32) & (*(table row + 0x38))`, the row being the one SAL_A left in `0x2_101d_0c00` (about 260 call sites). The runtime's `SN_SAL_GET_SN_INFO` reads it for bit 54. The interconnect phase (outside the reset path) writes it on a node: `NODE_ID` from the discovered number (14-bit field), `SHARING_MODE` in 47:46 as 0 for fewer than 32 nodes, 1 below 64, 2 below 128, else 3 (from the node count), `NODES_PER_BIT` from the sharing group size (1, 2, 4, 8, 16 or 32 per bit), and `RANGE_CHECK` set (routine `0xff4a9880`, established).

**The chip identification word (offset 0).** The part number and revision the firmware acts on are read from offset 0 of the node, not from `SH2_NODE_ID`: local `0x2_0000_0000`, global `0x3_0000_0000 | (nasid << (40 - V))`, the same place the SHub 1 firmware reads at `0x1_0000_0000`. The routine at `0xff4231e0` (called early in `main`, `0xff42b790`) does one 64-bit read through `0xff419e80` and stores bits 27:12 as the part number and bits 31:28 as the revision (established). It then offers the part number to three method tables in turn (array at `0xff5fd888`); each table's method 1 accepts exactly one part number: `0x254` (596, first table), `0x239` (569, second), `0x4422` (17442, third); a miss leaves the node's table pointer 0 (established). Which chip each is: unnamed in the image. The first table is the one the node-level code of a SHub 2 uses (inferred from table order against the SHub 1 firmware, which lists its SHub part number first; `0x239` and `0x4422` also appear in the SHub 1 firmware's list, where they are not SHub 1, so they are probably the router and TIO parts; inferred). The register has no entry in the image's name table, so its name and field layout beyond those two fields are unknown.

**What the PROM does with the `SH2_NODE_ID` fields 31:1.** Part number and manufacturer: no read of the register extracts them (established by listing all 59 sites that form its address; the other readers extract bits 45:32, 47:46, 53:49 or test bit 54). Revision: the routine at `0xff4adaf0` (slot 39, offset `0x138`, of the first method table) forms the node's address (global form for an even NASID, TIO form for an odd one), reads the register and returns bits 31:28; the caller near `0xff4ba84c` calls it through the node's method table and stores the byte at offset 7 of a record. No comparison of the revision was found, but the routine's callers were not all traced, so "never tests" is not established for the revision. Compared with SHub 1, which selects among four method tables by part number (first `0x4363`), SHub 2 selects among three (first `0x254`).

**What a model must return.** Bits 45:32 = this node's NASID, even (SHub) and fitting the V in section 1. Bit 54 consistent with the intended sharing-domain size (0 for a domain of 512). Bits 47:46 and 53:48 hold whatever was last written, 0 before the firmware writes them (inferred: the firmware writes before it relies on them; no read before a write was found). The register must be writable in bits 55, 53:46 and 45:32. The offset-0 word must return part number `0x254` in bits 27:12 for the SHub 2 method table to be selected (inferred as the SHub 2 part; a value that matches none leaves the node without a method table and later calls through it fail); the revision field 31:28 of the offset-0 word is stored and no test was found (the method tables were not traced exhaustively); real revision encodings are unknown. `SH2_NODE_ID`'s own part number and manufacturer fields: any value passes. Its revision field is returned by the method at `0xff4adaf0` and stored; no test was found, so any value passes the traced paths.

**Unknown.** The real revision encoding and manufacturer code; the register name and layout of the offset-0 word; the reset value of `NODE_ID`; whether bit 58, 57:56 mean what their names say.

## 3. Reset-path accesses (SAL_A, the SAL_B reset entry and the start of `main`)

Order and form follow [prom-reset.md](prom-reset.md). Sites are PROM addresses in this image (Ghidra module listing). R is a read, W a write; widths are 64 bits unless given. Names are the image's own register-name table (PROM name) where it has one; Linux v5.3 defines only `SH2_IPI_ACCESS0..3` and `SH2_RTC` of the registers below, apart from the LED ports. Every address is shown as its offset in the local window (`0x2_0000_0000 + offset`, bit 63 set); "what a read must return" is the software expectation, not a hardware reset value. Grades: *established* means the instruction, address, width and direction were read in full here; meanings are *inferred* unless stated.

### The progress write

SHub 1 wrote a history word in scratch memory and two LED registers per code. SHub 2 does one 16-bit store of the code to `0x2_f000_0000 | ((cr.lid >> 23 & 3) << 16)` (the four "real junk bus" LED ports, Linux `SH2_REAL_JUNK_BUS_LED0..3` at `0xf000_0000 + 0x1_0000 * n`, established), so slice n writes port n. No history word and no second LED register. The PROM's name table also has four LED registers at `0x1003_0000 + 0x80 * n` (`SH2_JUNK_BUS_LED0..3`, field `LEDn_DATA` bits 7:0), which the firmware reads (`0xff420420`, `0xff420760`: R64 `0x2_1003_0000 | slice << 7`) only to remember the current code while it waits on a lock, and to pass to SAL_B from SAL_A on reasons 1, 2 and above 3 (`r31`). Any value is accepted; nothing branches on it (established). Codes on this path: `0x30` (SAL_A hand-off), `0x31`, `0x35`, `0x08`, `0x0c`, `0x0d`, `0x0e`, `0x10` and onward; `0xb0` to `0xb4` are fatal stops.

**The node lock (L).** Routine `0xff421430` (set or clear a bit) and `0xff421ad0` (set a field) of `SCRATCH6`; the same shape on `SCRATCH7` at `0xff4ae770`. One cycle: R64 `0x2_1003_0000 | slice << 7` (remember the code); R64 `0x2_101c_0000` and `0x2_1006_0700` (clock); R64 `0x2_101d_0208` (`SCRATCH4_ALIAS`) repeated until it reads 0 (`0xff421f10`), with a 1000-microsecond wait between reads (`0xff423680`; every 100 ms of waiting it also writes the progress code, alternating `0x0f` and `0xf0`) and a 1,000,000-microsecond deadline after which the firmware writes 0 to `0x2_101d_0200` (`SCRATCH4`) and keeps polling; then R `0x2_101d_0300`, W `0x2_101d_0300` with the bit (`0xff421430`) or field (`0xff421ad0`: position, width and value arguments) changed; W `0x2_101d_0200` = 0 to release (`0xff422020`); the saved progress code is then written back (established, re-read in code for this page). A bit test (`0xff421c30`) and a field read (`0xff421e30`) are plain reads of `0x2_101d_0300` without the lock. The node-addressed versions (method slots `0x0f8` and `0x100`, `0xff421580` and `0xff421cb0`) do the same on `A(n, 0x101d_0300)` with `A(n, 0x101d_0208)` and `A(n, 0x101d_0200)`. Hardware behaviour of `0x...0208` on read (a read-to-take lock) is unknown; a plain register that always reads 0 satisfies every access. SHub 1 used the same offsets `0x101d_0200/0208`.

**Second lock and claim.** `0xff4221b0` (claim bit n in `0x2_101d_0280`, `SCRATCH5`, with an optional deadline) and `0xff422c90` (clear): poll R `0x2_101d_0280` until bit n is clear, take `0x2_101d_0188` (`SCRATCH3_ALIAS`, read until 0), test-and-set the bit, W `0x2_101d_0180` = 0 to release (established). Not on the direct reset path (callers are indirect).

### `main` (`0xff42b9c0`) from the node election to the first console message

Read in Ghidra (decompiler and the module's slot listing, objdump not used). `main` calls, in this order after progress `0x08`: `0xff4b2850(0)` (M2; it writes progress `0x0c`, and for argument 0 ends by calling the barrier of M3 and then clearing this slice's own 3-bit field of M2a), the barrier `0xff4b2c90` again (M3), progress `0x0d`, the chip identification read `0xff42b790` (M4), then `0xff42c8b0`, `0xff5b2f40`, `0xff430b00`, `0xff43b460` (M5 to M8), and the console print of "Prom starting..." (M9). Grades as in section 3: *established* means the instruction, address, width and direction were read in full; *software expectation* is what the code needs, not what the chip does.

**The address form every later access uses.** After M4 almost every chip access goes through two small routines: `0xff4207a0` reads 64 bits and `0xff420840` writes 64 bits at the address it is given. The caller builds that address from a node record whose first halfword is the node id `n` (a 16-bit value; even is a SHub, odd a TIO). Each access reads the V register `0x2_2011_0000` (once or twice) to get the shifts, then forms

- even `n`: `bit 63 | 0x3_0000_0000 | (n << (40 - V)) | offset`
- odd `n`: `bit 63 | (n << (40 - V)) | (1 << (38 - V)) | 0x8000_0000 | offset`

(established, sites such as `0xff4a4100`, `0xff4a71c0`, `0xff4f9a20`). Below, `A(n, off)` means the even-node form and the node is the issuing node unless said otherwise; the 32-bit `off` is the same offset space as section 1. A model therefore sees roughly two reads of `0x2_2011_0000` before every access in M5 to M9; that register must keep returning the same V (section 1) and these reads need no other state.

A second primitive: node-level tables of method pointers. The node record's table (the one M4 picked, `0xff5fce08` for part number `0x254`) is an array of function descriptors; the code calls "slot `0xNNN`" as `table + 0xNNN`. ### Differences from SHub 1

- Progress codes go to one junk-bus LED port by a 16-bit store; no history word at `0x1_5003_1500 + 16 n`.
- The firmware's shared scratch word is `0x2_101d_0300` (SCRATCH6, was `0x1_5003_1550`), its second word `0x2_101d_0280` (was `0x1_5003_1540`), third `0x2_101d_0380` (was `0x1_5003_1560`); the lock registers keep the same offsets `0x101d_0200/0208` and `0x101d_0180/0188`; the election pair `0x101d_0080/0088` is the same, now with slice + 1 up to 8.
- SAL_A writes `SH2_IPI_ACCESS0..3` (four registers) and `SH2_PIO_RQ_CRD_CTL`; there is no write of a constant `0x1503_1010` as SHub 1 A1.
- The clock control is `0x1006_0700` (`SH2_GC_SRC_CTRL`), a different offset from SHub 1's `0x1006_0280`, with the same start sequence.
- The node number is read from `0x1006_0f00` bits 45:32, not `0x1006_0580` bits 42:32; the part number from offset 0 as before (`0x254` first).
- The firmware's node-addressing table row is held in a SHub register (`SCRATCH24`) instead of a constant.

### The memory test engine

The "Testing memory" phase drives a self-test block (the PROM calls it MBIST) through the registers below. The output "MBIST_ERR, FRU..., ADDR:" and "MBIST TIMEOUT Byte Address" come from it.

| Offset | PROM name | Direction and use | Grade |
|---|---|---|---|
| `0x2_0080` | `SH2_MMRBIST_BASE` | write the start address | established (access); inferred (meaning) |
| `0x2_0088` | `SH2_MMRBIST_CTL` | write the command word, then poll. | `0xb8`, `0xc0` | `SH2_MEM_ERROR_SUMMARY`, `_ALIAS` | read after a failure and acknowledged through the alias (`0xff4809e0`) | established (access); inferred (acknowledge) |

**What a model must return to pass.** `0x2_0088` must show `IN_PROGRESS` (bit 40) clear soon after the command write (it is polled with a 2,000,000-microsecond limit, `0xff41c990`), `FAIL` (bit 41) clear, and `MEM_IDLE` (bit 42) may be anything. The `XBIST` and `YBIST` registers must hold what was written (the firmware does not read the pattern registers back on a pass). Error registers read 0 on a pass. With "Skipping memory test, as requested" (the console option) the PROM does not write these.

**Not read.** The numeric values written to the timing registers, the way the firmware chooses `CMD` and `BLOCK_LENGTH` per DIMM, the order of the sixteen BIST writes against the `ARM` writes, the exact poll loop in `0xff47bb60` (which of two registers it reads second), and the DIMM discovery over the L1 (it is serial traffic to the L1 controller, not chip registers). These are **unknown** here; the questions page should list them.

## Review (address map)

Independent review of the first four sections of this page: the address map (chips `562e128`), the identification register (`f7efee0`, corrected in `c3e5e21`), the reset-path accesses (`96896e8`, `1900546`) and the memory and directory registers (`9faa773`, `0cc9a99`), examined at chips `eb356ea`. The reviewer wrote none of it. Method: `shub2snprom.bin` from snprom 10.54 (sha256 `3ea83318...2c793`, matches `root/sn2/SHA256SUMS` and the page; banner "SGI SAL Version 1.54 rel081111 IP65 built 07:28:01 AM Nov 11, 2008" read from the image) loaded at `0xff400000` in Ghidra with the IA-64 module.
